# Isolated spaces: stages

Read [DESIGN.md](DESIGN.md) first.

## Delivery rules

- One stage is one small pull request into `main`. The maintainer reads and merges each one, so a stage must be readable in one sitting. If a stage grows, split it.
- The whole feature stays behind one switch. While the switch is off, the server registers none of the feature's routes, the UI shows none of its entry points, and nothing of the feature runs at all: see decisions 17 to 19 in [DESIGN.md](DESIGN.md). The switch gates the work while it is built, and at the first release it becomes the user's opt-in in Settings rather than being removed. The stage that builds the feature's settings screens builds it.
- Before each pull request: run the local bot review and fix its findings, run every escape test that exists so far, and complete the stage's checklist from [TESTING.md](TESTING.md).
- A checklist line has two states: "passed, here is the evidence" or "blocked, here is the reason". There is no "skipped".
- A personal integration branch for daily use is optional. Delivery goes through `main`.
- Stage 4 overlaps with the `opencode-v2-refactoring` branch (proxy, event frame format, the `translate-v2` layer). Before starting it, confirm the frame format is final and build after that layer.

The contract test suite is written in stage 1 and stays fixed against being rewritten per place. It is not frozen against a new stage: stage 2 added three assertions to it and changed none of the existing ones. The three are that the gatekeeper target runs in a container of its own, that `exec` knows those two targets and rejects any other, and that the gatekeeper is gone after `remove`. Each of them is marked in the file, and each was confirmed to fail against a place that fakes a gatekeeper. From stage 2 on, a place cannot host a space without a gatekeeper, so every later place is held to that too. A later place is done only when it passes the whole suite, including every escape test.

An obligation on whichever stage first puts a real credential behind the window: on Linux, any local process can reach the corridor and the window. A Linux Docker host routes into the bridge subnet, so no published port is needed, and the window authenticates nothing. Measured on Debian 13, amd64, Engine 29.8.1, from the host and not from a container. macOS and Windows hide it behind a virtual machine. The space cannot use it, so this is not about the agent; it is about an unprivileged local process spending the user's model key. Two ways to close it, neither chosen: a secret the host hands the window with the grant and every request carries, or binding the window to the space's inner address alone, which needs no change to the create order: the bind address is an argument of the program, and the program is delivered after the container is running, when Docker has given it both addresses. Whichever it is, it belongs in the same pull request as the first real credential.

Things stage 2 leaves for the stages that build the screens, most of them in the module's "Known limits" as well:

- Grants and the allowlist live in the gatekeeper's memory only, so they have to be set again after every start of a space, and after the machine restarts the space shows "needs access". DESIGN.md says that is what the user sees; some stage has to actually do it.
- The journal is memory only too. The blocked-attempts view shows nothing from before the gatekeeper last started, and it has to say so. An empty list that means "the record is gone" must not read as "the agent tried nothing".
- Turning the switch off stops every space and keeps its files, and the banner beside the switch has to say so before the user commits, with the count. Removing spaces is a separate action offered after the switch is off, never a checkbox beside the toggle: see decision 18. A space that could not be stopped is reported as still running.
- The current grant API requires a secret, while DESIGN.md defines a grant as a credential **or an opened domain**. The stage that builds the grant dialog must support an upstream without a credential, with the window adding no credential header. This is also the route for explicitly granting a private registry or mirror; the corridor refuses private addresses in both modes, regardless of its allowlist. For npm, verify package metadata and tarball downloads end to end through the window, including absolute tarball URLs that name the private upstream. Whether npm needs URL rewriting, and whether `replace-registry-host=always` provides the required behavior, remains unverified. Establish that behavior before choosing the configuration.
- A gatekeeper that has been removed is never made again. `start` brings back a stopped one, but a removed one means the space has to be applied or discarded and a new space made. Whichever stage owns a space's status and its repair actions has to say that in plain words.

Stage 3a leaves one check for the stage that first calls code in from the app: quit the packaged desktop app in the middle of a transfer and confirm that no `git` or `docker exec` is left on the host. The exit handler that kills a transfer was measured in a Node process and in a bare Electron process, never in the packaged app.

Later, in no fixed order: project-defined images, submodules, sandbox services, Copilot through the gatekeeper.
