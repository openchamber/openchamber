# Chat scroll

The transcript is a LegendList (`@legendapp/list`) owned by `useChatTimelineScroll`. These files hold the scroll logic that list does not do on its own: anchoring, end-keeping, restore and the mobile keyboard glide.

## Keeping the end

- **A row that shrinks as the chat widens is measured in the same frame.** LegendList on the web applies a smaller row height a frame late, to ride out transient shrinks; for text re-wrapping at a new width that left the rows below and the pinned end a frame behind on every frame of a resize, and a pinned reader's text jumped up and back by 70 to 200 px each frame while the chat widened. Our patch (`bun-patches/@legendapp%2Flist@3.6.0.patch`, `processContainerLayout`) applies a shrink at once when the row's width changed; carry it over when bumping the library. The end is still taken from the measured bottom of the last real row (`resolveRealContentEndOffset` in `timelineScrollAnchoring.ts`), not from `scrollHeight`, which can trail the rows.
- **The list footer counts.** `list.getState()` does not expose `footerSize`; the footer ends with a spacer (10vh on desktop, 40px on mobile), and its size arrives through the list's `onMetricsChange`. Ignoring it leaves the viewport about 80px short of the end.
- **End-keeping is ours, not the list's.** `MessageList` passes `maintainScrollAtEnd={false}`: the library's option did not keep the viewport pinned while one tail row grew during streaming. At rest the hook's pin is a same-frame `scrollTop` write, and it holds the measured end through a width resize. While a reply streams, `followEnd` glides instead (the reply lands a block at a time, at most every 400 ms, see `lib/streamTextCommit.ts`, so each landing is one short glide): once per frame it issues a native smooth scroll to the end (it lets one already moving toward the same end finish), and jumps to one screen above the end first when the viewport is further behind. Readers with `prefers-reduced-motion` get an instant scroll instead of the glide. Scroll the node directly: `list.scrollToEnd()` per chunk goes through the library's programmatic-scroll bookkeeping and roughly doubles frame production.
- **The list's state says whether to act; the scroll node says where the end is.** In the follow frame, a glide still moving toward an end the list's state has not moved is left to finish, decided from `getState()` alone, so those frames read no layout (`isFollowGlideUnderWay`). Whenever a glide is issued or the end is checked, the target comes from `scrollHeight`: the list's `contentLength` lags the DOM (a row is placed at its estimated height before it is measured, and the footer, whose tail spacer shrinks with the composer after a send, is measured a beat later without a size event), and a glide aimed by it stopped short of the end. While a glide runs, growth re-aims it from where it is, as one motion. Where it lands is checked only as a last resort: a gap of up to 4 px (`FOLLOW_LANDING_SNAP_MAX_PX`) closes with an instant write, too small to see, and anything larger goes through the follow rules again instead of a visible second glide. A native `scroll` listener that needs the current offset reads the node too: the list updates its `scroll` a frame after the event.
- **The follow stops at the start of what outgrew the screen.** A live turn grows past the screen, and following its end would scroll away what the reader wants to read from the top. `findFollowStops` names where the follow may stop, top first: with Activity Default set to Collapsed, the end of the reader's message (the start of the live turn's work, the topmost of the turn's rows after its prompt row, `[data-turn-row]`, so the compact work and the answer land right under the top edge); in both modes, the start of the reply being written (`data-streaming-reply` on `AssistantTextPart`, with a 16 px gap). With the sticky user header setting on, both starts land under the turn's `data-turn-sticky-header` instead of the top edge, so the message stays on top, and "taller than the viewport" below counts the header against the viewport. Once gliding to the end would carry such a start above the viewport and the turn or reply itself is taller than the viewport minus the list footer (the band the composer covers), `followEnd` glides only that far and drops live follow as a gesture would (`resolveFollowStop` in `followScroll.ts`). The rest lands below, the pill offers the end, and reaching the end follows again. Each place stops the follow at most once, and only one whose start was on screen when the follow first saw it; a reader who returns to the end themselves has passed the current ones (`retireFollowStops`). Expanded keeps following the work until a long answer, since that is what a reader who picks it wants to watch.
  - The latest turn owns the row lowest in the content, measured (`[data-turn-id]` or `[data-turn-row]`: a long turn's prompt row may be unmounted far above). The list places rows in pooled containers, so document order is not timeline order, and the last match in the document was often an older turn.
  - A send retires the stops it finds, before the sent row commits, so they are the previous turn's. A previous turn that never outgrew the screen kept its stop eligible, and the sent row pushing it up stopped the follow a few pixels into the send.
  - A reply's last block lands in the same render that ends its streaming and drops `data-streaming-reply`. The follow frame after that still checks that reply once (`lastStreamingReplyRef`), so a reply whose closing table, code block or held paragraph carries it past the screen stops at its start too.
  - That last block can land in the same commit that reports the session idle, or a beat after it, and growth at rest snaps to the end without the stops. For `TURN_END_GLIDE_WINDOW_MS` (1 s) after a turn ends, growth still follows with its stops. Entering another session clears the window, so the entry pin stays one instant write. The same window also sees the turn footer and the banners docked on the composer arrive. They also carry a start off the top on the way to the end, and before the height rule they stopped the follow and left the pill up under a reader who was on the end.
  - After a stop, the list reporting the end does not bring the follow back while the turn runs (`isTurnRunning`, without the turn-end window). Once it ends, reaching the end does: the work folding away after the turn often carries a stopped reader there. The list reports reaching the end once, so a report held while the turn ran is checked again when it ends. Before this, the pill stayed up under a reader on the end.
- **Folded work above the reader closes without moving them.** When a turn settles in the Collapsed activity mode, its work folds away above the answer. The fold is a row of its own and opens and closes at once, without a height animation: the list keeps the reader's row in place when a row above it changes size, as it does for any row (see "A turn is several rows").
- **Sending glides to the true end.** `scrollToBottomOnSend` asks for a follow glide at once (a snap with reduced motion), and for the send window (`SEND_GLIDE_WINDOW_MS`) every growth glides to the true end, so the sent row and the start of the reply end up whole above the composer. A reader who scrolled away is brought back with a jump, as before.
- **A gesture over a page frame releases the follow too.** The follow lets go only on gesture events the scroll node hears: a wheel up, a vertical swipe, a middle-button pan, an upward key. A wheel or swipe over an `openchamber_render` page scrolls the transcript around the frame, but its events stay inside the frame, so while a reply streamed the follow pulled the reader back to the end on every landing. The page reports each such gesture's direction, and its frame raises it as an `openchamber:frame-scroll` event (`dispatchFrameScroll` / `onFrameScroll` in `timelineScrollIntent.ts`) that the hook reads like touch: up releases, down releases only away from the end.
- **Opening a row lets go of the end.** A tool, an agent task, a reasoning block or the folded work opens below its header. Held on the end, the reader saw the viewport slide down by the whole row as it grew, and the header they clicked went off the top. The row raises `openchamber:row-expand` (`dispatchRowExpand` / `onRowExpand` in `timelineScrollIntent.ts`) from its element as it opens, before its state changes, and the hook takes it as a gesture: the follow is released, the header stays where it was, and the content opens below it. That also holds while a turn runs, as a scroll up would. Two more pieces belong to it:
  - The list keeps its own hold on the end it opened the session at (`initialScrollAtEnd`) until the reader scrolls, and re-asserted that end as the row grew. Any scroll command ends the hold, so the release issues one to where the viewport already is.
  - Growth below a released reader fires no scroll event, so the list never reports them leaving the end. `onTimelineDataChange` measures it instead and offers the pill once the last row passes the visible bottom, as it does with auto-follow off. Closing the row brings the end back to them just as silently, and the follow resumes once the content ends exactly at the viewport's bottom: a closing row animates, and within the usual 40 px band the follow came back mid-animation and pulled the closing header up for a few frames. That check, and any report of the end reaching a released reader (the list's scroll handler, the turn ending), waits for the frame after the list's pass (`confirmEndArrived`). Mid-pass the list can read as ending at the reader with screens still below: it reports its new total before it moves the viewport for rows above the reader that measured smaller than estimated, sometimes a frame later, and rows it has just added below count at their estimated height until measured. Judged at the report, scrolling up through short rows (a session in the Collapsed activity mode) jumped back 400 to 550 px every few screens, and a reader held at the start of a long answer was slid down to the end when the turn ended and the answer was cut into rows, short enough at their estimates that the browser clamped the scroll to them. A row that grew by less than the band never left the reader off the end, so no at-end change fires for it: the hook remembers that a row opening released the follow (`rowExpandReleaseRef`) and resumes it once that row has grown and the content ends at the viewport's bottom again. Without this, the next reply that did not start from this composer went by unfollowed and with no pill.
  - Closing a row raises nothing: the content below its header shrinks, and only a reader on the end moves, by what the browser clamps.
- **A page waiting for the reader's answer comes into view.** An `openchamber_render` page with `awaitAnswer` blocks the turn until the reader answers. After a reply taller than the screen, the follow had stopped at the reply's start, and the page landed below the visible area: the reader did not see the question. The page's block raises `openchamber:page-waiting` (`dispatchPageWaiting` / `onPageWaiting` in `timelineScrollIntent.ts`) when it appears and whenever its height changes, and the hook brings it into view (`resolvePageRevealTarget` in `followScroll.ts`): whole, ending at the band the composer covers, when it fits, else its top under the top fade. This happens only for a reader no gesture released, with auto-follow on: one still following, or one a follow stop left with no gesture since (a stop in another session does not count). A reader who scrolled away, or who turned auto-follow off, keeps their place, and the pill's status label says the agent waits. Each page comes once; its height arriving later moves it again for `PAGE_REVEAL_SETTLE_MS` unless the reader scrolls, because a frame off screen reports its size only once it is scrolled into view (measured in Chromium: it stayed at 48 px below the fold). The scroll is aimed in the next frame and again on the list's growth: aimed in the same pass as the height change, it stopped at the list's old end, short of the page's bottom. A page that ends the content (aimed within the 40 px band of the end, its top still in view there) is shown with the end, and the follow comes back as the pill would bring it, so no pill is left offering an end the reader is already on. One aimed further up releases the follow, as a stop does, so growth does not carry it off again.

- **The list header never changes height.** The "Load older" header in `ChatContainer.tsx` is a fixed 48 px slot that is always there; only the button inside it toggles (shown while older history exists and the viewport is within two viewport heights of the top, `nearContentStart` from the hook). LegendList compensates a header size change only while `maintainVisibleContentPosition.size` is on, which is off for a reader on the end, so a header that came and went moved the whole transcript by its height mid-glide (after a revert, the send hid it). Anything else rendered above the rows has to keep its height for the same reason.

- **A side column's width animation holds the end on every frame and defers the rest to its end.** While the session sidebar or the right slot animates its width (`lib/layoutAnimation.ts`, 240 ms), the transcript re-wraps on every frame. The pinned-end write runs on each of them, through the same measured end as a window resize, offset by where the reader sat relative to that end when the animation began (zero for a reader on the end once the list is measured; a list still on estimates differs): deferred to the end of the animation, as it once was, the end slid down out of view (over 1000 px as a 640 px panel opened beside a long reply) and jumped back when the animation ended. The measured end (`resolveRealContentEndOffset`) is the scroll node's own end computed from the rows: list header, rows, footer, minus the viewport. It once left the header out and counted the status row's reserve again on top of the footer, came out 8 px short, and the write 350 ms after a width change (window resize, toggle, drag held still) moved a reader on the end down by that much until the next write put them back. The active-turn spy and the scroll-shadow check each forced a transcript layout per frame; they queue with `runWhenLayoutSettled` and run once, at the final width, one frame after the animation ends, and the end is asserted once more then. Markdown tables refit their columns on every width change, from natural widths measured once (`MarkdownTable`), so they move with the prose; their cells re-render only when a column starts or stops being capped.
- **A drag holds the same state for as long as it lasts, and skips the off-screen messages.** Dragging the session sidebar or a context zone holds the layout animation (`holdLayoutAnimation`) until a frame after the release, so everything above applies on every pointer frame. Most of the text the list has mounted is off screen (4 percent of 34,000 characters was visible in a 120-turn session when a row was a whole turn; 8 percent since a turn is several rows), and re-wrapping the rest cost most of each frame's layout and, with an accessibility client on, rebuilt its accessibility nodes (25 dropped frames per drag). While a width drag lasts the timeline carries `data-columns-moving`, and every message off screen skips layout at the size it last had (`content-visibility: auto` with `contain-intrinsic-size: auto`, index.css); on release they re-wrap once. Only whole messages skip: a skipped element is contained, its children's margins stop collapsing through it, and markdown blocks grew as the flag turned on (21 px for a code block, 28 for display math); a message's text already sits in a layout-contained root. The flag is not set for the 240 ms toggle animations: with an accessibility client on, turning the skip on and off rebuilt the messages' accessibility nodes, 60 to 100 ms, more than such an animation saved, and toggles dropped 3 to 4 frames more.

- **A turn is several rows.** A list row is one piece of a turn (`lib/turns/timelineRows.ts`): its prompt row (`turn-head`, the only one carrying `data-turn-id`, `id="turn-…"` and `data-scroll-spy-id`), the fold's header in the Collapsed activity mode, the pages a turn without an answer showed, and its messages. A message is cut into several rows before every 24th part it draws, and a finished text of 3,000 characters or more is cut between Markdown blocks into pieces of about a screen (`answerChunks.ts`); every row but the prompt carries `data-turn-row`, and a message's later rows carry `data-message-slice`. The list keeps the row the reader looks at in place and moves the viewport for every row above it that changes size (`maintainVisibleContentPosition.size`, on once the reader leaves the end), so nothing inside the transcript holds the reader's place on its own. When a row was a whole turn, a change inside it above the reader (a long answer's block drawn for the first time, a fold closing, a window of steps mounting) moved the text, and each such change carried its own compensation, which disagreed with the list's now and then: one jump of 38 to 145 px in about a hundred scroll steps. Opening a 120-turn session mounts a few screens of rows, not four whole answers of four to seven screens each.
- **A row is placed at an estimate of its own height until measured.** The list moves the viewport by a row's error once that row, above the reader, is measured. On iOS the move lands while the scroll's momentum runs in another thread, which takes part of it back on its next frame: the text jumps by the error and partly back. With one estimate for every row (320 px) each tool step a reader scrolled past was off by 284 px, and scrolling up through an agent's turn on an iPhone shook and barely moved: 224 corrections and 54,687 px in 12 s of scrolling. `lib/turns/rowSizeEstimate.ts` builds the estimate from what the row draws (tool and reasoning lines, text wrapped at the column's width, a patch's file rows, the pages a fold hoists): 36 corrections and 594 px on the same scroll. Heights measured in one list are not carried to the next: a row keeps its key while what it draws changes (a reasoning block opened, a slice that moved), and a stale height is a worse estimate than one built from the row. The list takes it through `getEstimatedItemSize`, which our patch adds (`bun-patches/@legendapp%2Flist@3.6.0.patch`, `getItemSize`): the per-type average it has is no help, because its first layout caches an estimate for every row before any average exists. On touch layouts the corrections that remain wait until the scroll stops (`deferSizeWhileScrolling`, also our patch): while the user scrolls, every row's position shifts by the correction instead, so the rows on screen stay put, and the shift is undone with one scroll correction 150 ms after the last scroll event, at rest. Near the start of the list (within two viewports) the correction is made at once, because the shifted first row would leave space above it, or cover the "Load older" header, in view. With corrections written during momentum, even 2 px ones stalled the momentum for a frame and caught up the next, which read as micro-stutters on every fling. Carry it over when bumping the library.
  - A piece starts only at a paragraph or a heading. Its top margin is then the whole gap the answer had there (no block's bottom margin is larger), so the first block of a later piece keeps it (`[data-answer-continues]` in index.css) and the rows stack to within a pixel of the whole answer. A text with footnotes or link definitions stays whole: they resolve across the document. A text still streaming stays one row and is cut once it finishes; the first row keeps its key, so it keeps its React tree.
  - The rows of a message share its record: the first draws what comes before the cut and the message's header, the last its footer, error and actions (`MessageSliceContext`, read by `MessageBody` and `ChatMessage`). Copying and the image export take the message's text from the record, not from the DOM. Navigation and restore find a message by its first row (`[data-message-id]:not([data-message-slice])`); an anchor taken in a later row names that row (`MessageViewportAnchor.slice`).
  - The rows of one answer read as one text. The list puts its rows in DOM order once scrolling has been quiet for half a second (`useDOMOrder` in the list), so a selection the reader makes crosses rows in reading order. The selection menu of the row a selection starts in takes one that ends in a later row of the same message (`ownsSelection` in `TextSelectionMenu.tsx`); copying serializes each row's part as Markdown and joins them (`data-answer-part`, `getMarkdownSelectionText`). A quote counts in the message's stream: the text of its mounted rows joined in reading order (`findChatQuoteRoots`), as one root's was before the answer was cut, so quotes taken before then still resolve; a quote crossing rows is painted with a Range per row. Revealing a quote in a row not mounted steps down through the message's rows (`data-message-continues`), after asking the navigation hold on its first row to let go (`openchamber:navigation-release`).
  - Every row of the live tail reads the tail's entry with the newest parts from one store (`LiveTailSource` in `MessageList.tsx`), computed once per publish, so a streamed part re-renders the tail's rows and nothing else. The rows themselves are built from the timeline's record, and a row reads whether its turn is folded from the row (`underFold`), so the rows of a live turn agree on it while the record lags the stream.
  - The sticky prompt is the list's own sticky row (`stickyHeaderIndices`): the list keeps it on top until the next sticky row reaches the top. A turn's prompt leaves with its turn instead, as it did inside one turn row: once the turn's last row scrolls under it, the scroll handler pushes it up by as much (`pushStickyHeader`, a `transform` on the row's container, measured from the DOM because the list's positions and its scroll offset do not count from the same origin).
- **A Mermaid diagram lets the wheel through.** The diagram once stopped a plain wheel at its host, and the timeline's gesture handler never heard it: a reader who scrolled up over a diagram stayed in follow, and the next change to the content pulled them back to the end. The diagram's viewer zooms only on a modified wheel and stops that one itself.

## Connected scroll work

Effect cleanup cancels follow frames and clears their scheduling sentinel, and
clears the return-to-end reassert timers. Retained hook state can schedule a new
frame after setup without changing the reader's follow intent. A cancelled
follow callback cannot consume a later connection's pending frame.

History navigation belongs to the controller's current connected lifetime as
well as its session identity. Cleanup retires that lifetime, releases local
render waiters and stops the mobile prepend watchdog. An authoritative loader
request already sent may still publish its page, but its obsolete local search
cannot request another batch or finish navigation after reconnect. MessageList
owns one pending navigation alignment loop; replacement navigation, input,
session change and layout cleanup cancel its frame and listeners.

### Why cleanup retires navigation without cancelling the loader

The loader owns shared history coverage and request reconciliation. A viewport
owns only its navigation continuation, so ending that viewport's effects stops
local movement and subsequent demand without discarding a valid shared read.

### Quote source navigation

Clicking a quote loads older history before scrolling to its source. A source
already loaded needs no request. Before paging, the client checks whether the
source still exists. A confirmed 404 stops the search and shows the
missing-message notice. Other lookup failures leave its existence unknown, so
history loading still runs. Pending quote reveal stops on user scroll input,
including while history is loading, or when the chat changes sessions or unmounts.

Assistant replies without `parentID` are absent from the controller's turn
index. Quotes use the rendered message list's own index to reach these replies.
The controller's turn indexing stays unchanged.

### Why quote reveal waits for text

Message navigation opens folded Activity before aligning the source. Its body
and lazy Markdown can mount after the scroll completes, so quote reveal observes
source mutations until the renderer is ready. Lazy Markdown fallbacks carry
`data-chat-quote-pending`, including the raw-text mobile fallback. Once the source
has mounted without a fallback, an unresolved anchor ends the search. Mutations
inside unrelated messages do not schedule another lookup. A new reveal, user
input, scroller/session change or unmount disconnects that observer. There is no
per-frame polling while waiting.
Legacy quotes use GFM with chat's double-tilde rule and preserve the renderer's
structural whitespace and code headers before matching the rendered text stream; a repeated
fragment without context remains ambiguous. Saved modern anchors stay literal.

## Session list retention

`ChatViewport` keeps up to four `MessageList` subtrees, including the visible
one, through `KeepAlive`; the mobile surface keeps only the visible one, because
a phone's web view is killed under memory pressure. Entries are keyed by
session ID: the composite session key also carries the directory, which settles
after a session opens, and keying the pool by it retained a hidden second copy
of the open session. Inside an entry the list still remounts on a session key
change. The shown selection drives the LRU; loading, error,
empty and draft placeholders hide the pool without replacing its host. Leaving
the chat column releases the pool. Each stored JSX entry supplies its own
`ChatColumnSessionContext`, so hidden messages retain their session identity.

The scroll hook and timeline controller remain shared by the column. List
registration names the composite session key; a late detach from a hidden list
cannot clear the selected list. MessageList's imperative ref cleanup clears
only its own handle, and DOM navigation resolves only its own scroller.
Scroll-shadow cleanup clears the outgoing node's attributes because hidden
scrollers remain siblings of the shared fade and still match its CSS selector.
Restoration and reveal continue through the existing column logic.

The UI pool does not pin histories or change loader retention. Returning to an
entry supplies current authoritative messages through its existing props.
Loader request generations do not control UI identity: a tail refresh can
advance them without replacing history. Runtime changes replace the pool. Hidden JSX
can retain old message references until LRU eviction or column teardown, so
the entry limit is a count bound, not a byte budget.

### Why the pool sits at MessageList

This is the existing session-keyed replacement point. Retaining it preserves
the list, turn state and mounted Markdown without duplicating the composer or
the column's scroll controller. KeepAlive renders entries in stable key order;
LRU promotion changes visibility without moving retained iframe DOM.

## Row identity

- **A row keeps its React tree when it becomes or stops being the live tail.** Every row renders through `TimelineRow` in `MessageList.tsx`; only the tail's rows read the streaming parts. The tail moves on every send and on a revert. When the tail had its own component type, the moving row remounted, its state reset for one commit (a long user message lost its "Show more" link, 28 px), and LegendList measured that commit in its layout effect. The `ResizeObserver` never corrects such a size, because the short height was never painted, so the row below sat that much too high until a later re-measure: 40-80 ms after a send, and from the revert until 200 ms into the next send. Anything that remounts or resets state inside a mounted row has the same effect.
- **The gap under an answer belongs to the turn, not to the answer.** The 8 px between an answer and the row after it is the bottom padding of the turn's last row (`gapBelow` in `timelineRows.ts`), on every turn except one a hidden prompt continues, from the moment the turn is sent. It used to be the bottom padding of the answer's last step, and the last step changes while a turn runs: Claude opens a step's text block empty and the first paragraph is held until it ends (`lib/streamTextCommit.ts`), so a new step row added 8 px with nothing on screen and the follow lifted the sent message; dropping it on such a row instead shrank the transcript by 8 px whenever a step after tool calls began, moving the whole chat down. Giving the gap only once a next row exists made the settled turn above a new prompt grow, and the list measured that a frame late: the sent message dropped 8 px for a frame. So the live turn carries it too, at the content's end, and so does a turn that got no answer. Lists without turns (the BTW panel) keep it under the answer.

## Measuring

Scroll measurements from a background or occluded tab lie: such a tab runs about one frame per 500 ms. Measure with a headless CDP probe that logs `scrollTop`, the maximum and the last row's bottom per frame (see `scripts/perf/DOCUMENTATION.md`, "Running An Isolated Copy"); a resize fix holds when `scrollTop` equals the maximum on every logged frame. For streaming cost, `profile:session` compares builds; also sample the distance from the end, because a build that stopped following looks faster.

The mobile keyboard side (`keyboardFollowGlide.ts`) is documented with the composer: `components/chat/composer/DOCUMENTATION.md`, "Mobile".
