# Settings

## Purpose

`packages/ui/src/lib/settings` owns what an OpenChamber setting *is*: its key, its scope, how a value is parsed at the boundary, and where the UI keeps its live copy. The storage and sync mechanics (debounced writes, mirrors, bootstrap adoption) live in `lib/persistence.ts` and consume this module; the Settings pages consume the stores.

## Modules

- `registry.ts` — the settings registry. One `SETTINGS_REGISTRY` table plus two key lists (`LOCAL_DEVICE_KEYS`, `DESKTOP_SHELL_KEYS`) and the derived helpers other modules use: `DesktopSettings` (the document type), `parseSettingsDocument`, `applySettingsToStores`, `AUTO_SAVE_KEYS` / `readAutoSaveSnapshot`, `MIRRORED_KEYS`, `buildSettingsRegistrySnapshot`.
- `parsers.ts` — value-level boundary parsers (zod schemas wrapped as `SettingsParser<T>`). `undefined` means "reject", never "default".
- `registry-snapshot.ts` — renders the plain-JSON snapshot for the two consumers that cannot import the UI's TypeScript: the OpenChamber server (`packages/web/server/lib/settings/settings-registry.json`) and the VS Code extension host (`packages/vscode/src/settings-registry.json`). Regenerate with `bun run settings-registry:generate`; `registry.test.ts` fails when a checked-in copy is stale.
- `metadata.ts`, `search.ts` — Settings page metadata and the search index (unchanged by the registry; see `.agents/skills/settings-ui-patterns`). Entries for what the connected server serves are generated, not listed: each source-control provider adds `integrations.source-control.<id>` (titled by its literal label) and `.connect`, each tracker with words of its own adds `integrations.<id>` and, by capability, `.add-workspace` and `.mapping`. `SettingsView` passes both registries' descriptors to `buildSettingsSearchResults`, so a provider the server adds is searchable with no entry here. A title is a key with optional params, or a literal for a product name. `pageTitle.ts` maps each page slug to its translated title; the metadata's English title serves code and search keywords, and every user-facing title comes from that map, so Settings and the command palette name a page alike. Search availability mirrors the control's render guard, since an entry for a control the device hides would take the user to an empty spot; shortcut entries are generated for every in-app action, the system-wide (`desktop` category) ones live on General and are excluded here, and the `providers.classification` entry opens the Classification providers sub-page that `SettingsView` selects.
- `search-voice.ts` holds the Voice page's search entries.
- `vscodeNavigation.ts` defines and parses navigation intent crossing the extension-host bridge. It carries a page, optional item and Settings directory, plus provider-connect and new-snippet entry intent. It carries no saved settings, credentials or conversation content. `apps/vscodeSettingsNavigation.ts` connects chat-side Settings requests to the native tab and applies delivered intent there; settings persistence keeps its existing owner.
- `newSettings.ts` owns the "new" badge and its best-effort browser-storage baseline (`openchamber.settings.newBadgeSeen.v1`). It compares static search anchors with that baseline once per load, then filters pending anchors by current device availability. `getNewSettingPages` returns pending pages and `acknowledgeNewSettingPage` acknowledges available anchors on one page. `isNewSetting` retains the load-time answer for row badges, which the shared Settings rows read for their `settingsItem` through `SettingsNewBadge`. That badge shows only under the anchors `SettingsView` provides as available on this device, so an opener never announces a control the device hides and nothing outside Settings carries one.

## Invariants

- **A key that is not in the registry does not persist.** `parseSettingsDocument` drops unknown keys on the way in; `updateDesktopSettings` sends only registry keys that are not `computed`; the server and the VS Code bridge drop anything the snapshot does not list.
- **Every key has exactly one scope.** `instance` (a fact about the machine the server runs on, never synced), `profile` (the person's preference, shared by every client of the instance), `device` (state of this install/surface). `LOCAL_DEVICE_KEYS` are device fields that only ever lived in `useUIStore`'s persisted slice; `DESKTOP_SHELL_KEYS` are instance facts the Electron main process writes straight into `settings.json` and no client reads.
- **Per-surface profile fields** (`perSurface: true`) are a fixed, owner-decided set: the theme ids and mode, the chat-layout switches that depend on screen size, the typography sizes, and the sessions sidebar view mode (`sidebarViewMode`: every kind defaults to the timeline, VS Code always renders the grouped projects view, and a choice made on one kind must not flip another), the List view's session layout (`sidebarListSessionGrouping`: by project or by time) and its section and row toggles (`sidebarShowChatsSection`, `sidebarShowWorkSection`, `sidebarShowPinnedSection`, `sidebarDetailedZoneRows`), and which of the user's own sidebar sections the surface hides (`sidebarHiddenSections`; the sections themselves, `sidebarSections`, are one arrangement for every surface). A change made on one surface kind is stored for that kind only: every settings request carries the client's kind as the `surface` query parameter, never a header, so the request needs no CORS preflight from the cross-origin desktop and phone shells and works against older instances (`surface.ts`: `vscode`, `desktop`, `mobile` for the phone app and the hosted mobile shell alike, else `web`), the store writes the value under `fields[key].surfaces[<kind>]` and leaves the base untouched, and a read resolves that kind's value first, the base value otherwise, or nothing (the client keeps what it holds). Writes without a surface (migrations, the one-time seed) set the base. The Settings UI is unchanged; the difference is only where the value lands.
- **Missing is not default.** `applySettingsToStores` writes only the fields the snapshot carries; an omitted field leaves the store as it is. Defaults live in the stores' initial state, not in the registry.
- Project request paths use `lib/pathNormalization.ts` at the parser boundary, matching project stores and the SDK adapter. Parsing and serializing a Windows drive root preserves `C:/`; comparison or ID formatting must not turn it into a drive-relative request path.
- Project parsing preserves `labelSource` (`auto` or `manual`) only beside a non-empty label. Unknown sources are dropped without rejecting the project. Save echoes and subsequent reads must retain manual provenance so the store's legacy auto-label migration cannot change a user's rename.
- **Writes carry intent.** Fields with `ui.autoSave` are watched by `lib/appearanceAutoSave.ts`; changes made while `isApplyingServerSettings()` is true (a sync copying server values in) are a new baseline, not a write. The model-preference fields are watched by `lib/modelPrefsAutoSave.ts`, which delegates to the shared settings debounce, and are therefore `autoSave: false` here. Fields whose store setters already write through `updateDesktopSettings` (the config store), write several keys at once (`draftStarters` with its markers), or are owned by a dedicated auto-save are `autoSave: false` too.
- **Sibling-dependent applies are explicit.** A `ui.write` receives the parsed snapshot as `SettingsSiblingView`, which names the only siblings a write may consult (`draftStarters*Added`, `workStatusHiddenSectionsExplicit`, `workStatusSectionOrderExplicit`). Extend the view when a new field needs one.
- **Device fields never cross the wire.** `updateDesktopSettings` drops `device` keys before the debounce, the server and the VS Code bridge drop them again, and the mirror never held them. Their home is the local store (`useUIStore` persisted slice, `mobileKeyboardMode` browser storage, `desktopSplashColors` in the desktop shell's own store via the window-theme IPC). A server document that still carries device keys from before the split is applied exactly once per runtime as a seed (`openchamber.deviceSeeded.v1:<runtimeKey>` in browser storage) and ignored afterwards.
- **Two files on the instance.** `settings.json` keeps instance facts and legacy keys; `preferences.json` beside it holds every `profile` key as `{ value, updatedAt }` (`version: 1`). The server (`packages/web/server/lib/settings/settings-files.js`) and the VS Code bridge (`packages/vscode/src/settings-files.ts`) seed `preferences.json` once from an existing `settings.json`, keep a copy of the profile's base values in `settings.json` on every write (a build from before the split reads only that file, so a rollback keeps the user's preferences; current builds ignore the copy because `preferences.json` wins), and never touch a `preferences.json` they cannot parse; clients see one merged document and never address the files. Server modules that read a profile key off the disk (small model, session goal/assist, walkthrough) use `readMergedSettingsSync`.
- **Markers, not code, carry the special cases.** `adopt: 'bootstrap-only'` (workspace pointers), `derived` (computed by the writer from other fields), `secret` (accepted on write, never returned), `computed` (server-emitted, never persisted), `surfaces` (which surface kinds have the field).
- **Parsers are plain functions over `unknown`.** Each receives the untrusted document and returns a value or `undefined`; `undefined` rejects, never defaults. Malformed entries inside a collection (a project, provider logo, shortcut, model reference, tunnel preset, skill catalog) are dropped individually, so one bad entry does not reject the rest. Hidden-section ids no longer known are dropped because they would hide nothing and accumulate forever.
- **Empty and whitespace stay meaningful.** `parseTrimmedString` keeps `''` because some keys use it as unset; `parseTextUpTo` keeps whitespace because it is content; `parseStringList` keeps duplicates and order because they are the user's, while `parseStringSet` deduplicates. `agentMemoryDreamingModel` and `agentMemoryDreamingVariant` accept `''`, which means the default model or variant.
- **Server-backed controls are absent in VS Code.** Default permission mode, message search, session goal checker, session review offer, fallback model and Jev routing need the OpenChamber server, so their controls and search entries are hidden there. The Chats defaults are hidden there too. VS Code opens a chat only in a window with no folder, and that chat still starts on the Chats defaults from the shared settings file, as it does on the New sessions defaults. The message search index exists only while `messageSearchEnabled` is on, and turning `messageSearchReasoningEnabled` on makes the server re-read agent records. Per-session permission modes accept the booleans from before the modes; the server converts them on its first read.
- **Some instance facts are owned elsewhere.** `serverUpdateChannel` is the npm-installed server's own channel (Settings → About in its browser page); the desktop app uses `desktopUpdateChannel`. `pwaAppName` and `pwaOrientation` are instance facts because the server serves the PWA manifest from them, even though only the installed web app shows them. `browserProvider` names `builtin` or an installed extension id, and the server falls back to `builtin` when that extension cannot serve. `customProviderLogos` is written by the server's provider-logo routes together with the image file; the client only reads it.
- **Isolated spaces are not store-backed.** `isolatedSpacesIdleStop` and `isolatedSpacesSshHost` are read and written through the spaces route (the page's `PUT /machine` for the host), which also updates running spaces; writing them directly bypasses that. The host is `[user@]host[:port]`, or empty for none. The feature switch is read by the server at start, so a change takes effect at the next start. The page and its search entries are never available in VS Code, and before the feature's first release the page appears only with the feature key on.
- **Secret fields are write-only.** `desktopUiPassword`, `managedRemoteTunnelToken` and `managedRemoteTunnelPresetTokens` are accepted on write and never returned. `hasDesktopUiPassword` and the tunnel status endpoint tell the page what is set, and an empty string clears the desktop password.
- **Apply order carries meaning.** `applySettingsToStores` walks the registry in order: `sessionRetentionOnlyArchived` comes before `sessionRetentionAction`, so leaving archived-only mode can restore the incoming archive choice. `workStatusSectionOrderExplicit` is applied on its own too because the order write is skipped when the parsed order equals the local one; a list and its explicit marker are written in one store update so subscribers never see the list without its marker.
- **Some fields stay one value for every surface.** `sidebarSessionBatchSize` is one number for every surface; the phone has no control for it and follows the desktop.
- **Local device keys and shell keys are accounted for, not parsed.** `LOCAL_DEVICE_KEYS` name store keys that never cross the wire and therefore carry no parser; `globalDraftStarters` is the store's name for `draftStarters` and is deliberately absent. `DESKTOP_SHELL_KEYS` are written by the Electron main process straight into `settings.json` and never accepted from a client; `desktopSplashColors` arrives over the window-theme IPC and replaces the flat `splash*` keys older builds wrote.

## Adding a setting

`notifyOnPullRequests` is a profile preference, default on in `useUIStore` and the server defaults. The Notifications page exposes it on clients of an OpenChamber server; VS Code does not run that server follower. The server checks the preference at delivery time, including when no UI is connected.

1. Add one entry to `SETTINGS_REGISTRY` with `scope`, a parser from `parsers.ts`, and a `ui` binding when a store holds the live value. Use an existing setter so its side effects run.
2. Run `bun run settings-registry:generate` and commit both JSON snapshots.
3. If the server must validate the value beyond the registry gate, add its branch to `sanitizeSettingsUpdate` in `packages/web/server/lib/settings/settings-helpers.ts`; the drift test in `settings-helpers.test.js` needs a valid sample value for the new key.
4. Add the Settings control and search entry per `.agents/skills/settings-ui-patterns`.
5. The "new" badges follow from the anchor. The shared rows (`SettingsSection`, `SettingsControlGroup`, `SettingsStackedField`, `SettingsFieldRow`, `SettingsCheckboxRow`) render `SettingsNewBadge` for their own `settingsItem`; a control built without them puts `<SettingsNewBadge items={['<anchorId>']} />` next to its label, or the page badge points at a row that says nothing. A new control the page hides until something is opened carries its badge on that opener: the Chat and project tabs badge the anchors their tab maps hold, the notification switch badges the event rows, a tool's switch badges the options it reveals (`reveals`). Page badges count only available controls. Opening a visible page acknowledges its available anchors; hidden anchors remain pending. Row badges stay for the rest of the load. On mobile the title badge appears only on the navigation stage and counts visible pages. A fresh install seeds every build anchor and starts without badges.

`DesktopSettings`, `SettingsPayload`, the client sanitizer, the mirror, the apply step and the auto-save all follow from step 1; no second list has to stay in step for persistence.

`sttPrompt` is the profile preference for the transcription prompt. Its live copy is `useTranscriptionPromptStore`, a store of its own so `useConfigStore` does not grow; the Settings field writes it through `updateDesktopSettings`. It is kept as typed: a save echo is applied back to the field, and a trimmed one would remove the line break being typed. Dictation trims it before sending, and an older document without the key leaves it empty. The store remembers which host the prompt belongs to and reads empty on any other host: sync skips keys a snapshot omits, so without that a host that never saved a prompt would send the previous host's vocabulary.

`sessionCostAlertsEnabled`, `sessionCostWarnThreshold` and `sessionCostCriticalThreshold` are profile preferences: off by default with $5 and $20, amounts in US dollars as OpenCode reports them. Yellow stays below red everywhere a pair is read: the Settings field shows an error and keeps saving nothing until the pair is ordered, the parser takes an amount only while the document's pair (defaults filling a missing side) is ordered, and the server drops an out-of-order pair in an update and keeps the stored pair when a write of one amount would put it out of order. Amounts that are not positive and finite are dropped too, so a bad value keeps the previous one. Their live copy is `useSessionCostSettingsStore`, which, like the transcription prompt, remembers the host it was read from and reads the defaults on any other host, so a host that never saved them stays off instead of alerting with the previous host's amounts; the Settings section writes them through `updateDesktopSettings`, so they are never auto-saved to whatever host is current.

`selectionApprovalText` is a shared profile preference for the selection approval shortcut. An empty string means no custom text; older documents can omit the field. The setting stores only the override and does not define fallback message text or dispatch behavior.

`activityRenderMode` defaults to Grouped. `keepEarlierReplies` is off by default and on for a document that still says `text`, the removed Show notes mode: its users chose to see every text. Choosing a mode writes both keys, so that choice survives the old value's replacement; `updateDesktopSettings` never drops these keys as unchanged, because the server may only derive the value it returned.

## Decisions

### Why the local store drops Expanded on upgrade and not only a missing value

The persisted slice holds the old default for people who never chose it. Only a choice is written to the server, so a chosen Expanded comes back with the settings document.

### Why the Settings view passes its voice availability snapshot

Search and new-setting badges receive the voice fields the view subscribes to, so memoized results refresh when those fields change. Non-React callers can omit the snapshot and read the current config store; separate invalidation-only dependencies hid this relationship from hook checks.

### Why badges use item-level availability

Badges and acknowledgment use the search registry's page and item availability predicates with the current device context. Hidden controls remain pending until opened on a device that can show them. Filtering only whole pages would announce and acknowledge controls the user cannot see. The initial baseline still seeds every build anchor so a fresh install starts without announcements.

### Why row badges follow the anchor and not an opt-in prop

Page badges count every new anchor, so a row badge each control had to opt into left pages that said "new" with nothing on them saying what. Reading the badge from the row's `settingsItem` keeps the two counts the same set.

### Why the first baseline comes from the build and not from a list of announcements

A client with no baseline seeds every anchor the build has, so a fresh install sees nothing new. The alternative, listing the anchors this release announces, cannot tell a fresh install from an upgrade that predates the feature, and it lights up a new install that has nothing to compare against. The cost is that controls shipped in the same release as the badge are never announced. The seed runs when the client first renders Settings, which keeps the search table out of the startup path; a client whose first render comes after an update therefore seeds past that update's anchors too.

### Why the new-badge state is resolved once per load

Deciding what is new walks the whole search table, and the answer changes only when the user acknowledges a page; reading it again on every row render would repeat that walk for nothing. The load-time `newAnchors` keeps the page just opened showing which of its controls are new, while the next load reads the moved baseline and shows none of them.

### Why settings UI bindings use method syntax

Method syntax keeps `SettingsFieldSpec<T>` assignable to `SettingsFieldSpec<unknown>`, which is what the generic loops iterate. Property-function syntax does not make that assignment.

### Why the config store is reached through the window global

`useConfigStore` imports the shared write path, so a direct import here would be a load-order cycle. The store registers itself on `window.__zustand_config_store__`, which is absent outside a browser.

### Why built-in draft starters are re-added only when a marker says they were never offered

Removing a built-in starter must stay a durable choice, so the list is patched with the built-ins only when the corresponding marker says they were never offered. The markers travel with the user's edit, which is why the write consults them from the parsed snapshot.

### Why `getSettingsNavIcon` lives in `metadata.ts`

Light consumers such as the command palette can render settings entries without statically importing the whole settings surface into the eager startup graph.

### Why parsers are plain functions over `unknown` and not schemas

The registry can hold hand-written and schema-derived parsers alike, and its shape can be evaluated for the generated JSON snapshot without a browser.

### Why legacy values collapse onto their closest current value

The removed Sorted chat mode showed only the answers with the work folded away, and Collapsed is its closest match, so `chatRenderMode: 'sorted'` wins over a stored mode until the user picks one (which retires the key). The old wide layout is today's Full. `queueModeEnabled` is the old follow-up switch, and `'immediate'` is steer. The legacy `server` speech-to-text provider is the OpenAI-compatible endpoint, and `browser`/`wasm` are the local one. The legacy window-controls `auto` never read OS chrome configuration and behaves as `right`.
