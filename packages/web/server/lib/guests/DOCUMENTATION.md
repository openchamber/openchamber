# Guest panels

## Purpose

OpenChamber-owned install and static serve for iframe guests. This is not the OpenCode plugin manager (`plugin-routes.js` / Settings → Plugins).

## Routes

Host guests (`auth: 'host'`, `host.provider` naming a tracker; the SDK's `IntegrationHostProvider` is `'linear'` only) borrow the host's own sign-in through the tracker registry (`host-session.js`): the tracker's descriptor must have `capabilities.hostAccess`, and its implementation's `hostAccess` answers the account, the token, sign-in start and disconnect. A tracker that is not registered, does not offer host access or fails to load gives the guest nothing. "Host Linear" below is that path for Linear.


- `POST /api/guests/:id/storage` accepts only instance-scoped SDK storage requests and returns `GuestStorageResult`. It requires an installed, enabled, fully approved guest with either a panel or background entry, but no additional capability. Device-scoped requests are refused here, never treated as instance storage. The UI host supplies the frame's own identity. Guest-scoped asset tokens cannot call this route. Data lives beside `extensions.json` in `guest-storage/<id>.json`. Each key is 1 to 128 characters, each JSON value at most 64 KiB UTF-8, the whole namespace at most 2 MiB and 2,000 keys. `storage.js` owns serialized authorization/read/write/removal; writes are atomic and failures preserve prior bytes. `uninstallGuest` removes storage for every install source. Missing keys return `found: false`, including after removal; stored JSON null returns `found: true`.
- `GET /api/guests` also exposes `statusEntry` and optional `statusTitle` / `statusHeight` for `contributes.statusSection`, the extension's Work Status section. Its HTML and built scripts pass the same install checks, and it may be the package's only frame: the storage route and the asset route's `hasRuntime` accept `entry`, `backgroundEntry`, or `statusEntry`. A section with `source` adds `statusSource: { path, interval }` (interval resolved) and may come without `statusEntry`; it is not a frame, so it adds nothing to `hasGuestFrame`. The UI reads it through the ordinary `service/request` route, which needs no frame.
- `GET /api/guests` also exposes `fileEditors` (`[{ id, title, match, entry }]`, `contributes.fileEditors`) as declared. Each editor's HTML and built scripts pass the same install checks (`invalid-manifest` / `missing-build`), and editors may be the package's only frames. `hasGuestFrame` in `catalog.js` is the one definition of "has a page the host loads" (panel, background, status section, or file editor) used by the storage route and the asset route's `hasRuntime`. No server route reads or writes an editor's file: the Files view owns it and talks to the frame over `postMessage`.
- `GET /api/guests` also exposes `pageEntry` and optional `pageTitle` for `contributes.page`. Full-screen page HTML and its built scripts pass the same install checks as attach HTML. No new serving/auth path is required.

- `GET /api/guests` returns installed guests. `attach` is `"panel"` or `"dialog"` when declared, and `attachEntry` is the dialog's separate HTML. `version` is the package semver. `integration` is the public slice: name, description, `auth`, and settings; OAuth URLs and tokens stay on the server. `service` includes `runtime`, optional `permissions`, optional `socketBindings`, and `granted`. `capabilities` carries `{ requested, granted }`, derived through the SDK's `requestedGuestCapabilities`. `actions`, `commands`, `tools`, and `filesystem` retain their parsed declarations; UI owns menu placement, command collisions, and tool precedence. `entry` is the optional visible panel and `backgroundEntry` is independent on-demand execution HTML. Background-only extensions get no rail surface; tools-only extensions with neither entry mount no frame. A guest without every requested grant is inactive until approval. `enabled: false` pauses it. A failed listing is 500, never an empty list.
- `GET /api/guests/:id/oauth/status` — `{ connected, account, hasClient, settings, redirectUri }`. No secrets. Host Linear merges first-party Linear status. `redirectUri` is empty unless `auth` is `oauth`.
- `PUT /api/guests/:id/oauth/client` — client id and optional secret from the Integrations form. OAuth guests only.
- `PUT /api/guests/:id/token` — pasted API token. Token guests only. The host probes the declared account path. The token never goes to the iframe.
- `PUT /api/guests/:id/settings` — declared keys only. The Integrations card calls it when a declared field loses focus with a changed value; there is no Save button. Connect saves the token (and username for `basic`) or the OAuth client id and then the declared fields.
- `POST /api/guests/:id/oauth/start` — PKCE S256 for OAuth guests. Host Linear starts the first-party Linear authorize URL. Token guests get `NO_INTEGRATION`.
- `GET /api/guests/:id/oauth/callback` — public HTML page. The provider redirects here with no UI bearer. State and verifier stay on the server. A callback without a matching `state` is refused; nothing is inferred from a pending exchange. Host Linear uses the first-party Linear callback, not this URL.
- `DELETE /api/guests/:id/oauth` — drops tokens for that guest. Client and settings stay. Host Linear disconnects the first-party Linear workspace.
- `POST /api/guests/:id/request` — authenticated UI session. Attaches Authorization. Path must stay on that guest's `apiOrigin`. Token guests send the pasted token as is, `Bearer <token>` when the manifest sets `token.scheme: "bearer"`, or `Basic <pair>` for `"basic"`, where `PUT /api/guests/:id/token` took `{ token, username }` and stored `base64(username:token)` as the access token (`USERNAME_MISSING` without a username). Host Linear sends the Linear bearer to `https://api.linear.app` only. Linear issue file URLs stay on `GET /api/linear/issues/get`. The guest proxy does not add Linear headers. A paused extension (`enabled: false`) is 400 `DISABLED`; tokens stay. A guest without the `network` capability granted is 400 `NOT_GRANTED`. The answer is read through `response-body.js` up to `GUEST_REQUEST_RESPONSE_MAX` bytes; a larger one is 502 `RESPONSE_TOO_LARGE`, never a cut-off body the guest would fail to parse.
- `POST /api/guests/:id/service/request` — authenticated UI session. Proxies to that guest's host-spawned service on `127.0.0.1`. Spawns on first use after the grant; every service needs one. Missing grant, missing service, or bad path is 400 with `NO_SERVICE` / `BAD_PATH`. Paused extension is 400 `DISABLED` (service stopped). Ready failure is 502 `SERVICE_FAILED`. An answer over `responseMax` (default `GUEST_REQUEST_RESPONSE_MAX`) is 502 `RESPONSE_TOO_LARGE`.
- `POST /api/guests/:id/files` — authenticated UI session. `{ op: 'read' | 'write' | 'list' | 'stat', path, content? }` (`content` required for `write`, at most `GUEST_FILE_CONTENT_MAX` characters; `path` at most `GUEST_FILE_PATH_MAX`). The open project comes from `resolveOptionalProjectDirectory(req)` (`x-opencode-directory` header or `directory` query; a value outside Latin-1 travels percent-encoded with `x-opencode-directory-encoding: uri` and the resolver decodes it, since a header value cannot hold it as-is). `files.js` resolves the path: relative → joined to the project's realpath, and the deepest existing ancestor is realpath'd so a symlink out of the project is `BAD_PATH`; a relative path with no project is `NO_DIRECTORY`. `/…` or `~/…` → home expanded, normalized, canonicalized the same way, then matched against the package's `contributes.filesystem` globs whose literal prefixes were canonicalized too (`/tmp` → `/private/tmp` on macOS); no match is `BAD_PATH`. Any `..` segment, NUL, or backslash is `BAD_PATH`. Then the grant: project scope needs `files`, outside needs `filesystem`, else `NOT_GRANTED`. Then the operation: read is UTF-8 and refuses a file over the cap with `FILE_TOO_LARGE`; write makes parent directories and lands through a temp file plus rename (a reader never sees a truncated file); list returns `{ name, kind }` sorted by name and capped at `GUEST_FILE_LIST_MAX`, with symlinks as `other`; stat answers `kind: 'missing'` for nothing there. Answers are `{ ok: true, result }`, or `{ error: code, message }` with 400 (404 for `NOT_FOUND`). Paused extension is 400 `DISABLED`. `ENOENT` is `NOT_FOUND`, `EACCES` / `EPERM` is `DENIED`, `EISDIR` / `ENOTDIR` is `BAD_PATH`. Neither the path nor the content is ever logged.
- `POST /api/guests/:id/generate` — authenticated UI session. `{ prompt, system?, maxOutputTokens? }` (prompt at most `GUEST_GENERATE_PROMPT_MAX`, system `GUEST_GENERATE_SYSTEM_MAX`, tokens `GUEST_GENERATE_OUTPUT_TOKENS_MAX`). Paused extension is 400 `DISABLED`; missing `model` grant is 400 `NOT_GRANTED`. The call goes to `generateSmallModelText` in `lib/small-model`, which resolves and authenticates the Small Model the same way session titles and notes do (settings override → OpenCode config → signed-in provider); the optional `x-opencode-directory` header only picks which OpenCode config is read. No model (404) or Claude Code as the only candidate (422) is 400 `NO_MODEL`; a provider failure is 502 `MODEL_FAILED`. Answer is `{ ok: true, result: { text } }` capped at `GUEST_GENERATE_TEXT_MAX`. Prompt and answer are never logged.
- `GET /api/guests/:id/service/status` — `{ status }` for that guest's service runtime (`stopped` / `starting` / `ready` / `failed`).
- `PUT /api/guests/:id/capabilities` — `{ granted: GuestCapability[] }`. The list must equal the package's requested list, or be empty to withdraw approval (which also stops a running service). Anything else is 400 `invalid-request`. `service.granted` mirrors whether `service` is in the granted list. Approval also records the grant's scope (`grant-scope.js` `guestGrantScope`: the sorted `filesystem` patterns, the integration's `apiOrigin` and OAuth `authorizeUrl` / `tokenUrl`, the service's exec names and socket ids) as `capabilityScopes[id]`. When the recorded origin or OAuth endpoints differ from the new ones (`sameCredentialTarget`) the guest's stored tokens are dropped: a token pasted for one API, or a refresh token and client secret minted for one token endpoint, must not follow the integration to another.
- `PUT /api/guests/:id/service/sockets` — `{ id, path }` for a declared socket binding. Empty or null `path` clears the override. Stops a running service for that guest. Catalog `service.socketBindings` shows `resolved` and `override` for this host.
- `PUT /api/guests/:id/enabled` — `{ enabled }`. False is a full pause: catalog `enabled: false`, rail/attach/Integrations hide the guest, open panels close, cloud `request` and `service/request` return `DISABLED`, and a running service stops. Tokens and grants stay until Remove.
- `POST /api/guests` accepts exactly one of `{ path }` or `{ url }`, optional `replace`, and optional `gitIdentityId` for Git installs. `path` is an absolute folder or local ZIP. `url` is HTTPS Git/ZIP, `ssh://` Git, or scp-style SSH. Folder installs persist their realpath; Git and ZIP installs copy into `{openchamberDataDir}/extensions/{id}`. Success is 201, or 200 after replacement. Invalid input is `invalid-path`/`invalid-url`; clone and extraction failures are `clone-failed`/`extract-failed`, except a clone the host refused for lack of access (no stored HTTPS login, rejected login, or SSH key not accepted), which is `clone-auth-failed`; installs and updates both answer it. A missing selected identity fails cloning rather than falling back to global auth. Missing built scripts are `missing-build`, invalid package/version is `invalid-manifest`, and a newer required host is `host-too-old`. Duplicate installs are 409 `id-taken`/`already-installed`. Other install failures are 400. Clone uses the host's resolved Git binary; orphaned copy folders from interrupted installs can be replaced on retry. Each OpenChamber data directory owns its own catalog.
- `POST /api/guests/upload` — the archive itself as the body, `Content-Type: application/octet-stream`, for a browser or a remote instance that cannot name a path on the host. Query `replace=true` mirrors the JSON route's `replace`; `name` (the original filename) is accepted and unused, never logged. A wrong content type is 415 `unsupported-media-type`. A `Content-Length` over the cap is refused with 413 `too-large` before the body is read, and a body that grows past the cap without a declared length stops with the same answer. The cap is `OPENCHAMBER_GUEST_UPLOAD_MAX_BYTES`, default 50 MB (`upload.js` `guestUploadMaxBytes`). The bytes go to `installGuestFromZipBuffer`, the same function a local `.zip` path and an https `.zip` URL end in, so results and errors are those of `POST /api/guests` with a zip: 201 / 200 after replace with `{ guest }` (`source: "zip"`), 409 `already-installed` / `id-taken` with `id`, 400 `invalid-manifest`, `missing-build`, `host-too-old`, `extract-failed`. Registered before the `:id` routes because `upload` is a valid panel id shape. Archive contents are never logged.
- `POST /api/guests/updates/check` — `{ force?: boolean }` → `{ updates: Record<guestId, { version }> }` for every git install whose origin now carries a newer `package.json` `version`. The check runs `git fetch --depth 1 origin <ref|HEAD>` inside the installed clone and reads `FETCH_HEAD:package.json` through the SDK manifest parser; the only signal is semver (`updates.js` `compareSemver`, prerelease below release), no commit hashes. Results sit in a memory cache per store file and guest id for `UPDATE_CHECK_TTL_MS` (one hour); `force` asks the network again. That cache is separate from the catalog cache, so a store write does not drop it. One guest's failed fetch never hides another's update, and is not cached: the next check fetches again, and an answer already cached stays. Folder and zip installs are never checked.
- `POST /api/guests/:id/update` — replace the installed git copy with a fresh clone of its stored origin. Answers `{ guest }` (the refreshed catalog row) or 400 `{ error }` with `not-git` (folder, zip, or no stored origin), `clone-failed`, `invalid-manifest` (also when the clone declares a different panel id), `missing-build`, `host-too-old` (body may include `required`), or `swap-failed`. Unknown id is 404. Grants, tokens, settings, and the paused flag are keyed by guest id and stay as they were; a version that asks for more capabilities shows up as needs-approval in the catalog and goes through the usual review dialog.
- `DELETE /api/guests/:id` — drops the store row, any service grant, and socket overrides; stops a running service. Path-install does not delete the user's folder. Zip and git copies under `{openchamberDataDir}/extensions/` are deleted. Unknown id is 404.
- `POST /api/guests/:id/frame-grant` (normal API auth) mints `{ grant, expiresAt }` for an installed extension with a page (`hasGuestFrame`), else 404. `frame-grants.js` keeps grants in memory: 32 random URL-safe characters, one extension each, alive while the frame keeps loading files and gone after 12 idle hours or a server restart.
- `GET /api/guest-files/:grant/{*filePath}` serves that extension's package files by the grant alone: `core-routes.js` lets these GETs past API auth, an unknown or lapsed grant is 403, and the file rules are those of the route below. No query token is added to the HTML, because relative URLs already resolve under the grant, and `connect-src` is the grant's own path.
- Role listeners: `registerGuestRoutes` takes `onGuestDeactivated({ guestId, guestName, removed? })`, called after a pause, a withdrawn approval and an uninstall (`removed: true`), and `onGuestActivated({ guestId })`, called after an approval with a non-empty grant, an enable, an install or replace (JSON or upload) and an update. Both run after the change is stored; a listener that fails is logged and never turns the change into an error answer. The runtime combines its deactivation listeners with `settleGuestDeactivationListeners`, so one that fails (the browser hand-back) never skips another (the Git host withdrawal, the session event subscription). Listeners read the catalog themselves, so an event carries only the id (`../source-control/extension-providers.js` and `session-events.js` use both; `../browser-control/provider.js` the first).
- A catalog row carries `sourceControl: { label, defaultInstances, custom }` (the SDK's `toPublicSourceControl`) at the top level when the package declares `contributes.sourceControl`, for the approval dialog. The guest record keeps the whole parsed contribution as `sourceControl`.
- A catalog row carries `sessionEvents: { events, content }` (the SDK's `toPublicSessionEvents`) when the package declares `contributes.sessionEvents`, for the approval dialog's event list and the card. The guest record keeps the parsed contribution as `sessionEvents`; `requestedGuestCapabilities` adds `transcript` to `capabilities.requested` when `content` is true.
- A catalog row carries `notifications: { label, instances, token }` (the SDK's `toPublicNotifications`) when the package declares `contributes.notifications`, for the approval dialog and the Integrations card. The guest record keeps the parsed contribution as `notifications`.
- `GET /api/guests/:id/{*filePath}` serves package-local files. Unknown IDs, escapes, missing files, and unknown types return 404. HTML and JS require `entry`, `backgroundEntry`, `statusEntry`, or a file editor, expressed by `resolveGuestServedFile`'s `hasRuntime` option. Tools-only extensions still serve their SVG icons but no executable content. Guest HTML propagates the scoped `oc_url_token` onto relative script/link/image URLs. The token is minted for `guest:<id>` and works only under that guest's asset route, never `/api/fs/raw` or event streams. Every response carries `Content-Security-Policy: sandbox allow-scripts`, including direct document navigation. The host serves built files from disk and never compiles guest sources.

## Install

`contributes.background.entry` is optional package-local `.html`, separate from `panel.entry`. Install validates its HTML and every referenced built script using the same path confinement as visible panels. `backgroundEntry` is exposed on the catalog independently of `entry`; adding it does not create a rail icon or a visible page. Capabilities, services, integrations, and storage work with either execution entry. The SDK refuses visible contributions without `panel.entry` and all runtime contributions when neither entry exists. See `packages/sdk/DOCUMENTATION.md` for on-demand invocation ownership.

`html-styles.js` appends the SDK's shared scrollbar stylesheet and its small inline activity script (`GUEST_SCROLLBAR_SCRIPT`: shows a scrollbar while its element scrolls) to served HTML, including requests without an asset token. An authored CSP that blocks inline scripts leaves hover-only scrollbars. This applies to existing panel, page, and attach bundles in direct and relay mode; the relay loader retains the inline style in `srcDoc`. Appending preserves the doctype and avoids rewriting tag-like text inside scripts or comments. Authored CSP stays intact and can block inline styling. Package files on disk and non-HTML responses are unchanged. Scrollbar colors follow the SDK theme variables inside the frame. The one insertion before authored content is `<meta name="color-scheme" content="light dark">`, placed right after a leading doctype (or first when there is none): the frame inherits the host's dark scheme, and without that declaration its canvas paints white until the guest's own theme loads, so every panel flashed white on mount.

Built-ins ship with the app; user extensions are installed separately. Add a folder, local ZIP, HTTPS Git/ZIP URL, or SSH Git address from Settings → Extensions. The ZIP picker and drop zone upload the archive on web and remote desktop instances. A guest with a page must ship built classic-IIFE JavaScript, for example from `bunx openchamber-guest-bundle panel/main.ts panel/main.js`; the sandbox does not support ESM imports. `package.json` needs a semver version. A missing panel SVG or invalid manifest fails installation; page-less tools-only packages skip HTML/script checks. Optional `engines.openchamber` is checked against this host. Provider accounts are connected separately in Settings → Integrations.

Folder installs store their realpath with `source: "path"`. ZIP and Git copies live in `{openchamberDataDir}/extensions/{id}`. Git URLs may end in `#branch-or-tag`; clones use `--branch <ref> --depth 1`. `gitOrigins` stores `{ url, ref?, gitIdentityId? }` per install path and is removed on uninstall. Legacy origins without an identity retain global authentication. Malformed origins are dropped individually. The public catalog exposes the origin URL/ref, never the key path. Named profiles are re-resolved on each clone or update fetch so key rotation applies; missing profiles fail closed. Global auth preserves the server's SSH agent and Git/SSH configuration. ZIP limits remain 20MB for path/URL installs, 500 files and 40MB expanded, store/deflate only, no encryption, zip64 or parent-path escapes. Uninstall deletes copies and leaves folder-install sources intact.

OAuth and pasted tokens live in `{openchamberDataDir}/guest-auth.json`, each entry with the `target` it was minted for (`apiOrigin`, and for OAuth `authorizeUrl` and `tokenUrl`). `takeUsableGuestAuth` runs before every use (proxy, refresh, the status card): tokens whose target differs from what the package declares now, or that carry no target, are dropped on the spot, whatever the grants say. A pending authorization carries the same target; the callback refuses the exchange (`TARGET_CHANGED`) when the package changed its endpoints in between, and the exchange itself goes to the pending target's `tokenUrl`, never to the current manifest's. The client id and secret carry their own `clientTarget`, written by `PUT /api/guests/:id/oauth/client` (`saveGuestOAuthClient`: an empty secret field keeps the stored secret only for the same client id and the same endpoints, decided under the store lock; a new id or moved endpoints drop it); `usableClientCredentials` treats a client entered for other endpoints as absent (`CLIENT_MISSING` on Connect, `hasClient: false` on the card), so a moved package gets no old secret and the user enters new credentials. Every token write that follows a network round trip (the code exchange, a refresh) goes through `patchGuestAuth` with an `expect` predicate checked under the store lock: the entry must still hold the tokens and target the round trip started from, else the answer is dropped and the entry left as it is. The proxy's cleanup after a 401 is scoped the same way: `dropGuestTokens` with an `expect` on the access token the request was refused with, so a refresh that came back empty because the user reconnected meanwhile never erases the new connection. Host Linear tokens stay in `linear-auth.json`. Writes are atomic and `0o600`. The file is per OpenChamber instance, same as `extensions.json`. Web and desktop share it. VS Code and mobile set the guest catalog to `unsupported`. That is not an empty ready list. Those cards stay hidden.

A missing folder is omitted from the list. Other guests stay. The renderer reads catalog rows one by one (`packages/ui/src/lib/guests/parse.ts`): a row it cannot read, such as one from a newer server with a value this build does not know, shows in Settings → Extensions with its name and Remove, and the other rows still load. An install answered with such a row is reported as added, and the list reloads to show it. A corrupt `extensions.json` is 500, not an empty catalog. A missing or blank `guest-auth.json` is an empty store. Corrupt JSON there is 500, not a disconnected card. This is not Settings → Plugins.

### Why extension frames load by a grant in the path

A sandboxed frame has an opaque origin, so its own requests (scripts, styles, `fetch`) are cross-site and carry no `SameSite=Lax` cookie. Behind a sign-in proxy (Authentik, oauth2-proxy) that made the proxy redirect every script to its login page; the CSP refused the redirect and the panel stayed empty (#5326). Two fixes were rejected. Adding the proxy's origin to `script-src` cannot work, since the redirect target is a login page and not a script, and it would let code from elsewhere into an approved extension. Telling operators to exempt `/api/guests/` from the proxy opens installs, tokens and file operations to anyone when OpenChamber has no password of its own. `/api/guest-files/<grant>/` holds nothing but one extension's package files and takes only its grant, so a proxy can skip exactly that prefix (`packages/docs/content/docs/reverse-proxy.mdx`). The grant sits in the path, as the HTML preview's does, so relative URLs keep it and nothing in the page's URL is a session credential. The query-token route stays for clients and servers that predate grants, and for relay frames, which read files with the runtime's own credential.

## Invariants

- Built-in packages come from the app-owned registry bound by `registerBuiltInGuests` at server startup. Source/build/packaging rules are in `packages/extensions/DOCUMENTATION.md`. They receive only their declared grants automatically; ordinary runtime and enabled checks still apply. `openchamber-builtin-` IDs are reserved from user installs, including replacement. DELETE, Git update and grant-edit routes refuse built-ins. Disable preserves account/storage data and stops their services.
- Every valid installed or built-in guest has a random opaque `storageId` in the extensions store. Fully approved catalog rows expose it for the renderer's device-local storage namespace, alongside the renderer's own runtime partition. Replace and Git update preserve it, while replacement still clears the server's instance-scoped storage. A successful DELETE removes it, so a later install receives a new identity. Catalog omissions do not remove it: unavailable path installs can return later. Offline browser profiles can retain inaccessible old device bytes until site-data removal; the renderer's 16 MiB serialized-preference cap bounds that retention, excluding browser metadata overhead.

- Enterprise mode (`enterprise.js`, policy in `../enterprise-mode.js`): a package that asks for `network`, `origins`, `service` or `transcript` (session content posted to that service; it exists only with `service` and is gated with it) installs, updates and keeps those grants only when it comes from a Git repository in `allowedExtensions` (an entry ending in `/` allows everything under it; the match is on `host/path`, so `.git`, a trailing slash, a `#ref` and scp-style SSH spellings compare equal), or from a local folder when `allowLocalExtensions` is set. ZIP installs stay refused. Install and update refuse it with `enterprise-mode` (403 on install); `listInstalledGuests` strips the refused grants after its cache, so a policy change counts at once, and marks the row `enterpriseBlocked`; `PUT /capabilities` refuses to grant them. The list names repositories because a package declares its own id. Built-ins follow the same rule.
- Grants are narrowed on read, never trusted as stored. `listInstalledGuestsUncached` passes each guest's stored list through `effectiveGrants(granted, storedScope, currentScope)`: `filesystem`, `network`, `service` and `transcript` only count while the scope recorded at approval equals what the package declares now, and never count without a recorded scope. A newer version that widens its patterns, moves its API origin, or asks for more exec names or sockets shows up as needs-approval and is refused by every proxy meanwhile. Routes and `proxyGuestServiceRequest` take the grant list from the catalog row (`guest.capabilityGrants`), not from the store.
- Store changes are read-modify-write under one lock per file (`updateExtensionStore`): Allow, Pause, a socket override, an install, and an uninstall landing at the same time all keep each other's result. `guest-auth.json` has the same lock (`withAuthStoreLock`) and every temp file name is unique.
- ZIP downloads validate and pin each HTTPS hop, at most five. Git clones and update fetches share `prepareGuestGitNetwork`. HTTPS retains `http.followRedirects=false` and `http.curloptResolve` pinning. SSH validates the username/host/path, rejects password-bearing URLs and private DNS answers, pins `Hostname` to a resolved public address, and retains the original host for host-key checks through `HostKeyAlias`. Default SSH options use batch mode and `StrictHostKeyChecking=accept-new`, with ProxyCommand/ProxyJump disabled. Identity key paths are shell-quoted; keys and SSH agent sockets stay on the server. Public Git hosts are supported, not local SSH aliases or private-network targets. Existing user-configured Git/SSH commands remain trusted server configuration.
- The catalog cache is version-guarded: `invalidateGuestCatalog` bumps a per-path version, the store notifies before and after each write, and a listing only caches its result when the version did not move while it read. A read that straddled a withdrawal therefore never serves the old grants for the TTL.
- Stopping a service also cancels a request in flight: `stopGuestService` (Pause, Remove, withdrawn approval, socket change, host quit) bumps a per-guest epoch. `proxyGuestServiceRequest` reads the epoch before its first store read, hands it to the start, and checks it again after the service is up; `startGuestService` checks it after every await, right before `spawn`, and while polling readiness. Pause anywhere between the request's enabled check and the proxied call ends with no process and `NO_SERVICE`. Internal cleanup of a dead or failed runtime before a restart is `discardRuntime`, which does not bump the epoch: a crash is not a Pause, so the request that triggers the restart goes through.

- Paths stay inside the package root (`realpath`). `..`, absolute paths, and URLs do not serve.
- Only an allowlisted content type is served.
- Host and guest speak `@openchamber/sdk`. Do not copy those types into `packages/ui`.
- `contributes.actions`, `contributes.commands`, and `contributes.tools` are validated by the SDK parse at install (`invalid-actions` / `invalid-commands` / `invalid-tools` surface as `invalid-manifest`) and copied to the catalog row unchanged. Tool presentations are applied in the UI only (`packages/ui/src/lib/guests/tool-presentation.ts`); no server route reads them. No server route runs an action or a command: the message or session item is built in the UI from the same records Export as Markdown uses, and a slash command is answered by the guest frame over `postMessage`. The rail badge is UI memory only.
- `contributes.attach` is copied as `"panel"` or `"dialog"`. The composer + menu and New Worktree read that field. Omitted guests stay off those menus. The object form's `entry` (dialog only) is checked at install like `panel.entry`: missing HTML is `invalid-manifest`, an unbuilt script it loads is `missing-build`; the catalog exposes it as `attachEntry` and the attach window loads that page instead of `panel.entry`. The optional attach `data` payload lives only in the UI's chip, queued context part, and session metadata snapshot; no server route parses it.
- `request` never leaves the declared `apiOrigin`. A 401 refreshes once. If that fails, tokens for that guest are dropped. Host Linear does not drop Linear auth on a failed GraphQL query. A paused guest never proxies `request` or `serviceRequest`.
- A service with `provides: ["browser"]` is also driven by the host (`../browser-control/provider.js`), not only by a panel: `proxyGuestServiceRequest` takes `timeoutMs`, `responseMax`, `idleStopMs`, and `signal` for that. A service that never became ready is `SERVICE_FAILED` (nothing was sent); a request that was sent and got no usable answer is `REQUEST_FAILED` (the service may have acted on it), and callers word their errors accordingly. `idleStopMs` arms a per-guest timer re-armed at the end of every request; when it fires with no request in flight the process is discarded (not a Pause: no epoch bump) and the next request respawns it. A user-facing stop clears the timer. Panel requests pass none of these and keep the SDK limits. The guest routes call `onGuestDeactivated({ guestId, guestName })` after a pause, a removal, or a withdrawn approval so a host role the extension held is handed back and the user told.
- `surface.js` hosts shared surfaces (`contributes.service.surface`). `/api/guests/:id/surface/ws` (URL-token WebSocket, allowlisted in `ui-auth.js` and `relay/tunnel-host.js`; upgrade refused with 404 unless `isSurfaceGuest`: enabled, fully approved, declares the surface) attaches a viewer to the extension's one session. The session holds the service (`holdGuestService`) and runs one pump: `GET /surface/frame?after=<seq>&wait=25000` through `openGuestServiceRequest`, newest frame kept, delivered per viewer only after that viewer acknowledged the previous one (`frame` text message + one binary message). Control is the session's: `none`, `agent` (set by `noteAgentActivity`, expires after `SURFACE_AGENT_HOLD_MS`), or a viewer id; the first deliberate input (anything but a button-less pointer move) from a viewer while nobody or the agent holds it takes it, `release` or the holder's disconnect gives it back, a second viewer's input is refused with a `control` message. Every change is broadcast (`mine` per connection) and posted to `POST /surface/control`. Input, control notices, resizes, and clipboard reads run through one promise chain per session, in socket order; work queued for an ended session is dropped, and an ended session's close handlers never call the service, so closing a panel after a pause, removal, or withdrawn approval cannot restart the process under the session's old authorization. When the last viewer leaves normally the session stays registered until its queue (including the final `none`) has drained, so a deactivation in that window still finds and cancels it; a viewer that reattaches meanwhile restarts the pump. Every hand-off (release, holder disconnect) bumps `session.handoffs`; an input batch remembers the count it arrived under and, if it no longer holds control, may take control only when nothing was handed off since, so a click queued behind a slow request cannot re-take control after the user let go, and a viewer that left (`gone`) never becomes the controller. Viewer ids are random UUIDs. Every input batch reaches the service with `x-surface-viewer` and `x-surface-frame-seq`: the service's own sequence number (kept apart from the host's bumped `seq`) of the frame that viewer last acknowledged, read when the batch arrives, not when the queue reaches it. A 409 answer becomes an `INPUT_STALE` error to that viewer. Control notices carry `viewer` for a user controller. `viewerHeaders(guestId, viewerId)` gives `/api/guests/:id/service/request` the same viewer, control, and frame headers when the panel names a live viewer of that extension (`viewerId` in the body, from `surface-viewers.ts` in the UI); an unknown id adds nothing. `userControls` gates the browser provider; `endForGuest` (pause, removal, withdrawn approval) and a failed frame request end the session with an `ended` reason, and `stop()` closes every viewer on shutdown.
- The callback listener (`host-callback.js`) is how a host-spawned service calls OpenChamber back: a Node HTTP server on `127.0.0.1:0`, started on first use, unref'd, separate from the Express app, so the relay, tunnels, UI auth and a LAN bind never reach it. Routes are `POST` with a JSON body (at most about 6 MB) and `Authorization: Bearer <capability>`; a request with an `Origin` header (a browser) is refused. A route is `{ refusal, serve }`: `refusal(bearer)` runs before any body is read, so a bearer the route does not know is turned away without buffering anything, and a body past the cap stops being read at the cap; both answers cut the connection once sent. Its routes are `/source-control/outbound` and `/notifications/outbound`, each served by its own `../source-control/outbound-handles.js` instance. Only a service whose manifest provides `source-control` or `notifications` gets `OPENCHAMBER_HOST_CALLBACK_URL` in its environment (`startGuestService`); every other service never learns the port.
- A service that provides `source-control` is driven by the host like a browser provider (`../source-control/extension-provider.js`), with a 10-minute idle stop. Its grant scope (`grant-scope.js`) adds `service.sourceControl: { defaultInstances, custom }`, compared in `effectiveGrants`: a version that adds the role, drops it, or changes the instances it reaches needs approval again. The key is absent for every other service on both sides, so their stored approvals are unaffected. `persist.js` keeps the key when it reads stored scopes.
- A service that provides `notifications` is driven by the host as well (`../notifications/extension-channels.js`): the catalog decides which are channels, the accounts live in `../notifications/channel-accounts.js`, and every call carries a handle from `../source-control/outbound-handles.js` served on `/notifications/outbound`. Its grant scope adds `service.notifications: { kind, origin? }` (where the account lives), compared in `effectiveGrants`: a version that adds the role or moves the fixed origin needs approval again; `persist.js` keeps the key. `startGuestService` sets `OPENCHAMBER_HOST_CALLBACK_URL` for this role as for `source-control`.
- A service whose package declares `contributes.sessionEvents` is driven by the host too (`session-events.js`, below). Its grant scope adds `service.sessionEvents: { events, content }`, compared in `effectiveGrants` for `service` and, for `transcript`, required to have `content: true` as well: a version that adds an event type or starts asking for content needs approval again and receives nothing meanwhile. `persist.js` keeps the key; without it the schema would strip a stored subscription on every read and the card would ask again after each restart (`persist.test.js` pins the round trip).
- `serviceRequest` never leaves that guest's loopback port. Auth to the service is `Authorization: Bearer` with a host-minted token. The service env is an allowlist (PATH, HOME, temp, locale, Windows system variables) plus `OPENCHAMBER_SERVICE_*`; host secrets are not inherited. There is no sandbox: an allowed service has the user's full access, and the grant card says so. Ready is `GET /health` → 200. Parallel first requests share one spawn; they must not kill each other mid-start. Host quit stops every service; after a host crash, the next host start does (see Crash recovery). Disabling a guest stops its service without clearing OAuth or grants.
- File access is decided in `files.js` on canonical paths, never on the string the guest sent. `matchesFilesystemPattern`, `expandHome`, and `globToRegExp` are pure; `resolveGuestFilePath` and `runGuestFileOperation` take `fsPromises` / `nodePath` so tests can stub the OS. The project directory is whatever `resolveOptionalProjectDirectory` validated for this request, so a guest cannot name a project the UI did not open.
- Update swap (`updates.js` `updateGuest`): the new clone lands in `{dataDir}/extensions/.tmp-<id>-<random>` and is inspected exactly like an install before anything else moves. Only then: stop the guest's service, rename current → `.old-<id>`, rename temp → final, delete `.old-<id>`. Any failure before the swap deletes the temp dir and leaves the install untouched; a failed second rename moves `.old-<id>` back. The store row is not rewritten (same path, same id), the catalog cache and that guest's update cache entry are dropped.
- Update checks (`updates.js` `checkGuestUpdate`) never overlap for one installed copy: a second caller gets the running check's result, so two `git fetch --depth 1` runs cannot fight over `.git/shallow.lock`. Inside that guard a `shallow.lock` older than 60 s is removed before fetching, because nothing of ours is running. `runGit` ends a timed-out command with SIGTERM and only sends SIGKILL after 3 s, so git can remove its own locks. A `fetch-failed` result is not written to the update cache.
- The OAuth callback skips UI auth. Everything else under `/api/guests` stays behind the usual session.

## Session events

`session-events.js` owns the delivery of session events to extension services (`contributes.sessionEvents`, SDK `session-events.ts`): which catalog rows receive which event, when `turn-finished` fires, what each request carries, and how a delivery fails. `index.js` creates one runtime, feeds it every translated event from the hub loop after the trackers (`processPayload(payload, directory)`) and the server-made `openchamber:page-waiting` / `page-settled` from `onPageWaitChange`, calls `reconcile()` from `onGuestActivated` and the deactivation listener list in `feature-routes-runtime.js`, and stops it first thing in the graceful shutdown, in the same tick that closes admission to guest services (`beginGuestServiceShutdown`), so no event meets the shutdown refusal and reads as a broken service. The notifications runtime owns what a person is told; this module owns what an extension's service is told, and the two share the gates for "the turn is finished".

Invariants:

- Only host sessions reach this subscriber. Isolated-space events remain excluded from the hub subscription: their session ids must never be used for host OpenCode reads.
- The catalog decides, at delivery time, never an event: a guest is a subscriber when it is enabled, fully approved with an effective `service` grant and declares the event's type (`isSessionEventSubscriber`); content goes only to a guest holding `transcript`. `reconcile()` drops what waited for a guest that stopped being a subscriber and lets a subscriber deliver again at once.
- `turn-finished` is a `session.idle` that is not aborted, with no open ask on the session (`permission.asked`, `form.created` and `page-waiting` open one; `permission.replied`, `form.settled`, `page-settled`, `session.error` and an aborted idle close them), no working subagent (`createSessionActivityProbe`, the ready notification's check; one that cannot be made counts as none), no active goal in the session's metadata and no auto-review step (`isInAutoReview`). Two idles for one turn end within `SESSION_EVENT_IDLE_DEDUPE_MS` are one event; a busy `session.status` (a new turn) in between resets the window, so a quick follow-up turn is announced. The subscriber check runs before any read, so an idle with no subscriber costs nothing.
- `permission-asked` is sent `SESSION_EVENT_PERMISSION_DEBOUNCE_MS` after the ask, only while the request is still open and not auto-answered (the permission-auto-accept predicate, checked before arming and when the timer fires), once per `sessionId:requestId`.
- Every request carries identifiers only unless content was approved: `linked` is the stored link entries' ids, kinds, urls, providers and identifiers, never titles; `project.directory` is the event's directory, else the session record's, else `null`. The reply is cut at `SESSION_EVENT_REPLY_MAX` and flagged; `turn-failed` carries the error and no reply (the failing step has no `finish: 'stop'`, so a reply read would be an earlier turn's).
- Delivery is per guest, in order, one request in flight, at most once, with no persistence; events waiting for a starting service are capped at `SESSION_EVENT_PENDING_MAX`. A failed delivery (timeout, non-200, `ok: false`, unparseable) drops that guest's queue and its events for `SESSION_EVENT_FAILURE_BACKOFF_MS`, with one warning naming the guest, the event type and the service's `error` text; `NO_SERVICE`, `DISABLED` and `CANCELLED` mean "not a subscriber right now" and drop the queue with no warning and no backoff, except that a `NO_SERVICE` for a guest the catalog still lists as a subscriber (its service entry is missing or outside the package) is warned once, until the catalog changes. Nothing here logs event content.
- The service receives no token, no callback URL and no path back into the session through this route.

### Why a failed delivery drops events for 30 s and not a retry queue

Events are time-sensitive: a comment about a turn that ended a minute ago is noise, and a flood after a service recovers would be stale. The service already gets a chance per event; a backoff bounds the cost of a broken service to one request per 30 s and keeps nothing to replay.

### Why `NO_SERVICE` is silence and not a failure

The proxy answers `NO_SERVICE` for a paused or removed package, a withdrawn approval and a host shutting down, and `DISABLED` for a pause that landed between the catalog read and the call. None of these is the service's fault, and a pause that cost 30 s of dropped events after re-enable would read as a bug. The runtime also aborts its own requests on `stop()`, which surfaces as `CANCELLED`; without the signal a shutdown would surface as `NO_SERVICE` too. The entry checks in `service.js` share the `NO_SERVICE` code, so the runtime tells them apart by asking the catalog: a guest still listed as a subscriber was not paused, and its missing entry is said once.

### Why the open asks are tracked here and not read from OpenCode

The idle that follows a form or a page the agent shows arrives while the user still has to answer; asking OpenCode for the session's pending requests on every idle would be a read per turn end, and the translated stream already carries every ask and every settle. The set is cleared on `session.error` and on an aborted idle, so a settle the server missed cannot silence a session for good.

### Why preparation reserves arrival order before reading

Record and metadata reads can finish in a different order. Each announcement reserves its output position before those reads. The oldest preparation can hold at most `SESSION_EVENT_PENDING_MAX` later preparations; admission rejects newer announcements before any reads and warns once until the queue drains. Dropped announcements still update ask/settle tracking synchronously. Stop clears prepared bodies, aborts record reads and prevents unfinished preparations from starting follow-up reads. An idle captures its turn's terminal claim on arrival, so a later busy event starts an independent claim and an older read cannot suppress the next turn. The parent cache retains the directory too, expires after 60 seconds and is invalidated by session updates or deletion.

## Host shutdown

`beginGuestServiceShutdown` closes service admission synchronously. Requests retain
their host lifecycle across store reads and startup awaits, so a late completion
cannot spawn a process during shutdown or enter a later host lifecycle.
`stopAllGuestServices` cancels and drains pending starts as well as running and
already-stopping children. Per-guest Pause and ordinary cleanup do not close host
admission. `beginGuestServiceHost` opens a new lifecycle only after that drain.
The common graceful-shutdown runtime stops surface viewers before the services.

## Crash recovery

A host that dies without a shutdown (SIGKILL, an OOM kill, power loss) leaves
its services running with no parent. `service-registry.js` covers that case.
Every spawn writes `{openchamberDataDir}/guest-services/<pid>.json` (mode
`0o600`) with the pid, the host's pid, the guest id, the host binary, the
absolute entry script, and the SHA-256 of the service token; the token itself
is never written. The record goes once the child exits, whatever ended it.
Shutdown awaits that removal for a child that exited; one that outlived SIGKILL
keeps its record.

`beginGuestServiceHost({ registryDir })` starts the reaper, and every start in
that host lifecycle waits for it before spawning, so a leftover holding a
socket or a lock is gone first. For each record the reaper decides:

- Process gone, or the pid now runs something else: drop the record.
- Still ours and its host is alive: leave both.
- Still ours and its host is gone: SIGTERM, SIGKILL after 5 s, drop the record.
- Unreadable process: leave both for the next start.

"Still ours" is the recorded token digest found in the process environment on
Linux (`/proc/<pid>/environ`) and macOS (`ps -E`). Windows exposes no other
process's environment, so there the CIM command line must contain the recorded
entry script and the executable must be the recorded host binary. "Host gone"
on Unix is a parent pid other than the recorded owner, since a parent pid
changes only when the parent dies; Windows never reparents, so there the owner
pid must be dead. Records that do not parse, including a non-positive pid that
would signal a process group, are dropped without signalling anything. A temp
file a host left between writing a record and renaming it
(`<pid>.json.tmp-<writer pid>-<hex>`) is removed once its writer pid is dead.
Tests call `beginGuestServiceHost()` without a directory, which records nothing
and reaps nothing.

Orphans are rare on Windows: libuv puts every spawned child in a job object that
is killed with the host, even on a hard kill, so the Windows branch of the
reaper is a safety net.
