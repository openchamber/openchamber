# GitLab module

## Purpose

This module owns GitLab instance validation, authentication, remote resolution, and source-control resources for GitLab.com and self-managed GitLab.

## Invariants

- Instance identity is the normalized URL origin. HTTPS is required except HTTP loopback instances used for local deployments and tests.
- Selecting a self-managed instance intentionally allows authenticated users to reach private-network and loopback GitLab origins. Probe, OAuth, and token-verification requests never follow redirects, so those requests stay bound to the selected origin.
- Device-flow probing first confirms GitLab through `/api/v4/version`, accepting either a version payload or an authenticated response carrying GitLab's response marker, then probes `/oauth/authorize_device`. Network and server failures are not reported as unsupported device flow.
- Starting device flow makes one `/oauth/authorize_device` request with the `api` scope. It does not create a disposable grant before the grant returned to the user.
- Device-flow start exposes only an opaque OpenChamber `flowId`, user code, verification URL, expiry, and polling interval. The process-local source-control registry retains the raw provider code and the client ID used at start. Completion requires the same normalized instance and consumes terminal results once; pending and slow-down results remain pollable. Restart, unknown IDs, consumed IDs, and instance mismatch return `410`, while an overlapping poll returns `409`.
- OAuth and personal access tokens are verified through `/api/v4/user` before storage.
- Device flow reads its OAuth application ID from `OPENCHAMBER_GITLAB_CLIENT_ID`, then the persisted `gitlabClientId` setting, and finally OpenChamber's own application, which is registered on `https://gitlab.com` only. A self-managed instance therefore reports `device.available: false` with reason `invalid-client` until its operator supplies an ID. PAT and `glab` authentication do not require an OAuth client ID.
- `glab auth token --hostname <host>` is a bounded, shell-free fallback. Its token stays in memory for the request and is never persisted or logged.
- Auth data lives in the versioned `source-control-auth.json` file under `OPENCHAMBER_DATA_DIR` or the default OpenChamber data directory. Writes use an atomic rename and mode `0600`. Malformed or unsupported storage fails closed and is not replaced by a later mutation. This module does not read, migrate, or alter `github-auth.json`.
- Accounts and repository bindings are scoped by provider and normalized instance. Provider binding persistence, uniqueness checks, exact status validation, and account reconciliation use the same normalized origin and immutable credential ID. New credential IDs are opaque `occred:v1:gitlab:<uuid>:r1` values; the separate provider-user ID includes the normalized instance and GitLab user ID. Migrated records preserve their old provider-user-shaped credential IDs so existing `ocgit:v1` references remain exact.
- Persisted accounts retain `valid` or `invalid` status. `readAccount(instance, credentialId, revision?)` returns only that matching valid persisted revision and keeps its `providerUserId` separate. It never falls back to the active account or `glab`.
- Token-free account inventory remains available when the active credential is invalid or provider verification has a network failure.
- A provider resource `401` marks only the acting account invalid after source-control bindings have moved to `needs-attention`. Resource `403` and network failures preserve account validity.
- Canonical resource routes receive the immutable credential `accountId` from validated repository binding authority. Exact persisted and CLI lookup fails closed when the credential is missing, invalid, or the verified CLI user changed.
- Canonical merge-request, issue, branch, and upstream reads require an authoritative repository-binding read context. They validate repository identity, binding and Git-config revisions, bound state, normalized instance, immutable account ID, and primary remote before credential lookup or GitLab client creation.
- Canonical reads resolve only the validated primary remote. They never rank or fall back to tracking, `origin`, `upstream`, or another configured remote. Explicit issue and branch selectors may name only that primary project or its declared fork parent; parent lookup failures remain request failures rather than outside-network not-found success.
- Auth removal requires the exact credential `accountId` and reconciles matching bindings before deleting that account. Missing authority returns `400` without falling back to the active persisted or CLI credential. Removing one account never retargets those bindings to another account. The ambient `/api/source-control/gitlab/me` route is retired with `410` and `SOURCE_CONTROL_ACCOUNT_CONTEXT_REQUIRED`.
- Remote parsing accepts HTTPS, scp-style SSH, and `ssh://` URLs only when the hostname matches the requested instance. HTTP is accepted only for an HTTP loopback instance used by local deployments and tests. HTTP and HTTPS remotes must match the exact web origin authority; SSH may use the instance's separately configured SSH port. Nested namespaces remain part of project identity.
- Merge-request discovery ranks explicit, tracking, `origin`, `upstream`, then remaining remotes. Open requests across the fork/upstream candidates win; closed or merged history is limited to the highest-ranked source and its upstream.
- Resource payloads are converted to provider-neutral DTOs inside this module. Project web and clone URLs must match the selected instance and reported project path. Malformed canonical issue, nested issue identity and label data, issue-note, branch, fork metadata, merge-request list, merge-request note, and diff payloads fail the read rather than becoming partial, empty, or not-fork success. Raw GitBeaker payloads do not cross the server boundary.
- CI lookup is partial enrichment. A jobs failure or malformed jobs payload leaves the merge request authoritative and returns `ci: null`.
- GitLab supports merge and squash through the shared mutation. Rebase is not advertised because GitLab cannot perform it as the same atomic merge operation.
- The four merge-request mutation routes are canonical only. They require the complete repository binding context and durable idempotency executor; missing validation or execution support returns `501`. Validation runs before credential lookup, client creation, project resolution, or provider access, and mutation authentication uses only the validated account.
- Canonical mutation target resolution starts only from the trusted primary remote and that project's declared fork parent. The expected target project must match one of those projects. Parent lookup failures fail the request. Create accepts `remote` only when it equals the primary remote. `headRemote` defaults to the primary remote; an explicit value resolves that exact remote without ranking or fallback and must map to the already established primary/parent network.
- Update, merge, and ready preflight the expected project, merge-request number, head, base, and head SHA against strictly mapped provider state immediately before execution. Mutation preflight, mutation responses, and restart reconciliation also require an authoritative boolean `draft` or `work_in_progress` field. Broader resource reads retain compatibility with older payloads that omit those fields. Durable targets contain the repository and binding revisions, primary remote, server project identity, and actual merge-request coordinates. Digests cover the exact credential account ID and revision, resolved target, and every normalized operation input. Durable records never contain titles, descriptions, provider payloads, tokens, or remote URLs.
- The shared mutation executor claims the idempotency key durably before one provider write. After binding validation and exact local credential lookup, terminal durable records replay without provider project or merge-request preflight. Their stored credential actor and resolved target must match the trusted request, and the route recomputes the digest from that stored target, the resolved credential revision, and normalized operation input. Changed input conflicts. The route derives `providerUserId` from the resolved credential and passes it separately as receipt actor `providerAccountId` and audit identity; request payloads cannot inject it. Two credentials for one GitLab user therefore retain distinct replay authority while sharing provider actor identity. Only authoritative provider `4xx` rejections are definite failures. Provider `5xx` and transport, socket, network, or timeout failures after dispatch are outcome-unknown and never trigger a retry. A mutation `401` invalidates only the validated acting account.
- Restart reconciliation reads GitLab and never repeats a mutation. Running records resolve provider coordinates only when reconciliation needs them. Create succeeds only when one merge request exactly matches source project and branch plus target project and base. Update remains outcome-unknown because its private title and description are not persisted. Merge succeeds when GitLab reports merged, and ready succeeds when GitLab reports non-draft; authoritative unchanged states become definite failures where safe. Ambiguous or malformed results remain outcome-unknown.
- Cross-process execution exclusion, lock errors, and stopped-writer orphan recovery follow the [source-control lock contract](../source-control/DOCUMENTATION.md#cross-process-locks-and-manual-recovery). A live or crashed owner's execution lock blocks reconciliation; restarting alone does not remove it.
- GitLab has no route-level status, context, list, or history caches. After success, the client must perform an authoritative refresh. There is no server cache to evict, and failed mutations do not alter unrelated server state.
- Issue and merge-request list operations return open records for shared pickers. Direct number/context lookup can still resolve closed records.
- Shared picker and sidebar consumers select GitLab only from a matching repository remote. Self-managed hosts must already appear in source-control instance discovery; unknown hosts are never inferred as GitLab.

## Structure

- `instance.js`: instance origin normalization and transport policy.
- `auth-storage.js`: generic versioned auth persistence.
- `device-flow.js`: host probe, device authorization, and token exchange.
- `verify.js` and `user.js`: token verification and payload parsing.
- `glab-credential.js`: host-scoped CLI credential retrieval.
- `client.js`: GitBeaker client factory for later resource modules.
- `repo.js`: instance-bound remote parsing, ranking, and directory resolution.
- `mappers.js`: GitLab payload validation and provider-neutral DTO conversion.
- `resources.js`: project, issue, merge-request, and CI orchestration.
- `routes.js`: thin HTTP registration and auth/resource orchestration.

`GET /api/source-control/gitlab/auth/accounts?instance=...` returns persisted account metadata without tokens. The existing auth status route carries the same inventory for connected and disconnected states.
