# Gerrit module

## Ownership

This module is Gerrit as a source-control provider: instance validation, sign-in with a username and HTTP password, remote resolution, REST reads and writes, and their mapping to the neutral source-control DTOs plus the change-review fields (`voteLabels`, `submitRequirements`, `revisions`, `localRevision`). It runs behind the shared route shell (`source-control/provider-routes.js`), which owns HTTP, read-context validation, the `revision` query check, the status cache and the durable mutation executor. Reading Change-Id trailers is `source-control/change-id.js`; pushing to `refs/for/<branch>` and fetching `refs/changes/...` are the Git network planner's (`git/network-operation-plan.js`). No UI code names Gerrit: the client draws what the published descriptor says (term `change`, votes, revisions, push to create, submit).

Target: Gerrit 3.8 or newer, verified against live 3.8.9 and 3.10.9 (see *Verified against live instances*); `fixtures/api.json` holds their recorded answers.

## Invariants

- An instance is a normalized origin: HTTPS, or HTTP on a loopback host (a local `--dev` site). Sub-path installs are refused, because REST paths are `<origin>/a/...` and projects `<origin>/<name>`. There is no default instance; every instance comes from an account in `section('gerrit')` of `source-control-auth.json`.
- Sign-in is a Gerrit username plus an HTTP password (the descriptor's `username` and `http-password` settings fields). `/auth/token` verifies them with `GET /a/accounts/self` over HTTP Basic, refuses an account without a `username` (`400 GERRIT_ACCOUNT_WITHOUT_USERNAME`: it cannot use Git over HTTP), then reads `/config/server/version` anonymously, and with the credentials when anonymous reads are refused. A version older than 3.8 is `400 UNSUPPORTED_PROVIDER_VERSION` before anything is stored. Without credentials (the Settings capability probe) a refused version read leaves the instance unknown and lets it through. The username is stored as the account's `login`; re-verification, the REST client (`loginFor(session)`) and Git transport (`httpsUsername: { kind: 'login' }`) all use it.
- Credentials go only to `<origin>/a/...`, as `Authorization: Basic`. An anonymous client never sends to `/a/`. Every URL is built from the origin and checked against it before it is sent; `redirect: 'manual'` and any 3xx is an error, so a redirect cannot carry the header elsewhere.
- JSON answers start with Gerrit's `)]}'` line, which is stripped before parsing. Errors are plain text, or JSON with an `error` field (3.10 refuses an unknown reviewer with a 400 `ReviewerResult`), and become `{ status, message }` (capped at 500 characters). Reads retry after 429 and 502, up to three attempts; writes are sent once.
- A 401 writes the account off (`invalidated` first, then the store marks it invalid). A 403 or a network failure leaves it valid.
- Remotes: HTTPS must match the instance's exact authority, HTTP only for a loopback HTTP instance, SSH (any port, normally 29418) and scp-like remotes its hostname. On HTTP(S) a leading `a/` is Gerrit's authenticated path and is dropped; over SSH it is a real segment. Project names nest or stand alone (`repositoryPath: 'path'`): the `{ owner, name }` selector comes from `splitProjectPath` (`source-control/project-path.js`), split on the last slash, so `demo` is owner `''`, name `demo`, and `team/app/sub` is owner `team/app`, name `sub`; `joinProjectPath` turns a selector back into the project name. Change URLs use the `{project+}` token (`/c/{project+}/+/{number}`).
- Bound reads use only the binding's primary remote's project. A selector naming another project is a 404, and so is a change whose `project` is not the bound one. Gerrit has no forks, so `projectUpstream` is never a fork.
- Ids: a project's id is its full name; a change request's id is `<project>#<number>`; REST paths use `<project>~<number>` with the project URL-encoded, built from `project` and `_number`. ChangeInfo's own `id` is never read: 3.8.9 answers the `project~branch~Change-Id` triplet there, 3.10.9 `project~number` with a separate `triplet_id`. Changes of one Change-Id are matched by `change_id`.
- A change maps to a `ChangeRequest` with `draft` = `work_in_progress`, `private`, `topic`, hashtags as read-only `labels`, `head` = the current patchset ref (`refs/changes/NN/N/P`), `headLabel` = `Patchset P`, `revisionNumber`, and `mergeable` = `submittable` (open changes only; `mergeableState` `clean` or `blocked`).
- Status is found by the Change-Id trailer of the local branch tip, never by branch name: `change:<id> project:<name>`, up to 10 candidates. Among cherry-picks of one Change-Id the open change on the branch the local branch tracks on the primary remote wins (`git rev-parse --symbolic-full-name <branch>@{upstream}` with `branch.<b>.remote`; an upstream on another remote counts as none), then the one on the project's default branch (`/projects/{name}/HEAD`), then the only open one, then the most recently updated open one, then the newest merged or abandoned one as history. No Change-Id answers `changeRequest: null` without asking Gerrit. `localRevision.uploadedAs` is the patchset whose commit is the local tip, null when local commits are not uploaded. A local Git failure (no such branch) fails the read.
- An open change's status and context carry `stack` from `/revisions/current/related`, reversed to bottom-first (`number: null`, `base` = the change's branch, each `head` the layer's current patchset ref). Entries without a change number or of another project are left out; one relative is no stack (null). An unreadable chain leaves `stack` absent, except a 401.
- Context reads `ALL_REVISIONS`, `CURRENT_COMMIT`, `LABELS`, `DETAILED_LABELS`, `DETAILED_ACCOUNTS`, `MESSAGES`, `SUBMITTABLE`, `SUBMIT_REQUIREMENTS`: 3.8 leaves a label's `approved` / `rejected` / `recommended` / `disliked` summary out under `DETAILED_LABELS` alone. `reviewers` comes with `LABELS`, so mutation reads and reviewer candidates ask for that, not the detailed labels. `voteLabels` list each label's values, the caller's `permitted` values, `blocking`, a status (rejected over approved over disliked over recommended) and the non-zero votes; a zero in `all` only means that person may vote. Change messages are `issueComments` (with `revision`), published inline comments are `reviewComments`. `verdicts` are absent: votes hosts have none. `ci` is null: a Verified label is a vote.
- Files, diff, patch and file contents are those of `revision` (a patchset commit SHA the change has; another is a 404), the current patchset when none is named. The diff is the diff part of `/revisions/{rev}/patch` (base64 `format-patch` mail; headers and signature dropped). That patch has no rename detection: a renamed file's patch is the addition of its new path (the deletion of the old path is in `diff` too), while the file list still says renamed with `previousPath`. `/COMMIT_MSG`, `/MERGE_LIST` and `/PATCHSET_LEVEL` are not listed as files; `/COMMIT_MSG` can still be read, with no earlier side. The earlier side of a file is the patchset's first parent (`parent=1`). File contents over 5 MiB are `413 file-too-large`.
- Mutation kinds and digests are the standard table's (`source-control/standard-mutations.js`), including its votes branch: `/pr/review` takes `{ votes, body? }` under `change-request-review`, `/pr/merge` `{ method: 'submit' }` under `change-request-merge`. Both digests are frozen in `provider.test.js`. A review answer is accepted with or without `change_info` beside `labels` (3.10.9 adds it, 3.8.9 does not); only an `error` in it fails the vote. Routes performed: merge (submit), ready, review (votes), comment, state, reviewers. `/pr/create` is not among them (a change is created by push), nor are update, labels and the issue routes; the shell answers 501.
- Submit and votes require `target.headSha` (the standard table answers 400 without it; its `/pr/merge` digest stays `{ method }`) and check the current patchset against it first, so a newer upload is `SOURCE_CONTROL_MUTATION_TARGET_MISMATCH`, never a submit or vote on unread code. `submit()` also refuses a target without one, so no other path posts an unchecked submit. Votes are posted to that commit (`/revisions/{sha}/review`). Submit reconciles by `status === 'MERGED'`, ready by `work_in_progress` not set, state by the change status (closed = abandoned, open = restored); votes and comments stay `outcome-unknown`.
- Reviewers are set as a whole set of numeric account ids from `reviewers.REVIEWER`: additions (`POST /reviewers`), then removals (`POST /reviewers/{id}/delete`), one call per account. A `ReviewerResult.error` is a 400. Reconciliation succeeds only when the set matches.
- Reviewer candidates are the owners and reviewers of the project's 25 most recent changes: Gerrit has no project-member list a user can read.
- A worktree from a change uses the branch `change-<number>`, the current patchset ref as `headRef`, classification `same-repository`, and `<origin>/a/<project>` as the endpoint.
- List filters: `open` = `status:open`, `closed` = `status:closed` (merged and abandoned), `merged` = `status:merged`; `created` = `owner:self`, `reviewRequested` = `reviewer:self -owner:self`, `assigned` = `attention:self`; a search is the change number when it is one, else a quoted `message:` term. Pages are 20 changes, `S` offset, more while the last one says `_more_changes`.

## Enterprise mode

Gerrit is a new destination for a credential and for what the user writes into votes, messages and comments, at an origin the user entered. It follows Gitea and self-hosted GitLab: a user-initiated action toward a service the user connected is outside the mode today (`enterprise-boundary` skill), and whether enterprise mode should gate self-hosted source-control providers is an open product question for the maintainer.

## Verified against live instances

On 2026-10-22 every endpoint the module calls was exercised against Gerrit 3.10.9 and 3.8.9 (`gerrit.war init --batch --dev`, Java 17, three accounts, the fixture scenario rebuilt in a nested project `platform/app`), and the whole provider was driven end to end through the shell routes and the Git routes on both: status by branch, lists, context at both patchsets, patch and file reads, live summaries, candidates, every mutation route, push for review, the Change-Id preflight. `fixtures/api.json` holds the recorded answers, scrubbed and renumbered (its `_comment` says how); unsuffixed entries are 3.10.9, `_3_8` entries 3.8.9. "Both" below means both releases answered the same.

- Version and REST shapes: `/config/server/version` answers anonymously, also when anonymous users are blocked from reading every ref (both). `submit_requirements`, `o=SUBMIT_REQUIREMENTS` and `PUT /changes/{id}/message` exist (both; an empty message is a plain-text 400). REST paths `project~number` work with a URL-encoded nested project (both); ChangeInfo `id` is `project~branch~Change-Id` on 3.8.9 and `project~number` plus `triplet_id` on 3.10.9. 3.8.9 has no `current_revision_number`; the patchset number comes from `revisions`.
- Labels: value keys are `"-2"`, `" 0"`, `"+1"` and `permitted_labels` lists the same strings (both). `DETAILED_LABELS` alone leaves out the label summaries on 3.8.9, not on 3.10.9 (fixed: `LABELS` is asked too). Neither release sends `blocking` on a label. A NoBlock label (Verified) has no submit requirement; the default Code-Review requirement is legacy and has no description.
- `reviewers` comes with `LABELS` as well as `DETAILED_LABELS`, on single changes and on queries (both); nothing is answered without a label option. `CURRENT_COMMIT` dates use Gerrit's timestamp format, with `tz` in minutes (both).
- Paging: the last change of a full page carries `_more_changes: true`, `S` starts the next page (both). `attention:self` and `message:"..."` answer as filters (both).
- `/revisions/{rev}/patch` and `/files/{path}/content` answer base64 text without the XSSI line to `Accept: text/plain` (`x-fyi-content-encoding: base64`); asked for JSON they answer a JSON string instead (both). The patch has no stat block and no signature, and no rename detection. `parent=1` reads the earlier side; `/COMMIT_MSG` reads at the patchset and at `parent=1` (the same message); a deleted file at the patchset and an added file at `parent=1` are a plain-text 404 (both). File statuses seen: `A`, `D`, `R` with `old_path`, none for a modification; a copy reads as `A` and a full rewrite as modified, so `C` and `W` were never answered (both).
- `/related` lists the chain newest first and includes descendants and merged ancestors (both).
- Errors: 401 `Unauthorized`, 404 `Not found: <project>~<number>`, submit blocked 409 `Failed to submit N changes due to the following problems:` with one `submit requirement '<name>' is unsatisfied` line per change of the chain, ready on a ready change 409 `change is not work in progress`, a change message or inline comment over 16384 characters 400 `Comment size exceeds limit` (both). An unknown reviewer is a 400 JSON `ReviewerResult` on 3.10.9 and a 200 one on 3.8.9 (both carry `error`). Votes on an older patchset are accepted (200) and stay on that patchset, the current votes untouched (both), so the module's own current-patchset check is what keeps a vote on the code the user read.
- Writes: `POST /ready` and `/wip` answer the JSON string `""`; abandon and restore answer the ChangeInfo; submit answers it with `MERGED` (default `MERGE_IF_NECESSARY`); `POST /reviewers` answers a `ReviewerResult`, `/reviewers/{id}/delete` a 204 (both). A review answer carries `change_info` on 3.10.9 only; a message-only review answers `{}` on 3.8.9.
- Pushes: `%topic=`, `wip`, `private` and `t=` set what they name (both, through the network operation route). A commit without a trailer is refused with `missing Change-Id in message footer` in the remote output; a Change-Id closed on the same branch is refused with `change <url> closed` (both).
- Remotes: HTTP(S) remotes with the `/a/` prefix, `ssh://user@host:29418/<project>` and scp-like remotes resolve to the HTTP instance on the same host (both; read only, the dev sites run no SSH daemon).
- Reviewer candidates from recent changes list owners and reviewers (both).

Still unverified:

- Git transfers on an HTTP loopback instance: the Git network planner and its operation store now accept an HTTP endpoint on a loopback host when a registered provider allows loopback HTTP (`../git/loopback-http.js`), so push for review and a worktree from a change are allowed there, but neither was run against a live loopback HTTP Gerrit. Push for review was verified through a TLS front on the same Gerrit; a worktree from a change could not be, because managed Git trusts only the system certificate store. LFS upload stays HTTPS-only (`GIT_ALLOW_PROTOCOL=https` in `../git/network-operations.js`), so a review push from a repository with LFS objects to a loopback HTTP instance fails.
- Submit types that leave a change `SUBMITTED` but not `MERGED`, Gerrit's newer authentication tokens (not on these releases), an SSH daemon on 29418 (transfer, not remote parsing), a front proxy that refuses anonymous `/config/server/version`, hosts with many changes (`n` caps), `.gitcookies` hosts.

## Open questions

- **`.gitcookies` and googlesource.com-style hosts** are unsupported: their review host differs from the Git host, so the binding's instance check cannot match.
- **Editing a change's description** (`/pr/update` through `PUT /changes/{id}/message`) is left out: it creates a new patchset, which is a product question.

## Registration

Gerrit is the last built-in in `BUILT_IN_DESCRIPTORS` (`source-control/provider-descriptors.js`) and `BUILT_IN_LOADERS` (`source-control/provider-registry.js`), so the web adapter's older-server fallback keeps the leading entries. Its submit and votes digests are frozen in `source-control/mutation-digest-freeze.test.js` as well as `provider.test.js`; `source-control/provider-routes.gerrit.test.js` drives every route through the shell.

## Decisions

### Why a fetch client and not a Gerrit SDK

The calls are plain REST, the module needs exact control over redirects, retries and where the credentials go, and no dependency may be added. Gerrit's XSSI line and plain-text errors are two small rules a client of its own keeps in one place.

### Why status reads the Change-Id and not the branch

A Gerrit change has no source branch: it is pushed to `refs/for/<target>` and found again by the Change-Id trailer of the commit. Matching branch names would answer the wrong change, or none, for any local branch name.

### Why cherry-picks are chosen by tracked branch first

One Change-Id can be open on several branches. The local branch's upstream is what the user pushes for review against, so it names the change they mean; the default branch and recency only break ties when it does not.

### Why votes are pinned to the read patchset and not `current`

`revisions/current/review` would land votes on whatever was uploaded last, which the user never read, and Gerrit accepts a vote posted to an older patchset (it stays there and is not copied to the current one). Checking the current SHA first and posting to that commit turns a race into a target mismatch.

### Why candidates come from recent changes

Gerrit exposes no project-member list a normal user can read, and suggesting arbitrary accounts would need the account search, which may list the whole instance. Owners and reviewers of recent changes are the people who review there.
