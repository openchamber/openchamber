# Source control module

## Purpose

This module owns source-control provider registration and server-side repository bindings. Shared clients call `/api/source-control/{provider}` routes, this registry selects the provider module, and each provider owns its authentication and resource behavior.

Repository bindings intentionally keep provider accounts, parent Git transport credentials, auxiliary checkout credentials, and commit identities separate. Managed remote and auxiliary bindings require endpoint-specific opaque `credentialId` values; system bindings reject that field in both input and persisted state. New managed HTTPS grants use `ocgit:v2` references that pin the immutable credential ID and revision and retain the separate provider-user ID for actor and audit attribution. Auxiliary records identify `submodule` or `lfs` plus exact redacted endpoint metadata. Bindings contain references and redacted endpoint metadata only; provider tokens remain in their provider auth stores. The Git network operation service, not provider routes or clients, owns transport execution.

## Registration

- `routes.js` registers GitHub and GitLab before the generic OpenCode proxy.
- GitHub resources use canonical `/api/source-control/github/*` routes. Auth and user aliases remain under `/api/github/*`; retired PR, repository, issue, and pull-context aliases return `410` before authority or provider work.
- GitLab uses `/api/source-control/gitlab/*` only.
- `GET /api/source-control/instances` returns the default identities plus self-managed GitLab origins already present in the server credential store. It never exposes accounts or tokens.
- `repository-identity.js` derives a repository ID from the real Git common directory and its filesystem identity. A checkout, linked worktree, and symlink share one ID; a moved or path-replaced repository resolves to a different ID. Its public config revision hashes a versioned canonical repository ID and sorted normalized effective fetch/push topology. Author, signing, and upstream-only edits do not invalidate that revision. Private transport identity separately hashes Git's effective transport-relevant configuration across system, global, local, worktree, and included files. Only that hash reaches transport validation; values and origin paths stay inside the Git query process.
- `binding-storage.js` owns version-2 `source-control-bindings.json` persistence under `OPENCHAMBER_DATA_DIR`. Reads and writes share one store-local queue and a cross-process snapshot lock that covers the entire read/check/write, including account reconciliation. A missing file reads as an empty version-2 store. A file carrying any other version, or one that fails the strict parse, is rejected with `INVALID_SOURCE_CONTROL_BINDINGS` and left on disk untouched: the store never converts, repairs or replaces it, and bindings do not silently start empty. Writes are atomic, mode `0600`, and compare-and-swap by repository revision. Deletes retain revision tombstones so stale requests cannot recreate a binding.
- `binding-contract.js` owns the dependency-free strict persisted binding parser, separate binding-response parser, readiness projection, aggregate state, and public endpoint validation for the server and the web adapter. The persisted parser rejects response-only credential presentation, so `source-control-bindings.json` remains references-only. The response parser accepts only the tagged safe presentation contract and rejects unknown fields. Safe endpoint metadata accepts credential-free HTTP/HTTPS, SSH URL, and SCP display forms plus bounded base64url fingerprints; local-file, credential-bearing HTTPS, query, fragment, traversal, control-character, and unsafe fingerprint forms fail closed. Each provider stores its approved fetch endpoint and readiness. Each remote stores readiness alongside its exact fetch/push endpoints; auxiliary grants have their own readiness. Only `ready` grants authority. `account-unavailable`, `confirmation-required`, and `config-changed` retain repair metadata without granting the affected capability. Binding `state` is an aggregate UI summary, never the authority gate.
- `mutation-storage.js` owns strict versioned persistence for bounded source-control mutation records in `source-control-mutations.json` under the server config root. `claim` persists an idempotency key before provider work, exact key-and-digest replays return the stored record, and digest changes report a conflict. `complete` permits one transition from `running` to a terminal state. Failed records may retain only an HTTP status and stable code for replay; messages and provider payloads are rejected. Terminal records have a seven-day retention by default and may be evicted oldest-first at capacity; `running` and `outcome-unknown` records are never pruned or evicted. Snapshots use serialized atomic mode-`0600` writes and reject unknown fields, provider payloads, private text, tokens, and raw URLs.
- `mutation-executor.js` canonicalizes and hashes mutation input, joins exact process-local duplicates, claims persisted state before provider work, and never retries a provider mutation. Provider routes include the exact resolved credential account ID and revision in this digest and keep the credential account ID in durable replay authority. They pass the verified provider-user ID separately for receipt actor metadata and audit `providerAccountId`; clients cannot supply it. Its store must provide `withExecutionLock(key, operation)`, scoped to that store's file path and the SHA-256 digest of the key, not the input digest. The executor holds this separate lock from before claim through provider work or reconciliation and mutation/audit completion. A second daemon waits or fails busy, never reconciles live work. Completed requests replay their compact receipt after acquiring the lock. An unlocked persisted `running` record enters provider reconciliation; a crashed owner's leftover lock is reclaimed by the next contender (see below). Ambiguous provider outcomes become sticky `outcome-unknown` records when persistence remains available. A failed completion write leaves the prior snapshot available for reconciliation, never another provider write.
- `audit-storage.js` owns the separate version-1 `source-control-audit.json` log under `OPENCHAMBER_DATA_DIR`. It does not share records, retention, or write sequencing with mutation replay storage. The strict schema stores one logical record per provider mutation idempotency key and per server Git operation ID. It accepts only `user` as the current initiator, the `provider-api` or `openchamber-server-git` executor, an immutable runtime and repository snapshot, an authoritative provider-user account ID or `null`, authoritative transport metadata, a compact redacted target, lifecycle timestamps, and a result state, stable error code, and bounded steps. An opaque credential ID is never substituted for provider identity. Provider API records require a `null` transport reference. Single-path Git records require either an exact opaque managed `credentialId` or a system marker. Sync records keep exact fetch and push references separately, including mixed system and managed transport. Checkout hydration records a bounded list of discovered auxiliary kinds and endpoint fingerprints plus only the exact server-validated transport reference for each granted endpoint; it records `null` transport when no transfer grant is used and always records a `null` provider account. Existing hydration records with the former single parent transport remain readable but new records never write that attribution. The schema rejects unknown fields and URL-shaped transport or target values, so raw endpoints, hydration paths, directories, key paths, credential payloads, process output, provider payloads, and free-form errors cannot enter the file. GitLab account IDs retain their authoritative normalized-instance prefix because that prefix is part of the account identifier, not a transport endpoint. Writes are serialized, atomic, and mode `0600`. Resolved terminal records expire after 30 days by default and are oldest-first capacity candidates; `planned`, `running`, and `outcome-unknown` records are never pruned or evicted.
- `mutation-executor.js` also drives provider audit lifecycle around the existing durable claim. Exact in-process duplicates and durable replays use `provider:<idempotencyKey>` and therefore reuse the same audit record, while `transportReference` remains `null` because provider API calls do not use Git transport. The executor rejects an audited execution before claim when the route omits verified provider identity. Two credentials for the same provider user therefore share actor identity in receipts and audits, but their exact credential and binding authority still produce different mutation digests. Audit persistence does not replace or relax mutation claim, digest conflict, reconciliation, sticky unknown-outcome, or replay behavior.

Provider replay and reconciliation after restart reuse the runtime snapshot from the existing audit record. Strict audit planning still checks the other immutable fields. Terminal replay does not rewrite audit history. An unfinished audit can complete from the durable mutation receipt without repeating provider work.
- `binding-service.js` accepts remote names and account/credential references, normalizes provider instances before uniqueness checks and persistence, then resolves endpoint metadata and provider repository coordinates from current server-side Git state. A provider instance must match the selected remote host and applicable HTTP port; supplied repository coordinates must equal the path-derived coordinates. Client-provided URLs are never authoritative. Provider reads check the binding revision, the bound provider's own readiness and that its primary remote still exists, so a remote added or removed beside it does not interrupt change-request status. A repository with no binding (revision 0) or whose binding names no account for a host is read with the account the client is signed in to on that host, as before bindings existed: the context must name a remote that really points at the instance, and whether the account exists is the provider route's to decide. Mutation contexts pass the same checks plus the binding's saved config revision, then validate an idempotency key and an exact, copied target shape before provider code receives them. Stale revision or config/remote errors carry the current authoritative repository, revision, and redacted binding record. Account reconciliation uses the same normalization and also matches equivalent instance spellings in previously stored records.
- `url-redaction.js` removes URL credentials, query data, and fragments from endpoint display URLs before repository context crosses the server boundary. Endpoint fingerprints remain derived from normalized transport authority rather than the shortened display, so hidden query or fragment changes still change authority.
- `status-cache.js` keeps the last-known change request status per exact trusted read context (instance, account, credential revision, repository, binding revision, directory, branch, remote), bounded and TTL-fresh. A provider route answers a fresh repeat from it, answers a transient provider failure with the last-known status, drops a repository's entries after a mutation and an account's entries after invalidation. GitLab uses it; GitHub keeps its own equivalent in `github/routes.js` for now.
- `oauth-flow-registry.js` keeps device-flow secrets in a bounded, process-local registry. Clients receive an opaque flow ID; completion acquires the matching provider and normalized instance exclusively, then releases retryable attempts or consumes terminal attempts. Restarting the server invalidates every outstanding flow.

## Cross-process locks and recovery

`file-lock.js` owns the dependency-free exclusion contract for source-control and Git stores that import it. Every snapshot read and complete read/check/write transaction acquires `<json-file>.lock` using exclusive `wx` creation with mode `0600`. Local queues preserve call ordering; each filesystem acquisition waits at most two seconds by default before `SOURCE_CONTROL_LOCK_BUSY` with HTTP `503`. Other lock I/O or ownership failures return `SOURCE_CONTROL_LOCK_FAILED` with HTTP `500`. Neither failure is an empty store, a missing binding, or a disconnected provider. Errors name the lock basename and explain stopped-writer recovery without exposing the data-root path.

Provider execution uses `<mutation-json-file>.execution-<sha256-key>.lock`. Snapshot locks are brief and never span provider network calls. Different execution keys and different stores can progress while another provider request runs. These locks support multiple daemons sharing the same data root; there is no global backend lock. All writers must use this contract and the same file location on a filesystem that supports exclusive creation and atomic same-directory rename. Older unlocked writers, external file edits, and removal or replacement of the data directory while writers run are unsupported.

Each acquisition writes its owner — process ID, hostname, time and a nonce — and keeps its file handle open. Normal `finally` cleanup verifies the pathname still identifies that handle's device/inode before unlinking and closing. Failed initialization cleans only that acquisition's file identity. A contender that finds an existing lock reads its owner: a process on this machine that no longer exists left it behind, and the contender removes it once and retries; removal renames the file to a unique name first (atomic, so only one contender takes it) and checks it took the device/inode it inspected, linking back a newer lock it took by mistake, so two contenders that judged the same dead lock never delete each other's fresh one; a lock from another machine, or one without an owner record, is removed only when it is older than five minutes, longer than any writer stays inside one. A lock whose owner is alive, or too young to attribute, is waited on and reported busy.

Recovery therefore needs no operator: a crashed desktop backend or a killed server leaves a lock that the next reader reclaims, and a retained `running` mutation is then reconciled from provider reads and never performed again; an unproved outcome remains sticky `outcome-unknown`. The risk that remains is a lock removed while its owner is alive on another machine sharing the data root over a network filesystem for longer than five minutes, which the age bound accepts in exchange for a store that never needs hand cleanup.

Snapshot writes use unique same-directory temporary files, mode `0600` before rename, and atomic rename. They do **not** fsync the temporary file or parent directory. Persistence here supports process-restart recovery, not a power-loss durability guarantee. A failed pre-rename write leaves the previous snapshot intact and cleans the temporary file when filesystem access permits. A hard crash may leave both a temporary file and a lock. Mutation completion-lock errors retain their actionable status and warn that the outcome could not be recorded; retry only with the same idempotency key for reconciliation, never a new key. Existing terminal retention and capacity eviction still bound how long resolved keys replay.

## Repository binding routes

- `GET /api/source-control/repository-context?directory=...` returns canonical repository identity, config revision, and redacted remotes.
- `GET /api/source-control/binding?directory=...` returns the authoritative binding and its revision with `Cache-Control: no-store`. Managed remote grants keep their opaque reference internally and receive a response-only `presentation`. Revision-pinned HTTPS references resolve to provider, normalized instance, OAuth/PAT source, provider username and provider-user identity only when the exact valid credential revision still exists. Managed SSH references resolve through the exact inventory record and expose only its freshly verified public fingerprint. Missing, stale, malformed or failed credential lookups produce `{ status: 'unavailable' }` without changing grant readiness or dropping sibling grants. The projection deduplicates references and resolves at most 256 grants in batches of eight during the one binding request. System and anonymous grants are unchanged.
- Generic whole-binding `PUT` and `DELETE` routes are not registered. The internal whole-binding replacement requires exact `expectedRepositoryId`, `expectedRevision`, and `expectedConfigRevision`, re-resolves topology before compare-and-swap, and rejects unknown/client endpoint fields. `POST /api/source-control/binding/reset` is the only full-reset contract. It requires that same repository, revision, and config authority plus literal `confirmed: true`, re-resolves topology, and writes a revision tombstone. It removes only binding references; provider credentials, managed SSH records, Git remotes and configuration, the worktree, and author identity are unchanged.
- `POST /api/source-control/binding/transport` configures one remote through `GitAPI.configureTransportBinding`. It requires the authoritative `expectedRepositoryId`, `expectedRevision`, `expectedConfigRevision`, `expectedFetchFingerprint`, and `expectedPushFingerprint`, plus explicit remote and transport selections. System requires `unverifiedConfirmed: true`. Managed HTTPS requires a separate `credentialAccount` containing provider, normalized instance, and exact credential account ID. The runtime validates both authoritative HTTPS endpoints against the account instance, reads that exact valid persisted credential without active-account or CLI fallback, and saves an `ocgit:v2` reference with its current credential revision and provider-user ID. Reauthentication creates a new credential ID, so an existing grant cannot silently move to replacement secret material. Managed SSH instead requires an existing opaque `sshCredentialId`, verifies it through the connected server's managed inventory, and requires both authoritative endpoints to use SSH. Generic client-supplied credential references, tokens, key paths, and endpoint URLs are rejected. The [Git module](../git/DOCUMENTATION.md#exact-ref-transport-authority) owns inventory capability and host setup.
- `POST /api/source-control/binding/transport/remove` removes only one committed remote grant. The intent pins repository ID, binding and config revisions, remote name, and exact fetch and push fingerprints. Configure and remove both re-resolve the repository and require the selected remote plus both endpoints to still exist before one CAS. Provider associations, auxiliary grants, sibling remote grants, credentials, and Git state are preserved. Missing or changed authority is a stale conflict, not an idempotent success.
- After transport configure, remote removal, or confirmed reset commits, the server writes the repository's `.git/config` credential helper and SSH command so shell Git follows the grant. If that write fails the route answers `500` with code `SOURCE_CONTROL_TRANSPORT_CONFIG_PARTIAL` and `committed: true`: the binding changed, shell Git still uses the previous credentials, and the client must reload the binding instead of reporting success.
- `POST /api/source-control/binding/auxiliary` configures or removes one exact kind-plus-endpoint grant through `GitAPI.configureAuxiliaryBinding`. The request pins repository, binding, config, parent remote, parent endpoint fingerprint, repository-relative discovered path, and discovered endpoint fingerprint. The service resolves the parent through its ready fetch grant, re-inspects committed checkout data to recover the raw endpoint, validates the selected HTTPS account or managed SSH key, then requires the repository, config, parent remote, parent fetch endpoint, and discovered endpoint to still exist and match before one CAS. It replaces or removes only the exact auxiliary record and preserves every sibling. System requires fresh per-grant confirmation. Anonymous is credential-free and HTTPS-only. Clients cannot submit a raw auxiliary URL or credential reference.

Narrow provider and transport routes apply the same response-only projection after persistence, so committed mutation results can update the summary without a client refetch. Projection failure cannot fail or roll back the completed mutation; it produces unavailable presentation for only the affected grants. Mutation input, planning and stored records remain unchanged.

Revision conflicts return `409` with the current authoritative record. Missing or unsupported repositories fail explicitly; they never fall back to a path-scoped or project-scoped binding. Raw remote URLs and Git common-directory paths remain server-internal.

Shared UI runtimes read through `SourceControlAPI.repositoryBinding` and mutate through narrow provider, transport, remote-removal, auxiliary, and confirmed-reset intents. No shared generic whole-binding set/delete API exists. Web, Electron, hosted mobile, and Capacitor mobile execute narrow mutations on the OpenChamber server. VS Code persists no bindings: its webview projects repository remotes as a ready System-transport binding read and exposes no binding mutations.

The optional presentation field gives runtime parity without weakening native boundaries. Web, Electron, hosted mobile and Capacitor receive server-projected metadata. VS Code never returns managed grants, so it never carries a presentation. Shared UI treats omission as unavailable and never turns the opaque grant reference into a label.

## Account and binding UI

Git Settings lists provider accounts independently; the legacy active-account field is not selection authority. OAuth, PAT, and CLI credentials with the same provider, normalized instance, and provider user ID share one visual account group, but retain separate credential IDs, validity, and actions. Account pickers offer one option per provider user — the current credential — labelled by provider, user and instance; the credential's own opaque reference is never a label. Removal requires the exact immutable credential account ID from client contract through provider route. Omission returns `400` and never removes the current account. Reconciliation moves only bindings for that exact credential to `needs-attention`. Ambient `/me` routes are retired with `410`; auth status and token-free account inventory own account presentation. The active repository's account and transport controls live in the Git panel rather than global Settings or Settings search. A missing binding may be suggested from its remotes and valid accounts, but persistence requires user confirmation. Confirming a provider account does not create a System or managed Git transport grant; until the user selects transport for a remote, network operations for that remote fail before planning while local Git operations remain available. Runtime or directory changes invalidate in-flight binding reads so a late response cannot replace the current repository's state.

Git operation surfaces show one thing per repository: the identity it works as. The Git panel button and the add/clone screens name that identity, and choosing another applies its provider association, transport grant, and author together through the same exact-target CAS mutations described below; the display is derived from the committed binding read and the repository author, never from the choice itself. The OpenChamber server remains the executor and enforces the authoritative binding on every read, mutation, and Git execution.

An identity is specific to an instance and to a way of reaching it. One tied to an account on `private.gitlab.example` cannot be chosen for a repository on `gitlab.com`; an account or anonymous identity needs an HTTPS remote and an SSH-key identity an SSH remote. Such identities stay visible but disabled with the reason. The System identity — the person's own Git configuration and credentials on the connected host — is always available and is what a repository uses until another identity is chosen; choosing it asks nothing. Choosing it removes the provider association and the repository-local author instead of copying global values into the repository. There is no separate transport editor or reset; the repository dialog holds the other addresses and checkout repair, and choosing the System identity is how a repository starts over.

A remote with no record of its own follows the repository's identity: `binding-service.js` derives its grant from the identity's remote grant (the provider association's primary remote, else `origin`, else the first ready grant). A System grant reaches every remote; a managed or anonymous grant reaches remotes whose fetch and push endpoints share its protocol, host and port, with the same credential reference. `validateGitTransportContext` uses the derived grant when no record names the remote, and `get`/`present` add it to the read with `inherited: true`, which only the response contract accepts; mutations read the stored binding and never persist a derived grant. A remote's own record, ready or not, always wins. The terminal credential helper reads the presented binding, so shell Git follows derived grants too.

Transport configuration replaces only the selected remote record, and explicit transport removal deletes only that selected remote record. Both preserve sibling endpoints, provider associations and auxiliary grants, including their unresolved readiness. A stale sibling no longer prevents an independent repair. Provider add/replace/remove changes only the selected association, never transport grants or their saved endpoints. Account repair on the same primary remote retains its approved provider endpoint and clears only that association's health; it cannot grant a changed destination. Replacing that destination requires removing and adding that association or selecting a different primary remote. A legacy association with no endpoint proof receives its first endpoint only on explicit confirmation. Identity and topology are re-read before each write, and the original CAS revision guards it. Failure leaves the previous binding intact; reload never retries a mutation automatically.

Provider writes (`validateMutationContext`) require the provider association ready on its approved endpoint and no remote transport grant `config-changed` (moved or gone). A remote added beside the bound ones, such as an upstream or a fork a change request was checked out from, grants nothing and does not block a write, the same drift reads already tolerate; the binding's aggregate `state` still reports it as `needs-attention`.

Known v1 snapshots convert without consulting paths or current Git configuration. Provider records have no independently approved endpoint, so they retain their references with a null endpoint and `confirmation-required`. Every v1 System remote or auxiliary grant also becomes `confirmation-required`, because v1 cannot prove explicit consent. Managed remote and auxiliary grants retain their exact saved endpoints and credential references. Conversion increments each live binding's CAS revision once and preserves tombstone revisions. The strict parser rejects malformed records, unknown fields and unknown versions before writing. A failed conversion write leaves the original file intact. A legacy public config revision never becomes authority merely because the repository still occupies the same path.

Reads project endpoint drift onto only the affected provider or remote while retaining the approved fingerprints. Provider API validation rejects a public config-revision mismatch as stale even when the selected provider endpoint still matches. Provider validation uses its own approved fetch endpoint; transport validation uses its own remote grant plus current request config revision and private transport revision. Unrelated provider repair cannot renew transport readiness or sibling capability grants.

Web contributor destination listing also checks the selected remote's readiness and exact endpoint fingerprints rather than aggregate binding health. Healthy transports remain usable when an independent provider requires repair. Contributor destinations still require managed credentials and a one-use exact selection, including when the selected destination is the contributor fork itself.

## Git transport authority

Current version-2 bindings also accept a tagged `mode: 'anonymous'` remote or auxiliary grant without a `credentialId`. The strict parser rejects credentials, System confirmation and unknown fields on persisted anonymous records. Version-1 conversion and existing managed/System version-2 records retain their behavior. Anonymous remote setup requires an authoritative HTTPS fetch endpoint and the same repository, revision and fetch/push fingerprint checks as other transport setup. It performs no account lookup, and replaces only the selected remote. Push authority is always rejected for that grant, even when its saved push endpoint is HTTPS. Anonymous auxiliary grants authorize only the exact HTTPS endpoint under the credential-free read environment described under [anonymous reads](../git/DOCUMENTATION.md#anonymous-reads).

Source control owns repository-to-provider and repository-to-remote authority. `binding-service.js` resolves the current repository identity, binding revision, public config revision, private transport revision, primary remote, raw fetch and push endpoints, transport mode, and opaque credential reference. Git network planning records the transport revision only in its process-local internal plan and records only redacted endpoint metadata publicly. Execution revalidates the same authority immediately before transfer. Atomic sync validates its named fetch and push remotes independently, so they may use different endpoints, modes, and credentials. A stale repository, binding, config revision, transport revision, remote, endpoint fingerprint, transport mode, or credential reference stops that transfer before spawn; the operation retains completed earlier sync steps in its result.

`validateGitAuxiliaryContext` is server-internal. The checkout planner and executor supply the raw submodule or LFS endpoint discovered from the selected commit; HTTP clients cannot call this contract or provide an authoritative discovered URL. The service recomputes its redacted display and fingerprint, requires an exact kind-plus-endpoint auxiliary record, and returns the exact transport mode, private transport revision, and optional opaque credential reference attached to that record. Same-host paths do not inherit a parent grant. Missing, stale, mismatched, or cross-endpoint grants fail before credential resolution or spawn.

Contributor worktree creation submits only exact read context, target project identity, change-request number, expected head SHA, and a requested local remote name. The provider adapter revalidates that authority and resolves the current head repository, ref, SHA, HTTPS endpoint, and same-repository/contributor classification. The Git runtime re-resolves the source before managed transfer and rejects changed authority before fetch.

Contributor-fork provenance adds a separate worktree-scoped authority check. It never turns the PR-head fetch remote into a push destination implicitly. System transport is forbidden for contributor transfers, and managed push planning requires a one-use exact destination selection issued against the current repository binding and provenance revision. The contributor source may appear as an explicit chooser candidate when the current binding independently grants managed push authority for that exact endpoint. Candidate ownership labels come from provenance plus current provider/account binding authority, never from a remote name.

Provider account references authorize provider API calls. Git credential references authorize Git transport. Commit identity references configure local authorship. They are not interchangeable, and none is a raw token, password, key, URL, or filesystem path. Credential resolvers may dereference an opaque credential ID only inside the server process and only for the endpoint authorized by the current binding. `ocgit:v1` HTTPS references remain readable for migrated bindings, but every explicit managed HTTPS save writes a revision-pinned `ocgit:v2` reference.

Raw Git endpoints stay behind the source-control and Git execution boundary. Existing-repository operations accept a remote name plus redacted display URL and fingerprint from the authoritative binding response; they never trust a client-provided fetch or push URL. HTTP/HTTPS display forms contain no userinfo, query, or fragment. SSH URL forms may retain a non-secret username but no password, query, or fragment; strict SCP forms remain valid. The network service rejects unsafe authoritative URLs before plan registration or argv construction, then passes only a validated server-resolved endpoint to Git after revalidation. Clone is the explicit parent-endpoint exception because a new checkout has no repository identity or binding. Its auxiliary grants still contain no raw discovered child or LFS URL. The Git module owns its protocol allowlist, keeps endpoints out of public operation state, and redacts failures.

`bindClonedRepository` is an executor-only callback, not an HTTP mutation. It compares the published checkout's actual fetch and push endpoints with the executor's captured approved endpoint, then creates revision 1 with the exact selected remote transport and only auxiliary grants matched to endpoints and kinds discovered during execution. It does not infer provider or author associations. The legacy `/api/fs/clone` requires explicit System confirmation for the parent and every System auxiliary grant, or returns `GIT_NETWORK_OPERATION_REQUIRED`. See `../git/DOCUMENTATION.md` for the canonical clone selection, retained-checkout partial results, cleanup, and runtime contracts.

Provider-neutral issue, upstream, branch, change-request status, list, and detailed context reads carry the repository ID, binding revision, provider instance, immutable account ID, and primary remote returned by this binding read. Before provider credential or cache lookup, repository resolution, or a provider call, the server resolves the directory again and rejects a missing binding, a non-ready selected association, a changed approved provider endpoint or config revision, a stale revision, and any repository, provider, instance, account, or primary-remote mismatch. A sibling association or transport needing attention does not block this provider. List and upstream resolution start from the trusted primary remote. Explicit issue, branch, and change-request repository selectors remain inside that repository's fork network, and a fork-network resolution failure is an error rather than an authoritative empty result. Repository coordinates and URLs remain server-resolved. Provider-returned clone URLs must match the resolved provider origin and project coordinates before they enter a worktree request. Retired `/api/github` resource aliases return `SOURCE_CONTROL_CONTEXT_REQUIRED` instead of entering this contract with ambient authority.

PR walkthrough reads, generation, progress, and cancellation use this same validation before entering the walkthrough service. They currently reject validated non-GitHub bindings. GitHub diff reads use the exact bound account and trusted primary remote; an exact-account `401` follows normal account reconciliation, while `403` and network failures do not invalidate the account. The validated tuple scopes every PR walkthrough job, cache entry, pointer, previous-result lookup, cancellation, progress stage, and returned result. Legacy unscoped walkthrough pointers and cache entries are not fallback data for these reads.

Multi-repository issue and change-request lists report failed repository scopes separately from complete results. A failed repository does not erase successful siblings, and clients retain the previous result only for explicitly incomplete project IDs. If every repository fails, the canonical read fails instead of returning authoritative empty data. Canonical search endpoint failures also fail the read; if search succeeds but every matched item fails provider enrichment, the read fails rather than publishing an empty result.

Provider auth modules report exact account invalidation and removal to the binding service before changing auth storage. The binding store scans by provider, normalized instance, and immutable account ID in one serialized write. Matching provider associations become `account-unavailable`; managed HTTPS remote and auxiliary grants whose parsed opaque reference names that exact account become `confirmation-required`. Credential references remain stored for explicit repair, but no affected provider or transport capability remains ready. Sibling accounts, managed SSH grants, opaque malformed references, unrelated providers, and tombstones remain intact. Each affected binding receives one new CAS revision, and repeating reconciliation after every exact match is already unavailable is a no-op. Provider caches and mutation/audit contexts keep the overall binding revision; an old context is rejected before cache lookup and must reload through the shared binding owner rather than retrying with guessed authority.

The reverse happens when an account connects (and once at server start for every valid account): `adoptAccount` moves managed HTTPS grants that are `confirmation-required` and whose reference names the same provider user on the same instance but another credential, to the connected account, rebuilt with its credential and revision and `ready` again; provider associations marked `account-unavailable` whose account those grants named move with them. This is what keeps a repository working after its user signs in again as a new credential (an OAuth renewal, a removed and re-added account). Grants of other users and bindings to live accounts are never touched; repeating it is a no-op.

GitLab implements projects, issues, merge requests, draft/ready transitions, merge/squash, and CI through GitBeaker. Its capabilities advertise only those operations; rebase merge is intentionally absent. GitLab has no draft parameter on merge-request create or edit, so a draft create prefixes the title with `Draft:` and ready removes the GitLab-recognized prefix (`Draft:`, `[Draft]`, `(Draft)`) from the current title; ready on a non-draft merge request returns applied without an edit call.

Shared issue and change-request pickers consume provider-neutral list methods. These lists return open items only; historical closed or merged records remain available through status and direct context lookup, not picker pagination.
