# Source control module

## Purpose

This module owns source-control provider registration and server-side repository bindings. Shared clients call `/api/source-control/{provider}` routes, the provider registry selects the provider's implementation, the route shell owns the HTTP surface, and each provider owns its authentication and resource behavior.

Repository bindings intentionally keep provider accounts, parent Git transport credentials, auxiliary checkout credentials, and commit identities separate. Managed remote and auxiliary bindings require endpoint-specific opaque `credentialId` values; system bindings reject that field in both input and persisted state. New managed HTTPS grants use `ocgit:v2` references that pin the immutable credential ID and revision and retain the separate provider-user ID for actor and audit attribution. Auxiliary records identify `submodule` or `lfs` plus exact redacted endpoint metadata. Bindings contain references and redacted endpoint metadata only; provider tokens remain in their provider auth stores. The Git network operation service, not provider routes or clients, owns transport execution.

## Registration

- `provider-id.js` defines the open provider id (`^[a-z][a-z0-9-]{0,31}$`) and the ids no registry may take (`guest`, `link`, `external`, `repository`). `provider-descriptors.js` lists the built-in descriptors in priority order (GitHub, GitLab, Gitea, then Gerrit); each provider's `descriptor.js` is static and SDK-free: instance form, `normalize` and `origin`, capabilities, auth methods, Git transport policy, limits, settings fields and the client presentation. `provider-instance.js` normalizes an instance through its descriptor and refuses an unknown id. `provider-contract.d.ts` types the descriptor, the implementation and the published descriptor.
- Extension providers take the id `ext-<guestId>` (`extensionProviderId`; a guest id longer than 28 characters cannot take the role). Built-in descriptor lists and the tracker registry refuse every id with the `ext-` prefix. The descriptor facade holds them in an extension segment (`attachExtension` / `detachExtension`): `list()` is the built-ins in priority order, then extensions sorted by id, so every reader of `sourceControlProviderDescriptors` sees them without change and a built-in wins where both could answer. `extension-descriptor.js` (`buildExtensionDescriptor`) turns a manifest's `contributes.sourceControl` into a frozen descriptor and fixes what the host owns: PAT-only sign-in, origin instances (only the declared ones unless `custom`, loopback HTTP and ports only when declared, and never a host a built-in serves by default, `builtInDefaultHosts`: github.com and gitlab.com, refused as a declared default, which keeps the extension unregistered, and as an instance the user enters), review threads, uploads, stacks and the reference picker off, creation through `/pr/create` only (it never declares `createVia` or `branchHeads`), and `urls.thread.pattern` compiled from the URL templates with escaped literals and bounded placeholders. The change-based fields a manifest may declare (the `change` term, `reviewModel`, `revisions`, `submit`, `submitRequirements`) pass through only when declared, and the `basic` token scheme adds a `username` settings field, so a manifest without them builds the same descriptor as before. Its server-only `extension` block names the guest and the token header; `publicProviderDescriptor(descriptor, order, extension)` publishes `{ guestId, name, version }` only. Tests that attach to the singleton detach in `afterEach` (`provider-descriptors.test-support.js`).
- `pat-account-auth.js` is the account half of a PAT-only provider over its `section(id)`: status, accounts, connect (verify, then probe), activate, remove, exact-account resolution with the token in a module `WeakMap`, write-off of a refused token, instance and account listing, and Git transport's credential read. `standard-mutations.js` is the standard mutation table: route to persisted kind, normalization and digest fields. Gitea and every extension provider use both, so an extension's kinds and digests are the host's, never the extension's.
- Extension providers (the `source-control` role of `contributes.service.provides`): `extension-providers.js` keeps the registered set equal to the catalog's eligible guests (enabled, approved with an effective `service` grant, the role and a parsed `contributes.sourceControl`, an id that fits `ext-`). It reads the catalog itself on every run, runs one reconcile at a time, rebuilds a descriptor only when the guest's name, version or contribution changed, re-registers when its package root, service or grants changed, and broadcasts `openchamber:source-control-providers-changed` when the set changed. It runs at start, from the guest routes' `onGuestActivated` (approval, enable, install or replace, update) and `onGuestDeactivated` (pause, withdrawn approval, removal); removal also drops the provider's auth section. A catalog that cannot be read changes nothing, and one broken contribution leaves the others registered. A paused or unapproved extension keeps its accounts; its routes answer the catch-all's 404 and bindings naming it answer `422 SOURCE_CONTROL_PROVIDER_UNAVAILABLE`, with no fallback to another provider.
- `extension-provider.js` (`createExtensionProvider`) is an extension's `ProviderImplementation`. Every forwarded call first reads the guest's current catalog row (`currentGuest`, backed by the cached `listInstalledGuests`, which applies enterprise policy on every read) and takes `capabilityGrants` from it, never from the registration snapshot; a row that is no longer eligible (`isSourceControlProviderGuest`: paused, unapproved, its `service` grant refused by policy, or gone) is refused as `NO_SERVICE` before anything is sent, and a reconcile is started. `dispose()`, called by the registry on unregister, makes the provider refuse `setAccount`, `activate` and `markAccountInvalid` on its section, so a connect still waiting on the service cannot write an account back after removal dropped the section. Accounts are `pat-account-auth.js` over `section('ext-<guestId>')`, with `auth.verify` and `auth.probe` forwarded to the service; mutations are `standard-mutations.js`; Git transport reads the stored credential. Resource reads and the three mutation steps go to the service (`POST /source-control`, the SDK's wire 1, through `proxyGuestServiceRequest` with the SDK's per-method timeouts, its response cap and a 10-minute idle stop). Every answer is parsed with `sourceControlProviderSchemasV1`; one that does not parse is `502 MALFORMED_PROVIDER_RESPONSE`. The adapter also re-checks what it acts on: a mutation target must describe the validated context field by field (a non-create replay must equal the stored target, else `409 SOURCE_CONTROL_MUTATION_CONFLICT`), a change request status must name this provider and instance, and a change request source must name the expected project and head, be classified consistently, and point at the head project on the instance's origin over HTTPS (loopback HTTP only when the descriptor allows it). A failed call's `kind` (what `classifyFailure` answers) comes from the guest service error (`SERVICE_FAILED`, `NO_SERVICE`, `DISABLED`: temporarily unavailable; `REQUEST_FAILED`: unreachable; else provider error).
- `outbound-handles.js` mints a handle (32 random bytes) per forwarded call, bound to the guest, the provider, the instance origin, the call's token or none, the call's deadline and the forge methods it may send (`GET` only for every read, `auth.*`, `mutation.resolveTarget` and `mutation.reconcile`; every method for `mutation.perform` alone, so a write happens only where the executor keys and audits it; another method is refused with `403 METHOD_NOT_ALLOWED` before it is recorded); the adapter revokes it when the call ends and the registry revokes a guest's handles when it unregisters. `refusal(bearer)` answers the listener before it reads a body (unknown or expired handle), and `serve` is the `POST /source-control/outbound` route of the callback listener (`../guests/host-callback.js`): it parses the request with the SDK's `outboundRequest` schema, joins path and query on the bound origin (`joinGuestRequestUrl`), passes only the allowed request headers, adds the token as the extension declared (`authorization: Bearer|token <t>`, or `private-token`), does not follow redirects, stops at 20 s or the deadline, refuses an answer over 8 MB, and relays only the allowed response headers. Every request a handle carried is recorded as `{ method, status }` before it is sent; nothing here logs a handle, token, body or query.
- The adapter trusts only what the proxy recorded. A `401` the service reports writes the account off (through the shell's usual 401 handling) only when the forge answered 401 on that call's handle; otherwise it is a malformed answer. A failed mutation is `failed` only when the service was never reached or every non-GET request of the call got a 4xx (or none was sent); a malformed answer the adapter detects after the call (a foreign target, status or change request source) carries the call's record too. Any other failure is `outcome-unknown`, whatever status the service reports.
- Enterprise mode adds no key for the role: it needs the `service` grant, which enterprise mode already limits to allowlisted Git sources or local folders (`../guests/enterprise.js`), and the callback listener is loopback-only. The limit holds at runtime too: every call re-reads the guest's row, which carries the policy as it is now, so a policy turned on or narrowed after registration refuses the next call and withdraws the provider without a restart. What the user writes reaches the instance they signed in to, as with self-hosted GitLab and Gitea (the open question in `../gitea/DOCUMENTATION.md`); the outbound proxy is the one place a future policy would act.
- `provider-registry.js` (`createSourceControlProviders`) is created once per runtime by `opencode/feature-routes-runtime.js` over one auth store. It serves the descriptors synchronously, loads each implementation (`<provider>/provider.js`, `createProvider(hostServices)`) on first use, answers `readTransportCredential` for Git transport and bindings (a credential is valid only for the instance it was asked for: its provider-user id must start with `<instance>#`, checked by the provider and again by the credential resolver, the binding validators and the clone planner, so a credential id that exists on another host never mints or resolves a reference for this one), and carries the account events (`connected`, `invalidated`, `removed`) providers report; listeners run in order and are awaited, so bindings move before a provider changes its store. `registerExtension({ descriptor, guest })` attaches an extension's descriptor to the facade and builds its implementation (`extension-provider.js`) on first use with the runtime's `extensionServices` (outbound handles, the extension store path); `unregisterExtension(id)` detaches it, disposes and drops the implementation and revokes the guest's handles.
- `routes.js` registers, before the generic OpenCode proxy: the shell's routes for every provider (`provider-routes.js`), `GET /api/source-control/providers`, `GET /api/source-control/instances`, the binding routes, and last a catch-all that answers any other path under `/api/source-control/` with `404 SOURCE_CONTROL_PROVIDER_UNAVAILABLE`. Between the binding routes and the catch-all sits the shell's extension dispatcher: a request under `/api/source-control/ext-<id>/` goes to that extension's router when one is mounted, and falls through to the catch-all otherwise. `registerExtensionProvider` / `unregisterExtensionProvider` (on the object `registerSourceControlRoutes` returns) register an extension in the registry and mount its router together, and take both down together; registering also moves bindings left on an earlier credential of its accounts, as the start-up repair does for built-ins.
- `provider-routes.js` is the generic shell. For each provider it registers literal `/api/source-control/<id>/...` routes: capabilities, auth (status, accounts, device flow through `oauth-flow-registry.js`, token, activate, CLI switch, removal), bound reads (status, lists, context, issues, upstream, branches, labels, reviewers), the reference picker (`references`, `references/across`, `references/detail`, `references/status`, capability `referencePicker`), uploads, the mutation routes and the retired `/me`. A descriptor's `routeAliases` adds the provider's legacy aliases declaratively: its account routes and `/me` under another prefix, extra names for a route, and retired paths answering `410` (GitHub's `/api/github/*`). A request without `instance` names the descriptor's legacy instance, if it has one. It validates the read or mutation context through the binding service before any account lookup, resolves the exact bound account through the implementation, keeps one status cache per provider, maps errors (`401` writes off only the acting account after renewal, transient failures answer the last-known status, a `4xx` after dispatch is a definite failure and anything else `outcome-unknown`; a provider may classify and word its own mutation failures through `mutations.classifyError` / `presentError`, and an error carrying `sourceControlResponse` is answered as the provider chose) and drives the durable mutation executor. A provider's `mutations.afterSuccess` (GitHub drops its pull context and pull-list caches there) runs after the executor returns, best effort: the record is already durable, so a failure there never turns a landed write into `outcome-unknown`. A create whose result names the number it made gets that number in the receipt's target. A capability the descriptor turns off still gets its route and answers `501 SOURCE_CONTROL_CAPABILITY_UNSUPPORTED`; so does one the implementation lacks. It also returns the reads other modules make with an already validated context (`readChangeRequestPatch`/`File` for walkthroughs and the comparison view, `readLiveSummaries` for tracked items, `readChangeRequestHead`, `resolveChangeRequestSource`), dispatched by the context's provider; these provider-neutral names are the only ones `routes.js` returns. The first three resolve the account through the implementation (`auth.resolveAccount`); live summaries pass `orCurrent`, so a provider may read with the instance's current account when the named one no longer resolves (GitHub does, GitLab does not).
- `GET /api/source-control/providers` answers `{ providers }`: each descriptor's public fields in the shape the UI registry parses (`publicProviderDescriptor`, with `order` from registry priority). No function, pattern or transport policy leaves the server. The web adapter's fallback for a server without this route is GitHub and GitLab only, because a server old enough to lack the route serves exactly those two; a test holds the fallback equal to the leading entries of the published list.
- Gitea (`../gitea/`) is the third built-in provider and the template for further in-core ones: one module folder with `descriptor.js` and `provider.js`, one entry in the descriptor list and one in the loader map, and no UI code (its icon is a path in the descriptor). It signs in with personal access tokens only, keeps its accounts in `section('gitea')` of the auth store (so a file holding a Gitea account is written as version 4), has no default instance, and turns off review threads, uploads, stacks and the reference picker, so those routes answer 501. What was verified against live Gitea 1.21 and 1.27, and what is still unverified, is listed in `../gitea/DOCUMENTATION.md`.
- GitHub, GitLab, Gitea and Gerrit all answer at `/api/source-control/<id>/*` with the same neutral DTOs. GitHub's descriptor keeps its auth and user aliases under `/api/github/*`; its retired PR, repository, issue, and pull-context aliases return `410` before authority or provider work.
- `GET /api/source-control/instances` returns, per provider in registry order, its default instances plus the ones its implementation knows: self-managed GitLab origins, Gitea origins and GitHub Enterprise hosts already present in the server credential store (a host the user registered a PAT for, or one gh has a stored login for). It never exposes accounts or tokens. A provider that fails to load or list is named in `unavailableProviders` instead of failing the whole answer, so one broken provider never hides the others' instances.
- `repository-identity.js` derives a repository ID from the real Git common directory and its filesystem identity. A checkout, linked worktree, and symlink share one ID; a moved or path-replaced repository resolves to a different ID. Its public config revision hashes a versioned canonical repository ID and sorted normalized effective fetch/push topology. Author, signing, and upstream-only edits do not invalidate that revision. Private transport identity separately hashes Git's effective transport-relevant configuration across system, global, local, worktree, and included files. Only that hash reaches transport validation; values and origin paths stay inside the Git query process.
- `binding-storage.js` owns version-2 `source-control-bindings.json` persistence under `OPENCHAMBER_DATA_DIR`. Reads and writes share one store-local queue and a cross-process snapshot lock that covers the entire read/check/write, including account reconciliation. A missing file reads as an empty version-2 store. A file carrying any other version, or one that fails the strict parse, is rejected with `INVALID_SOURCE_CONTROL_BINDINGS` and left on disk untouched: the store never converts, repairs or replaces it, and bindings do not silently start empty. Writes are atomic, mode `0600`, and compare-and-swap by repository revision. Deletes retain revision tombstones so stale requests cannot recreate a binding.
- `binding-contract.js` owns the dependency-free strict persisted binding parser, separate binding-response parser, readiness projection, aggregate state, and public endpoint validation for the server and the web adapter. The persisted parser rejects response-only credential presentation, so `source-control-bindings.json` remains references-only. The response parser accepts only the tagged safe presentation contract and rejects unknown fields. Safe endpoint metadata accepts credential-free HTTP/HTTPS, SSH URL, and SCP display forms plus bounded base64url fingerprints; local-file, credential-bearing HTTPS, query, fragment, traversal, control-character, and unsafe fingerprint forms fail closed. Each provider stores its approved fetch endpoint and readiness. Each remote stores readiness alongside its exact fetch/push endpoints; auxiliary grants have their own readiness. Only `ready` grants authority. `account-unavailable`, `confirmation-required`, and `config-changed` retain repair metadata without granting the affected capability. Binding `state` is an aggregate UI summary, never the authority gate.
- `mutation-storage.js` owns strict versioned persistence for bounded source-control mutation records in `source-control-mutations.json` under the server config root. `claim` persists an idempotency key before provider work, exact key-and-digest replays return the stored record, and digest changes report a conflict. `complete` permits one transition from `running` to a terminal state. Failed records may retain only an HTTP status and stable code for replay; messages and provider payloads are rejected. Terminal records have a seven-day retention by default and may be evicted oldest-first at capacity; `running` and `outcome-unknown` records are never pruned or evicted. Snapshots use serialized atomic mode-`0600` writes and reject unknown fields, provider payloads, private text, tokens, and raw URLs.
- `mutation-executor.js` canonicalizes and hashes mutation input, joins exact process-local duplicates, claims persisted state before provider work, and never retries a provider mutation. Provider routes include the exact resolved credential account ID and revision in this digest and keep the credential account ID in durable replay authority. They pass the verified provider-user ID separately for receipt actor metadata and audit `providerAccountId`; clients cannot supply it. Its store must provide `withExecutionLock(key, operation)`, scoped to that store's file path and the SHA-256 digest of the key, not the input digest. The executor holds this separate lock from before claim through provider work or reconciliation and mutation/audit completion. A second daemon waits or fails busy, never reconciles live work. Completed requests replay their compact receipt after acquiring the lock. An unlocked persisted `running` record enters provider reconciliation; a crashed owner's leftover lock is reclaimed by the next contender (see below). Ambiguous provider outcomes become sticky `outcome-unknown` records when persistence remains available. A failed completion write leaves the prior snapshot available for reconciliation, never another provider write.
- `audit-storage.js` owns the separate version-1 `source-control-audit.json` log under `OPENCHAMBER_DATA_DIR`. It does not share records, retention, or write sequencing with mutation replay storage. The strict schema stores one logical record per provider mutation idempotency key and per server Git operation ID. It accepts only `user` as the current initiator, the `provider-api` or `openchamber-server-git` executor, an immutable runtime and repository snapshot, an authoritative provider-user account ID or `null`, authoritative transport metadata, a compact redacted target, lifecycle timestamps, and a result state, stable error code, and bounded steps. An opaque credential ID is never substituted for provider identity. Provider API records require a `null` transport reference and a change-request target, or an issue target for `issue-comment`. Single-path Git records require either an exact opaque managed `credentialId` or a system marker. Sync records keep exact fetch and push references separately, including mixed system and managed transport. Checkout hydration records a bounded list of discovered auxiliary kinds and endpoint fingerprints plus only the exact server-validated transport reference for each granted endpoint; it records `null` transport when no transfer grant is used and always records a `null` provider account. Existing hydration records with the former single parent transport remain readable but new records never write that attribution. The schema rejects unknown fields and URL-shaped transport or target values, so raw endpoints, hydration paths, directories, key paths, credential payloads, process output, provider payloads, and free-form errors cannot enter the file. GitLab account IDs retain their authoritative normalized-instance prefix because that prefix is part of the account identifier, not a transport endpoint. Writes are serialized, atomic, and mode `0600`. Resolved terminal records expire after 30 days by default and are oldest-first capacity candidates; `planned`, `running`, and `outcome-unknown` records are never pruned or evicted.
- `mutation-executor.js` also drives provider audit lifecycle around the existing durable claim. Exact in-process duplicates and durable replays use `provider:<idempotencyKey>` and therefore reuse the same audit record, while `transportReference` remains `null` because provider API calls do not use Git transport. The executor rejects an audited execution before claim when the route omits verified provider identity. Two credentials for the same provider user therefore share actor identity in receipts and audits, but their exact credential and binding authority still produce different mutation digests. Audit persistence does not replace or relax mutation claim, digest conflict, reconciliation, sticky unknown-outcome, or replay behavior.
- OAuth renewal goes through the provider that issued the token: the runtime hands the auth store a `refreshOAuthToken` that calls the implementation's `auth.refreshOAuthToken` (GitLab's today); a provider without one has no renewable tokens.
- `auth-storage.js` owns the versioned `source-control-auth.json` server token store under `OPENCHAMBER_DATA_DIR`, shared by GitLab (instances keyed by origin), GitHub Enterprise (hosts in `providers.github`, each with its own personal access tokens and gh CLI switch) and one origin-keyed section per further provider (`section(id)`, the GitLab shape; GitLab's own section is also the store's top-level surface; `dropSection(id)` forgets an extension provider's whole section in one locked write and refuses any other id); github.com's device-flow accounts stay in `github-auth.json`. Credential ids are `occred:v1:<provider>:<uuid>:r1` and provider-user ids `<instance>#<user id>`. Version 2 (GitLab only) and version 3 (plus `github`) read as before; version 4 is version 3 plus extra sections keyed by any syntactically valid provider id. An extra section is kept as read, an opaque object, until a provider of this build asks for it through `section(id)`, which parses it strictly then; a section no provider asks for is written back untouched whatever its shape (a newer build's host-keyed provider, an unknown credential field), and a section that does not parse fails only its own provider's calls, never GitLab's, GitHub's or another section's. The serializer writes the oldest version that holds the state: 2 while only GitLab holds anything, 3 once an enterprise host is stored, 4 only while an extra section is not empty, so a user who never added such a provider can still go back to an older release (one who did meets the same fail-closed version check as the v2→v3 step). `source-control-mutations.json` has the same kind of constraint: after a mutation on a path-style provider's top-level project (`repositoryPath: 'path'`, Gerrit's `demo`), the file holds a project with an empty owner, and a build older than top-level projects refuses the whole file. Tracked items are different: an older build's `parseThread` (`../tracked-items/items.js`) drops an item of a top-level project rather than refusing the store, so the item disappears there and the rest of the list stays. An unknown version or a shape the version forbids fails closed and is not replaced. OAuth renewal receives `{ provider, origin, refreshToken }`. Writes are serialized, atomic, and mode `0600`, and GitLab OAuth tokens are renewed before they lapse, once per credential across processes, so a refresh token is never spent twice.

Provider replay and reconciliation after restart reuse the runtime snapshot from the existing audit record. Strict audit planning still checks the other immutable fields. Terminal replay does not rewrite audit history. An unfinished audit can complete from the durable mutation receipt without repeating provider work.
- `binding-service.js` accepts remote names and account/credential references, normalizes provider instances before uniqueness checks and persistence, then resolves endpoint metadata and provider repository coordinates from current server-side Git state. A provider instance must match the selected remote host and applicable HTTP port; supplied repository coordinates must equal the path-derived coordinates. Client-provided URLs are never authoritative. Provider reads check the binding revision, the bound provider's own readiness and that its primary remote still exists, so a remote added or removed beside it does not interrupt change-request status. A repository with no binding (revision 0) or whose binding names no account for a host is read with the account the client is signed in to on that host, as before bindings existed: the context must name a remote that really points at the instance, and whether the account exists is the provider route's to decide. Mutation contexts pass the same checks plus the binding's saved config revision, then validate an idempotency key and an exact, copied target shape before provider code receives them. Stale revision or config/remote errors carry the current authoritative repository, revision, and redacted binding record. Account reconciliation uses the same normalization and also matches equivalent instance spellings in previously stored records.
- `url-redaction.js` removes URL credentials, query data, and fragments from endpoint display URLs before repository context crosses the server boundary. Endpoint fingerprints remain derived from normalized transport authority rather than the shortened display, so hidden query or fragment changes still change authority.
- `status-cache.js` keeps the last-known change request status per exact trusted read context (instance, account, credential revision, repository, binding revision, directory, branch, remote, and for a `createVia: 'push'` provider the local branch tip), bounded and TTL-fresh. A provider route answers a fresh repeat from it, answers a transient provider failure with the last-known status, drops a repository's entries after a mutation and an account's entries after invalidation. A push-create host's status is derived from the tip (its Change-Id, `localRevision`, `uploadedAs`), so the shell reads the tip with one `git rev-parse` per status read (`readBranchTip`) and a new or rewritten commit is a new entry. The Change-Id amend also drops that branch's entries in every provider's cache (`invalidateBranchStatus`, which `routes.js` returns for `git/routes.js`). The shell keeps one per provider, GitHub's included. A read that started before an invalidation answers its caller but stores nothing (`begin`/`store`), so a mutation's invalidation is never refilled by an older read.
- `change-request-worktree.js` builds a change-request source from a directory and a pull or merge request number alone, for `session.create` with `pullRequest`. It chooses the read context the way the client's `getBoundSourceControlReadContexts` and `useRepositoryReadContext` do: a ready bound provider first, else a remote on a host a registered provider owns (its `auth.ownsHost` over its default instances and `auth.listInstances`: github.com or a trusted enterprise host, a known GitLab, Gitea or Gerrit origin; an HTTP(S) remote's port must match an origin's, so two instances on one host stay apart, while an SSH remote names no web port and its host alone decides) read with that host's current account (each provider's `readCurrentAccountId`, the gh or glab login only while the user switched to it). Where several could answer, the earlier provider in registry order wins (GitHub, then GitLab, then Gitea). A provider that fails to load or list its instances is skipped with a warning, so it never blocks the others. The provider's `readChangeRequestHead` then answers the project, head branch, head revision and head owner on that context's primary remote; a GitHub pull request whose fork was deleted, or a number that is not one there, is refused with its own message. No caller-supplied project, endpoint or remote name enters the result, and the Git contributor pipeline resolves it again before any transfer.
- `oauth-flow-registry.js` keeps device-flow secrets in a bounded, process-local registry. Clients receive an opaque flow ID; completion acquires the matching provider and normalized instance exclusively, then releases retryable attempts or consumes terminal attempts. Restarting the server invalidates every outstanding flow.

## Cross-process locks and recovery

`file-lock.js` owns the dependency-free exclusion contract for source-control and Git stores that import it. Every snapshot read and complete read/check/write transaction acquires `<json-file>.lock` using exclusive `wx` creation with mode `0600`. Local queues preserve call ordering; each filesystem acquisition waits at most two seconds by default before `SOURCE_CONTROL_LOCK_BUSY` with HTTP `503`. Other lock I/O or ownership failures return `SOURCE_CONTROL_LOCK_FAILED` with HTTP `500`. Neither failure is an empty store, a missing binding, or a disconnected provider. Errors name the lock basename and explain stopped-writer recovery without exposing the data-root path.

Provider execution uses `<mutation-json-file>.execution-<sha256-key>.lock`. Snapshot locks are brief and never span provider network calls. Different execution keys and different stores can progress while another provider request runs. These locks support multiple daemons sharing the same data root; there is no global backend lock. All writers must use this contract and the same file location on a filesystem that supports exclusive creation and atomic same-directory rename. Older unlocked writers, external file edits, and removal or replacement of the data directory while writers run are unsupported.

Each acquisition writes its owner — process ID, hostname, time and a nonce — and keeps its file handle open. Normal `finally` cleanup verifies the pathname still identifies that handle's device/inode before unlinking and closing. Failed initialization cleans only that acquisition's file identity. A contender that finds an existing lock reads its owner: a process on this machine that no longer exists left it behind, and the contender removes it once and retries; removal renames the file to a unique name first (atomic, so only one contender takes it) and checks it took the device/inode it inspected, linking back a newer lock it took by mistake, so two contenders that judged the same dead lock never delete each other's fresh one; a lock from another machine, or one without an owner record, is removed only when it is older than five minutes, longer than any writer stays inside one. A lock whose owner is alive, or too young to attribute, is waited on and reported busy.

Recovery therefore needs no operator: a crashed desktop backend or a killed server leaves a lock that the next reader reclaims, and a retained `running` mutation is then reconciled from provider reads and never performed again; an unproved outcome remains sticky `outcome-unknown`. The risk that remains is a lock removed while its owner is alive on another machine sharing the data root over a network filesystem for longer than five minutes, which the age bound accepts in exchange for a store that never needs hand cleanup.

Snapshot writes use unique same-directory temporary files, mode `0600` before rename, and atomic rename. They do **not** fsync the temporary file or parent directory. Persistence here supports process-restart recovery, not a power-loss durability guarantee. A failed pre-rename write leaves the previous snapshot intact and cleans the temporary file when filesystem access permits. A hard crash may leave both a temporary file and a lock. Mutation completion-lock errors retain their actionable status and warn that the outcome could not be recorded; retry only with the same idempotency key for reconciliation, never a new key. Existing terminal retention and capacity eviction still bound how long resolved keys replay.

## Repository binding routes

- `GET /api/source-control/repository-context?directory=...` returns canonical repository identity, config revision, and redacted remotes.
- `GET /api/source-control/binding?directory=...` returns the authoritative binding and its revision with `Cache-Control: no-store`. Managed remote grants keep their opaque reference internally and receive a response-only `presentation`. Revision-pinned HTTPS references resolve to provider, normalized instance, OAuth/PAT source, provider username and provider-user identity only when the exact valid credential revision still exists. Managed SSH references resolve through the exact inventory record and expose only its freshly verified public fingerprint. An HTTPS presentation's instance is HTTPS, or HTTP on a loopback host by the Git transport's rule (`isLoopbackHost`: localhost, 127.0.0.0/8, ::1), which `binding-contract.js` inlines because it is bundled into the web client; `binding-contract.test.js` holds the two equal. Missing, stale, malformed or failed credential lookups produce `{ status: 'unavailable' }` without changing grant readiness or dropping sibling grants. The projection deduplicates references and resolves at most 256 grants in batches of eight during the one binding request. System and anonymous grants are unchanged.
- Generic whole-binding `PUT` and `DELETE` routes are not registered. The internal whole-binding replacement requires exact `expectedRepositoryId`, `expectedRevision`, and `expectedConfigRevision`, re-resolves topology before compare-and-swap, and rejects unknown/client endpoint fields. `POST /api/source-control/binding/reset` is the only full-reset contract. It requires that same repository, revision, and config authority plus literal `confirmed: true`, re-resolves topology, and writes a revision tombstone. It removes only binding references; provider credentials, managed SSH records, Git remotes and configuration, the worktree, and author identity are unchanged.
- `POST /api/source-control/binding/transport` configures one remote through `GitAPI.configureTransportBinding`. It requires the authoritative `expectedRepositoryId`, `expectedRevision`, `expectedConfigRevision`, `expectedFetchFingerprint`, and `expectedPushFingerprint`, plus explicit remote and transport selections. System requires `unverifiedConfirmed: true`. Managed HTTPS requires a separate `credentialAccount` containing provider, normalized instance, and exact credential account ID. The runtime validates both authoritative HTTPS endpoints against the account instance, reads that exact valid persisted credential without active-account or CLI fallback, and saves an `ocgit:v2` reference with its current credential revision and provider-user ID. Reauthentication creates a new credential ID, so an existing grant cannot silently move to replacement secret material. Managed SSH instead requires an existing opaque `sshCredentialId`, verifies it through the connected server's managed inventory, and requires both authoritative endpoints to use SSH. Generic client-supplied credential references, tokens, key paths, and endpoint URLs are rejected. The [Git module](../git/DOCUMENTATION.md#exact-ref-transport-authority) owns inventory capability and host setup.
- `POST /api/source-control/binding/transport/remove` removes only one committed remote grant. The intent pins repository ID, binding and config revisions, remote name, and exact fetch and push fingerprints. Configure and remove both re-resolve the repository and require the selected remote plus both endpoints to still exist before one CAS. Provider associations, auxiliary grants, sibling remote grants, credentials, and Git state are preserved. Missing or changed authority is a stale conflict, not an idempotent success.
- After transport configure, remote removal, or confirmed reset commits, the server writes the repository's `.git/config` credential helper and SSH command so shell Git follows the grant. If that write fails the route answers `500` with code `SOURCE_CONTROL_TRANSPORT_CONFIG_PARTIAL` and `committed: true`: the binding changed, shell Git still uses the previous credentials, and the client must reload the binding instead of reporting success.
- `POST /api/source-control/binding/auxiliary` configures or removes one exact kind-plus-endpoint grant through `GitAPI.configureAuxiliaryBinding`. The request pins repository, binding, config, parent remote, parent endpoint fingerprint, repository-relative discovered path, and discovered endpoint fingerprint. The service resolves the parent through its ready fetch grant, re-inspects committed checkout data to recover the raw endpoint, validates the selected HTTPS account or managed SSH key, then requires the repository, config, parent remote, parent fetch endpoint, and discovered endpoint to still exist and match before one CAS. It replaces or removes only the exact auxiliary record and preserves every sibling. System requires fresh per-grant confirmation. Anonymous is credential-free and HTTPS-only. Clients cannot submit a raw auxiliary URL or credential reference.

Narrow provider and transport routes apply the same response-only projection after persistence, so committed mutation results can update the summary without a client refetch. Projection failure cannot fail or roll back the completed mutation; it produces unavailable presentation for only the affected grants. Mutation input, planning and stored records remain unchanged.

Revision conflicts return `409` with the current authoritative record. Missing or unsupported repositories fail explicitly; they never fall back to a path-scoped or project-scoped binding. Raw remote URLs and Git common-directory paths remain server-internal.

Shared UI runtimes read through `SourceControlAPI.repositoryBinding` and mutate through narrow provider, transport, remote-removal, auxiliary, and confirmed-reset intents. No shared generic whole-binding set/delete API exists. Web, Electron, hosted mobile, and Capacitor mobile execute narrow mutations on the OpenChamber server. VS Code persists no bindings: its webview projects repository remotes as a ready System-transport binding read and exposes no binding mutations.

The optional presentation field gives runtime parity without weakening native boundaries. Web, Electron, hosted mobile and Capacitor receive server-projected metadata. VS Code never returns managed grants, so it never carries a presentation. Shared UI treats omission as unavailable and never turns the opaque grant reference into a label.

## Account and binding UI

Git Settings lists provider accounts independently; the legacy active-account field is not selection authority. OAuth, PAT, and CLI credentials with the same provider, normalized instance, and provider user ID share one visual account group, but retain separate credential IDs, validity, and actions. Account pickers offer one option per provider user — the current credential — labelled by provider, user and instance; the credential's own opaque reference is never a label. Removal requires the exact immutable credential account ID from client contract through provider route. Omission returns `400` and never removes the current account. Reconciliation moves only bindings for that exact credential to `needs-attention`. Ambient `/me` routes are retired with `410`; auth status and token-free account inventory own account presentation. The active repository's account and transport controls live in the Git panel rather than global Settings or Settings search. A missing binding may be suggested from its remotes and valid accounts, but persistence requires user confirmation. Confirming a provider account does not create a System or managed Git transport grant; until the user selects transport for a remote, network operations for that remote fail before planning while local Git operations remain available. Runtime or directory changes invalidate in-flight binding reads so a late response cannot replace the current repository's state.

Git operation surfaces show one thing per repository: the identity it works as. The Git panel button and the add/clone screens name that identity, and choosing another applies its provider association, transport grant, and author together through the same exact-target CAS mutations described below; the display is derived from the committed binding read and the repository author, never from the choice itself. The OpenChamber server remains the executor and enforces the authoritative binding on every read, mutation, and Git execution.

An identity is specific to an instance and to a way of reaching it. One tied to an account on `private.gitlab.example` cannot be chosen for a repository on `gitlab.com`; an account or anonymous identity needs an HTTPS remote and an SSH-key identity an SSH remote. Such identities stay visible but disabled with the reason. The System identity — the person's own Git configuration and credentials on the connected host — is always available and is what a repository uses until another identity is chosen; choosing it asks nothing. Choosing it removes the provider association and the repository-local author instead of copying global values into the repository. There is no separate transport editor or reset; the repository dialog holds the other addresses and checkout repair, and choosing the System identity is how a repository starts over.

A remote with no record of its own follows the repository's identity: `binding-service.js` derives its grant from the identity's remote grant (the provider association's primary remote, else `origin`, else the first ready grant). A System grant reaches every remote; a managed or anonymous grant reaches remotes whose fetch and push endpoints share its protocol, host and port, with the same credential reference. `validateGitTransportContext` uses the derived grant when no record names the remote, and `get`/`present` add it to the read with `inherited: true`, which only the response contract accepts; mutations read the stored binding and never persist a derived grant. A remote's own record, ready or not, always wins. The terminal credential helper reads the presented binding, so shell Git follows derived grants too.

Transport configuration replaces only the selected remote record, and explicit transport removal deletes only that selected remote record. Both preserve sibling endpoints, provider associations and auxiliary grants, including their unresolved readiness. A stale sibling no longer prevents an independent repair. Provider add/replace/remove changes only the selected association, never transport grants or their saved endpoints. Account repair on the same primary remote retains its approved provider endpoint and clears only that association's health; it cannot grant a changed destination. Replacing that destination requires removing and adding that association or selecting a different primary remote. A legacy association with no endpoint proof receives its first endpoint only on explicit confirmation. Identity and topology are re-read before each write, and the original CAS revision guards it. Failure leaves the previous binding intact; reload never retries a mutation automatically.

Provider writes (`validateMutationContext`) require the provider association ready on its approved endpoint and no remote transport grant `config-changed` (moved or gone). A remote added beside the bound ones, such as an upstream or a fork a change request was checked out from, grants nothing and does not block a write, the same drift reads already tolerate. The binding's aggregate `state` follows the projected grant readiness, not the public config revision, so such a remote leaves it `bound`.

Known v1 snapshots convert without consulting paths or current Git configuration. Provider records have no independently approved endpoint, so they retain their references with a null endpoint and `confirmation-required`. Every v1 System remote or auxiliary grant also becomes `confirmation-required`, because v1 cannot prove explicit consent. Managed remote and auxiliary grants retain their exact saved endpoints and credential references. Conversion increments each live binding's CAS revision once and preserves tombstone revisions. The strict parser rejects malformed records, unknown fields and unknown versions before writing. A failed conversion write leaves the original file intact. A legacy public config revision never becomes authority merely because the repository still occupies the same path.

Reads project endpoint drift onto only the affected provider or remote while retaining the approved fingerprints. Provider API validation rejects a public config-revision mismatch as stale even when the selected provider endpoint still matches. Provider validation uses its own approved fetch endpoint; transport validation uses its own remote grant plus current request config revision and private transport revision. Unrelated provider repair cannot renew transport readiness or sibling capability grants.

Web contributor destination listing also checks the selected remote's readiness and exact endpoint fingerprints rather than aggregate binding health. Healthy transports remain usable when an independent provider requires repair. Contributor destinations still require managed credentials and a one-use exact selection, including when the selected destination is the contributor fork itself.

## Git transport authority

Current version-2 bindings also accept a tagged `mode: 'anonymous'` remote or auxiliary grant without a `credentialId`. The strict parser rejects credentials, System confirmation and unknown fields on persisted anonymous records. Version-1 conversion and existing managed/System version-2 records retain their behavior. Anonymous remote setup requires an authoritative HTTPS fetch endpoint and the same repository, revision and fetch/push fingerprint checks as other transport setup. It performs no account lookup, and replaces only the selected remote. Push authority is always rejected for that grant, even when its saved push endpoint is HTTPS. Anonymous auxiliary grants authorize only the exact HTTPS endpoint under the credential-free read environment described under [anonymous reads](../git/DOCUMENTATION.md#anonymous-reads).

Source control owns repository-to-provider and repository-to-remote authority. `binding-service.js` resolves the current repository identity, binding revision, public config revision, private transport revision, primary remote, raw fetch and push endpoints, transport mode, and opaque credential reference. Git network planning records the transport revision only in its process-local internal plan and records only redacted endpoint metadata publicly. Execution revalidates the same authority immediately before transfer. Atomic sync validates its named fetch and push remotes independently, so they may use different endpoints, modes, and credentials. A stale repository, binding, config revision, transport revision, remote, endpoint fingerprint, transport mode, or credential reference stops that transfer before spawn; the operation retains completed earlier sync steps in its result.

`validateGitAuxiliaryContext` is server-internal. The checkout planner and executor supply the raw submodule or LFS endpoint discovered from the selected commit; HTTP clients cannot call this contract or provide an authoritative discovered URL. The service recomputes its redacted display and fingerprint, requires an exact kind-plus-endpoint auxiliary record, and returns the exact transport mode, private transport revision, and optional opaque credential reference attached to that record. Same-host paths do not inherit a parent grant. Missing, stale, mismatched, or cross-endpoint grants fail before credential resolution or spawn.

Contributor worktree creation submits only exact read context, target project identity, change-request number, expected head SHA, and a requested local remote name. The provider adapter revalidates that authority and resolves the current head repository, ref, SHA, HTTPS endpoint, and same-repository/contributor classification. The Git runtime re-resolves the source before managed transfer and rejects changed authority before fetch.

Contributor-fork provenance adds a separate worktree-scoped authority check. It never turns the PR-head fetch remote into a push destination implicitly. System transport is forbidden for contributor transfers, and managed push planning requires a one-use exact destination selection issued against the current repository binding and provenance revision. The contributor source may appear as an explicit chooser candidate when the current binding independently grants managed push authority for that exact endpoint. Candidate ownership labels come from provenance plus current provider/account binding authority, never from a remote name.

Provider account references authorize provider API calls. Git credential references authorize Git transport. Commit identity references configure local authorship. They are not interchangeable, and none is a raw token, password, key, URL, or filesystem path. Credential resolvers may dereference an opaque credential ID only inside the server process and only for the endpoint authorized by the current binding. `ocgit:v1` HTTPS references remain readable for migrated bindings, but every explicit managed HTTPS save writes a revision-pinned `ocgit:v2` reference.

Raw Git endpoints stay behind the source-control and Git execution boundary. Existing-repository operations accept a remote name plus redacted display URL and fingerprint from the authoritative binding response; they never trust a client-provided fetch or push URL. HTTP/HTTPS display forms contain no userinfo, query, or fragment. SSH URL forms may retain a non-secret username but no password, query, or fragment; strict SCP forms remain valid. The network service rejects unsafe authoritative URLs before plan registration or argv construction, then passes only a validated server-resolved endpoint to Git after revalidation. Clone is the explicit parent-endpoint exception because a new checkout has no repository identity or binding. Its auxiliary grants still contain no raw discovered child or LFS URL. The Git module owns its protocol allowlist, keeps endpoints out of public operation state, and redacts failures.

`bindClonedRepository` is an executor-only callback, not an HTTP mutation. It compares the published checkout's actual fetch and push endpoints with the executor's captured approved endpoint, then creates revision 1 with the exact selected remote transport and only auxiliary grants matched to endpoints and kinds discovered during execution. It does not infer provider or author associations. The legacy `/api/fs/clone` requires explicit System confirmation for the parent and every System auxiliary grant, or returns `GIT_NETWORK_OPERATION_REQUIRED`. See `../git/DOCUMENTATION.md` for the canonical clone selection, retained-checkout partial results, cleanup, and runtime contracts.

Provider-neutral issue, upstream, branch, change-request status, list, and detailed context reads carry the repository ID, binding revision, provider instance, immutable account ID, and primary remote returned by this binding read. Before provider credential or cache lookup, repository resolution, or a provider call, the server resolves the directory again and rejects a missing binding, a non-ready selected association, a changed approved provider endpoint or config revision, a stale revision, and any repository, provider, instance, account, or primary-remote mismatch. A sibling association or transport needing attention does not block this provider. List and upstream resolution start from the trusted primary remote. Explicit issue, branch, and change-request repository selectors remain inside that repository's fork network, and a fork-network resolution failure is an error rather than an authoritative empty result. A change request is in reach when the repository it targets is in that network; the repository its head comes from is not checked, because the host serves a fork's head under the target repository and already authorises the token for the request. So a maintainer's upstream clone reads, comments on, reviews and merges a contributor's fork pull request on every host. `repository-network.js` (`changeRequestNetworkTarget`) is that rule, and GitHub, GitLab and Gitea call it (Gerrit has no forks, so it checks the one project the binding names); creating a change request is the other direction, where each provider still requires the head remote's repository to be in the network. Repository coordinates and URLs remain server-resolved. Provider-returned clone URLs must match the resolved provider origin and project coordinates before they enter a worktree request. Retired `/api/github` resource aliases return `SOURCE_CONTROL_CONTEXT_REQUIRED` instead of entering this contract with ambient authority.

PR walkthrough reads, generation, progress, and cancellation use this same validation before entering the walkthrough service. They serve providers whose descriptor has `capabilities.changeRequestPatch` and reject any other validated binding. Diff reads use the exact bound account and trusted primary remote; an exact-account `401` follows normal account reconciliation, while `403` and network failures do not invalidate the account. The validated tuple scopes every PR walkthrough job, cache entry, pointer, previous-result lookup, cancellation, progress stage, and returned result. Legacy unscoped walkthrough pointers and cache entries are not fallback data for these reads.

Multi-repository issue and change-request lists report failed repository scopes separately from complete results. A failed repository does not erase successful siblings, and clients retain the previous result only for explicitly incomplete project IDs. If every repository fails, the canonical read fails instead of returning authoritative empty data. Canonical search endpoint failures also fail the read; if search succeeds but every matched item fails provider enrichment, the read fails rather than publishing an empty result.

Provider auth modules report exact account invalidation and removal to the binding service before changing auth storage. The binding store scans by provider, normalized instance, and immutable account ID in one serialized write. Matching provider associations become `account-unavailable`; managed HTTPS remote and auxiliary grants whose parsed opaque reference names that exact account become `confirmation-required`. Credential references remain stored for explicit repair, but no affected provider or transport capability remains ready. Sibling accounts, managed SSH grants, opaque malformed references, unrelated providers, and tombstones remain intact. Each affected binding receives one new CAS revision, and repeating reconciliation after every exact match is already unavailable is a no-op. Provider caches and mutation/audit contexts keep the overall binding revision; an old context is rejected before cache lookup and must reload through the shared binding owner rather than retrying with guessed authority.

The reverse happens when an account connects (and once at server start for every valid account): `adoptAccount` moves managed HTTPS grants that are `confirmation-required` and whose reference names the same provider user on the same instance but another credential, to the connected account, rebuilt with its credential and revision and `ready` again; provider associations marked `account-unavailable` whose account those grants named move with them. This is what keeps a repository working after its user signs in again as a new credential (an OAuth renewal, a removed and re-added account). Grants of other users and bindings to live accounts are never touched; repeating it is a no-op.

GitLab implements projects, issues, merge requests, draft/ready transitions, merge/squash, and CI through GitBeaker. Its capabilities advertise only those operations; rebase merge is intentionally absent. GitLab has no draft parameter on merge-request create or edit, so a draft create prefixes the title with `Draft:` and ready removes the GitLab-recognized prefix (`Draft:`, `[Draft]`, `(Draft)`) from the current title; ready on a non-draft merge request returns applied without an edit call.

Shared issue and change-request pickers consume provider-neutral list methods. These lists return open items only; historical closed or merged records remain available through status and direct context lookup, not picker pagination.

## Change-based review hosts

A host that reviews one commit at a time (Gerrit) declares optional extensions to the contract. A descriptor that declares none of them publishes, digests and routes exactly as before: `provider-publication-freeze.test.js` holds the `/providers` and `/capabilities` answers of GitHub, GitLab and Gitea as literals, and `mutation-digest-freeze.test.js` their review digests.

- **Terminology.** `terminology.changeRequest` may be `change`.
- **Review model.** `capabilities.reviewModel: 'votes'` (absent means `verdict`). `/pr/review` then takes `{ votes: { <label>: <int> }, body? }` instead of `{ verdict, body? }`: label names `^[A-Za-z0-9][A-Za-z0-9_-]{0,63}$`, integer values from −10 to 10, at most 16 entries, a vote or a message required, `target.headSha` required (the revision voted on). A verdict sent to a votes host and votes sent to a verdict host are both 400; an older client is told to update rather than having its verdict mapped to a guessed label. Which labels exist, what the caller may vote and who voted come per change in the context (`ChangeRequestContext.voteLabels`, `submitRequirements`).
- **Revisions.** `capabilities.revisions: true` lets `/pulls/context`, `readChangeRequestPatch` / `readChangeRequestFile` (walkthroughs and the comparison view) take `revision`, a 40-hex SHA. A provider without the capability answers `400 INVALID_SOURCE_CONTROL_READ_CONTEXT` for one, before any context or account work, and never receives the field.
- **Submit.** `MergeMethod` includes `submit`; `provider-descriptors.js` refuses a descriptor that lists it beside another method. It reuses `/pr/merge`, the kind `change-request-merge` and the digest `{ method: 'submit' }`, and requires `target.headSha` (400 without it), the patchset that was read; the digest does not cover it, since `target` already does.
- **Create by push.** `capabilities.createVia: 'push'` (absent means `api`): a change is created by pushing to `refs/for/<branch>`, through the Git network planner's review class (`../git/DOCUMENTATION.md`, *Review refs on a change host*), which opens only on the primary remote of a ready association with such a host. `binding-service.js` names those providers in the transport authority (`primaryOf`).
- **Presentation.** `presentation.features.branchHeads` (false when a change's head is a revision ref, not a branch) and `submitRequirements`. `publicProviderDescriptor` adds `features.reviewModel`, `features.revisions` and `features.createByPush` from the capabilities, each only when declared.
- **Accounts.** Settings field kinds include `username` (not secret) and `http-password` (secret). A provider whose settings declare a `username` field signs in with HTTP Basic: `/auth/token` requires and passes `username`, and `pat-account-auth.js` calls `verify(origin, token, { username })` and `probe(origin, token, { username })`, stores the typed username as the account's `user.login`, re-verifies with it and answers it through `loginFor(session)`. One username rule (`isProviderUsername` in `provider-id.js`: printable ASCII except `:`, at most 256 characters, no surrounding spaces) is checked by `/auth/token`, by an extension's `basic` login (`outbound-handles.js`, `extension-provider.js`) and by the binding's credential presentation (`binding-service.js`, `binding-contract.js`), so a username sign-in takes (`jane@corp.com` on an LDAP-backed host) never presents as unavailable. Every other provider is called with `(origin, token)` and `(origin)` as before.
- **Project paths.** `repositoryPath: 'path'` means projects are any path, nested (`team/app/sub`) or top-level (`demo`). Selectors keep `{ owner, name }`, split on the last slash by `project-path.js` (`splitProjectPath`, `joinProjectPath`), with an empty owner for a top-level project. An empty owner is accepted only for such a provider: by the route shell's project selectors, mutation targets (`binding-service.js`), mutation records (`mutation-storage.js`) and tracked items, whose key uses the joined path, so every key a built-in stored reads exactly as before. A binding association for a top-level project leaves out its informational `repository`, so the persisted bindings file stays readable by a build that predates such projects. A descriptor may supply `projectPathOfRemote` when a remote's URL path carries more than the project (a Gerrit HTTP remote's `/a/` prefix). The published descriptor adds `repository.pathStyle: 'path'` for such a provider only.
- **Change-Id preflight.** `POST /api/git/change-id` (`addChangeIdToHead` in `change-id.js`) gives the checked-out commit the `Change-Id` trailer a review host's commit-msg hook would have added, computed locally from the commit's tree, parents, author, committer and message. It refuses unless HEAD is a branch at the caller's `expectedHead`, tracked files are unchanged, no merge, cherry-pick, revert, rebase or `git am` is in progress (`MERGE_HEAD`, `CHERRY_PICK_HEAD`, `REVERT_HEAD`, `rebase-merge/`, `rebase-apply/` at their `--git-path`) and the commit has no Change-Id, and it moves the branch only by compare-and-swap. The committer becomes the current user, as with `commit --amend`; a GPG signature on the old commit is dropped, and the new commit is signed only when `commit.gpgSign` is set.
- **Downgrades and audit.** The extensions add no mutation kind and no auth store section: votes and submit are stored under existing kinds (see the Decisions), and a Gerrit account lives in `section('gerrit')`, which an older build round-trips untouched. The one file an older build can refuse is `source-control-mutations.json` after a write on a top-level project (see `auth-storage.js` above). A push for review is a Git network operation, audited like any push; its audit target names only `refs/for/<target>`, never the push options. A review is audited as `change-request-review` whether it carries a verdict or votes.
- **Older clients.** An app built before these fields reads `change` as a pull request and offers no votes, revisions or push for review; the server cannot tell it apart. The UI drops a merge method it has no words for, so a later method cannot break the merge button.
- **Branch status.** `change-id.js` (`readBranchChangeIds`) reads the branch tip's `Change-Id` trailer, and with a base the Change-Ids of `base..branch`, oldest first, at most 50 from the tip. The DTO fields a push-create host adds (`ChangeRequestStatus.localRevision`, `stack`; `ChangeRequest.private`, `topic`, `revisionNumber`; `ChangeRequestContext.revisions`) are typed in `provider-contract.d.ts`.

## Open provider ids

Persisted parsers validate a provider id's syntax only; the registry decides at read time whether that provider is available. A record written by a provider this build does not know therefore never fails a store:

- `source-control-bindings.json`: the association parses and survives every write untouched. Reads and mutations naming it get `422 SOURCE_CONTROL_PROVIDER_UNAVAILABLE` from the binding service; sibling providers and grants read as before. The user can still remove it (`parseProviderTarget` compares its stored instance text); account reconciliation and adoption skip it.
- `ocgit:v2:https:<id>:...` references parse with an unchanged format; resolving one fails closed before any credential lookup or spawn.
- `source-control-auth.json`: an unknown extra section round-trips (see `auth-storage.js` above).
- Git identities, contributor provenance and network-operation actor metadata accept any syntactic id; an unregistered provider resolves to no account, like a disconnected one.
- `source-control-mutations.json` and `source-control-audit.json` were already open. Each provider's persisted mutation `kind` names and digest fields stay byte-identical through its implementation's `prepare()`; `mutation-digest-freeze.test.js` holds literal digests of records written before the shell.

## Adding a source-control provider

A provider is one module folder under `server/lib/<id>/` plus two registry lines. `../gitea/` is the reference for a pull-request host.

- `descriptor.js`: static, SDK-free, every field of `ProviderDescriptor` in `provider-contract.d.ts`. Its `presentation` block is all the client draws.
- `provider.js`: `createProvider(hostServices)` returning the `ProviderImplementation`, JSON in and JSON out. Keep the HTTP client, mappers and resources in files beside it.
- `mappers.js`: payload checks and the mapping to the neutral DTOs GitLab, Gitea and Gerrit emit. A malformed payload fails the read.
- `resources.js`: reads of an existing change request and its mutations find it in a repository of the bound network and check its target with `changeRequestNetworkTarget` (`repository-network.js`), never its source.
- Tests beside each file, with fixtures for the provider's API, and a `DOCUMENTATION.md` that says which behaviours were checked against a live instance and which are still assumed.
- One entry in `BUILT_IN_DESCRIPTORS` (`provider-descriptors.js`) and one in `BUILT_IN_LOADERS` (`provider-registry.js`). Append it: the list is priority order, and the web adapter's fallback for older servers must stay equal to the list's leading entries.

No other file changes. The shell registers every route for the new id, accounts land in `section(<id>)` of `source-control-auth.json`, tracked items batch by `trackedItems.batchLimit`, agent links key threads by `urls.thread`, Git transport follows `transport`, and `/api/source-control` is already host-only in spaces.

The UI renders the provider from the published descriptor alone: a Settings card with the sign-in methods in `authMethods` and fields in `settings`, the mark from `presentation.icon`, a sprite name or path data, wording by `terminology.changeRequest`, link matching from `presentation.urls`, and the board and picker gated by `presentation.features`. `features.changeRequestPatch` is published from `capabilities.changeRequestPatch`, so a host that lists change requests without serving their diff shows no comparison or walkthrough for them. The term and the field kinds are closed lists the UI translates; a provider that needs another one needs a UI change first.

Capabilities say what the provider does. A flag that is off still gets its route, which answers `501 SOURCE_CONTROL_CAPABILITY_UNSUPPORTED`, and so does a resource method the implementation leaves out. Gitea turns off review threads, uploads, stacks and the reference picker this way.

A host that reviews one commit at a time, the way Gerrit does, also picks from the options under *Change-based review hosts*: the `change` term, `reviewModel: 'votes'`, `revisions`, the `submit` method alone, `createVia: 'push'`, `repositoryPath: 'path'` with `projectPathOfRemote`, the `username` and `http-password` settings kinds, and the presentation's `branchHeads: false` and `submitRequirements`. Each one is off when left out, and `../gerrit/` is the reference. A host without forks checks a change request against its bound project instead of `changeRequestNetworkTarget`, as `../gerrit/resources.js` does.

Mutation kinds and digests are the provider's own, through `mutations.prepare()`. Pick them once, because a stored `running` or `outcome-unknown` record replays only while both stay byte-identical. A new provider may reuse GitLab's names and digest fields, as Gitea does; add its literal digests to `mutation-digest-freeze.test.js`.

An installed extension can also be a provider, without a change here: a package whose service declares `provides: ["source-control"]` and whose manifest carries `contributes.sourceControl` (`packages/sdk/GUEST_SERVICES.md`, reference `packages/sdk/examples/source-control-provider/`). The host derives the descriptor (`extension-descriptor.js`), the id (`ext-<guestId>`), the routes (a mounted router) and the account store section; the extension supplies the forge calls. That route fits a Git host whose API can be spoken through the outbound proxy with a personal access token; device flow, uploads, review threads, stacks and the reference picker need an in-core provider.

A provider is a new destination for a token and for what the user writes into issues, pull requests and comments. Load the `enterprise-boundary` skill before adding one. Self-hosted GitLab, Gitea and Gerrit are not gated by enterprise mode today, and whether they should be is an open question for the maintainer (`../gitea/DOCUMENTATION.md`, Enterprise mode).

## Decisions

### Why descriptors are separate from implementations and not one provider list

The Git layer, the binding contract (also bundled into the web client) and tracked items need provider metadata synchronously and must not load Octokit or GitBeaker. Descriptors are static, SDK-free modules; implementations load lazily through the registry. One list holding both would load every SDK at startup or make those callers asynchronous.

### Why literal per-id route paths and not `/:provider/`

`/api/source-control/binding/*`, `/instances` and `/providers` live under the same prefix, so a parameter route would capture them; the read cache matches exact prefixes; and an unknown id falls through to the module's catch-all instead of a provider handler. Descriptor ids that would collide with the shell's own route names are refused. Extension providers keep the literal paths: each gets its own router with the same routes, reached through one dispatcher before the catch-all, because they appear and leave while the server runs and Express cannot remove a route.

### Why mutation kinds and digests stay provider-owned

`running` and `outcome-unknown` records are never pruned, and a retry must replay them. GitHub digests a short kind (`create`) while GitLab digests the record kind (`change-request-create`) with different fields; a shell that computed digests its own way would turn every retained record into `SOURCE_CONTROL_MUTATION_CONFLICT`. `prepare()` keeps each provider's exact kind and digest.

### Why a disabled capability gets a 501 route and not no route

An unregistered path under `/api/` would reach the OpenCode proxy and answer something unrelated. Every route the shell knows is registered for every provider; a capability that is off answers a stable `501 SOURCE_CONTROL_CAPABILITY_UNSUPPORTED` the client can tell from a failure.

### Why legacy aliases are declared in the descriptor and not registered by the provider

GitHub kept its own Express routes while its wire was GitHub-shaped; once it answered neutral DTOs, the only GitHub-specific HTTP left was its `/api/github/*` aliases and retirements. Registration is synchronous before the OpenCode proxy while implementations load lazily, so a provider cannot register routes itself; the descriptor lists the aliases and the shell registers them with the same handlers.

### Why a provider may word its own mutation failures

GitHub records a refused write with its own stable code (`GITHUB_MUTATION_REJECTED`), passes GitHub's reason for a `403`/`404`/`405`/`409`/`422` and answers anything else with a generic message whose cause goes to the log by status and code only. The shell's default (a provider `4xx` with its message) would change what GitHub's stored failures replay as, so `mutations.classifyError` and `presentError` stay with the provider; the shell still writes off a refused account before either runs.

### Why an extension's thread pattern is compiled from templates and not supplied as a regex

`session-link.js` runs every provider's `urls.thread.pattern` over every link an agent posts. A regular expression from an extension could backtrack without bound on a crafted path and stall the server. The host compiles the declared URL templates instead: literal segments escaped, every placeholder a bounded repetition, the same templates the UI's link matcher reads.

### Why GitLab uploads return a Response and not a URL with headers

GitLab's downloader follows a storage redirect once without the credential, and only over HTTPS or on the instance. A `{ url, headers }` answer would move that rule into the shell; returning the provider's Response keeps it in `gitlab/client.js`, and the shell still owns the type allowlist, headers and streaming.

### Why an extension's descriptor is declared in its manifest and not published by its service

Bindings, the Git planner and tracked items read descriptors synchronously, and listing providers must never start a third-party process. A manifest contribution is checked at install, shown in the approval dialog and pinned by the grant scope; a descriptor the service published would be none of those.

### Why the host names an extension's provider `ext-<guestId>` and the extension does not

Bindings, auth sections and mutation records persist the id. Guest ids are already unique, and the reserved prefix keeps every extension off a built-in's id (today's or a later one) and off another extension's, and keeps the id stable across versions.

### Why the host owns an extension's mutation kinds and digests

The digest decides whether a retried write is a replay, and `running` and `outcome-unknown` records are kept. A digest the extension computed could change between its versions and turn retained records into conflicts, or make two different writes look like one. The standard table (`standard-mutations.js`) gives every extension Gitea's kinds and digests.

### Why tokens stay in OpenChamber and the service reaches the forge through a proxy

Git transport needs the raw secret inside OpenChamber anyway, the auth store already handles credential ids, revisions, invalidation and account events, and only OpenChamber can pin a token to the origin it was stored for. So the service gets a per-call handle, never the token. This is least exposure, not a sandbox: an approved service runs as the user and could read `source-control-auth.json` itself.

### Why the adapter decides a write-off and a failed write from what the proxy saw

A service with a bug, or a hostile one, could report `401` and write off a working account, or report a `4xx` for a write that landed, so that it is recorded as failed and never reconciled. The proxy's record of what the forge answered on the call's handle is the only evidence the host has that does not come from the service.

### Why every forwarded call re-reads the catalog and not only the reconciler

The registered set changes only on guest route events, but enterprise policy can change under a running server. Reading the row on each call (cached, policy applied on read) is what the panel routes do and leaves no window; reconciling on a policy-file change would leave one until the watcher fired, and miss environment changes.

### Why only `mutation.perform` may write through its handle

The executor keys, records and audits a write only in `mutation.perform`. A write from a status poll or a reconcile would have no idempotency key or audit record, and a reconcile that writes double-applies a mutation. Approved services still run as the user; this keeps the host's own proxy from being the way around the executor.

### Why a change request is checked by its target and not by its source

A pull request from a contributor's fork has its head in a repository the maintainer's clone never bound. Requiring the head's repository in the network as well would refuse exactly the review a maintainer does most, from the clone they review in. The host serves the head under the target repository and authorises the token for the request, so the target is the only repository the binding has to cover; a request whose target is outside the network is still refused.

### Why votes reuse the review kind and not a new one

`mutation-storage.js` parses against a closed list of kinds and rejects the whole file on an unknown one. A new `change-request-votes` kind would make an older build refuse the mutation store after a downgrade. Votes are `change-request-review` with their own digest fields (`{ votes, body }`), and submit is `change-request-merge`.

### Why the review model is in the descriptor and the labels in the context

Gerrit's labels and their ranges are set per project and can differ by branch, so a static list in the descriptor would be wrong for some changes. The descriptor says how the host reviews (a verdict or votes); each change's context says which labels exist, what the caller may vote and who voted.

### Why a change is created by push and not through an API route

Gerrit creates a change when a commit reaches `refs/for/<branch>`; it has no create call that takes a branch. The push goes through the audited Git network operation path, so `/pr/create` stays off for such a host (501), and the planner's review class is gated on the host's descriptor so the same push can never reach another host, where `refs/for/*` would be an ordinary branch.

### Why a change is found by its Change-Id and not by the branch name

A Gerrit change remembers the commit's `Change-Id` trailer, not the local branch it was pushed from; the same branch can carry several changes in a stack, and a cherry-pick to another branch keeps the Change-Id. Trailers are parsed by `git interpret-trailers`, so a `Change-Id:` line in the body is not one and the last trailer wins, as on the host.


### Why a push-create host's status is keyed by the local tip and not left out of the cache

Its status follows the tip's Change-Id, so a key without the tip answered a commit or a Change-Id amend with the old change for up to the TTL, and indefinitely through an outage. Skipping the cache for such hosts would fix that too, but would cost a host round trip per badge and lose the last-known answer through an outage; one `git rev-parse` per read keeps both.
