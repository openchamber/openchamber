# Desktop shell

## Ownership

Electron owns native windows, privileged IPC, desktop host credentials, browser-panel sessions, SSH and tunnel lifecycle, the in-process server's startup and shutdown, and the OpenCode server the app ships ([opencode-server/DOCUMENTATION.md](opencode-server/DOCUMENTATION.md)), which the in-process server starts. Shared UI and runtime selection belong to `packages/ui`; the server and relay tunnel client belong to `packages/web`. Build and release constraints live in [scripts/DOCUMENTATION.md](scripts/DOCUMENTATION.md). Commands and platform setup live in [README.md](README.md).

## Invariants

### Startup and storage

- `entry.mjs` and `early-startup.mjs` stay small enough to paint the splash before importing the main process and server graph. Electron delays `ready` until the entry graph finishes evaluating. Both bundles share one runtime instance of `early-startup.mjs`, including its window handoff and startup clock.
- Splash readiness has a deadline. A renderer that never becomes ready cannot prevent backend startup. Closing the early window records quit intent so main cannot recreate it during adoption.
- Splash load rejection is harmless when backend resolution navigates the window to the application before the splash finishes loading.
- One launch resolves startup once. Window requests and buffered launch events wait for that resolution because a second server initialization can replace process-global listener state even when binding fails. Port selection precedes server initialization for the same reason. Serverless background launches probe again when a window eventually opens.
- The login-shell environment resolves before the backend is imported or shell-provided flags are read. Finder launches have a minimal PATH. Concurrent callers share the probe, including failure and fallback, so a missing shell is attempted once. Probe output is parsed only after its final marker because shell startup banners can corrupt the first environment entry.
- Desktop-injected server variables are set before importing the server and recorded through `assignInjectedEnv`, so terminal and agent shells can exclude them from startup services. The backend skips a duplicate shell snapshot except on Windows, where its registry-based snapshot contains more than the desktop PATH loader.
- Settings writes use atomic replacement and main-process read-modify-write operations are serialized across awaits. A rejected mutator leaves the queue usable. Only newly created settings directories receive tightened permissions; existing administrator permissions and ACLs survive.
- Theme intent takes precedence over the last resolved variant. System mode continues following the OS. Desktop-scoped preferences override base preferences, which override legacy settings. Stored splash colours are validated again when read because they enter a trusted page's CSS, including values persisted before validation existed.
- Splash defaults match the web loading page and the native frame uses the opening theme's background, so startup does not flash a different appearance. Persisted nested splash colours retain the legacy flat-key fallback.
- The backend's working directory represents a workspace. Using Electron userData makes managed OpenCode appear to have an empty, separate workspace.
- Compile-cache failure cannot prevent startup. Cache pruning is confined to the known userData cache root and proceeds only when Node's active directory is its direct child. The cache environment never leaks into user tools. Cache flushing runs off the startup path because it writes synchronously.

### Windows and navigation

- Main and mini-chat windows use the unsandboxed ESM preload with context isolation and Node integration disabled. Enabling the sandbox breaks that preload and removes the desktop bridge. Browser-panel pages have a separate sandboxed CommonJS preload that exposes nothing to the page.
- Native macOS control positions change together with the header and mini-chat titlebar geometry in the shared UI. The plain hidden titlebar avoids the extra inset of `hiddenInset`; accepting the first mouse event lets a background window's controls work on the first click.
- Revealing a live window preserves its renderer and navigation. macOS app activation precedes window restore/show/focus so the window can come forward from a backgrounded app. Native visibility events remain necessary when background throttling keeps Chromium's Page Visibility state visible.
- Window runtime state and credentials belong to each window. Additional and mini-chat windows never inherit unrelated startup state. A relay-capable mini chat restores the parent instance's transport, including direct probing and relay fallback.
- Runtime identity reported by the current document wins over a window's creation-time host tag. The tag applies only before the first report; an unresolvable reported key claims no host. Committed navigation away from the app clears the reported identity, because a merely started navigation may still leave the current document in place.
- Session links and notification clicks target one owning-runtime window. Broadcasting navigation changes unrelated windows. Reported live matches take precedence over booting windows. Forwarded notifications use the shell's current host identity and discard nested payload copies that could overwrite that identity during a later normalization pass.
- A host id from a deep link is always prefixed with `host:` so it cannot impersonate a URL runtime key. Runtime URL normalization stays aligned with the shared UI. Opaque custom-scheme origins never identify saved HTTP hosts.
- A newly loaded document receives queued session links only once its listener asks for them. Document load alone proves no listener exists; remote documents that never ask use the bounded fallback. Fresh windows receive queued links rather than immediate events.
- Host links open through the host-window route, which supplies runtime state and credentials. A bare Electron window on a host URL cannot authenticate or render desktop chrome correctly. Same-instance session links use the current window; arbitrary app links do not create bare windows.
- Quake bounds are transient and never overwrite normal saved geometry. Quake keeps the existing renderer alive, and closing hides it only while a registered hotkey can recover it. Its default Ctrl+backtick coexists with Windows Terminal's Win+backtick. An explicitly unassigned shortcut stays unassigned even when the default would otherwise apply.
- Quake hiding proceeds even when window-state persistence fails, so a storage failure cannot prevent the requested visibility change.
- Global shortcuts require a single representable accelerator and a modifier for ordinary typing keys; function keys are exempt. An unavailable shortcut remains configured but inactive. Reapplying Quake before Mini Chat releases obsolete registrations before attempting new ones. With no renderer alive, Mini Chat first reveals the main window because draft creation belongs to the renderer.
- Native menu actions take one delivery path: preload already fans IPC events into listeners and DOM events. Customizable renderer-owned bindings show hints without registering a duplicate native accelerator. Session navigation menu items have no extra Alt+arrow binding because those keys belong to other views too.
- Native Copy writes to the focused web contents, including guests and undocked DevTools. The extra app copy event requires exact identity with a live app document; DevTools can lack a host. Link-copy handler replacement preserves the dependency's menu item identity and translations, and failures never log clipboard data or raw native errors.
- Linux terminal entries receive a directory through a path field code or a known working-directory option; URI field codes and arbitrary positional arguments cannot safely substitute for those. Inherited cwd covers newly started processes, but single-instance terminals need an explicit directory argument. The generic terminal choice tries the configured default first, while an explicitly chosen app tries its own entry first.
- Terminal discovery inspects forwarded launcher files without executing them. An early nonzero exit advances the launch chain. App matching drops names that normalize to empty strings because every string contains the empty string, and icon lookup prefers hicolor and mid-sized PNGs usable without SVG tooling.
- AppImage launcher integration writes its icon before publishing the desktop entry because GNOME reads the entry immediately. Only app-marked entries are managed; user-hidden entries and third-party integration retain ownership. Installed package entries take precedence over an AppImage user entry, which would otherwise shadow them.
- Hiding during a macOS full-screen transition preserves the latest visibility intent. A queued full-screen exit still completes after an explicit show; restoration waits for that exit. Hide/toggle can restore full screen, while close discards restoration. Early entry remains limited by Electron's lack of a public entry-start signal.
- Minimize remains a normal taskbar or Dock minimize. Only close participates in tray background mode. macOS activation restores the last live surface, including a minimized mini chat, before creating another main window.

### Privilege and host boundaries

- Main enforces per-command local-sender gates even though the desktop IPC bridge and shell identity are exposed to remote app pages. Remote-safe commands carry only their permitted window and host-switching capabilities. Filesystem, process, dialog, clipboard selection, local runtime identity, and tunnel-listener capabilities stay local-only.
- Main and preload agree on the exact local and development HMR origins. Local home paths reveal usernames and are irrelevant to remote workspaces. A remote host switcher may read the local server's origin, but local credentials and machine information remain behind their separate gates.
- Packaged runtime values are returned only to an app window's top frame through checked IPC. Scheme requests cannot identify the requesting frame, so shared scheme responses contain no credentials. Relative runtime API requests fail closed because the scheme cannot determine the owning window or host.
- Empty startup headers remain unexposed until resolved: contextBridge globals are read-only and would otherwise block the real headers. Boot outcomes stay writable through the main-world initialization script so later host navigation can refresh them. Safe-start state is read synchronously before application scripts restore a crashing layout, and the splash never consumes it.
- Persisted desktop identity deduplicates re-authentication on remote servers. Remote connections use the ordinary desktop client kind; only this machine's embedded server, including its own LAN interfaces on the listening port, receives desktop-local privileges. Display metadata never determines authorization.
- Host storage retains both direct and relay transports so renderer-selected direct addresses remain trusted. Relay public keys are checked at storage time; one-time pairing grants are never persisted. Relay-capable windows bootstrap local UI and let the renderer choose transport, because a failed direct leg does not make the relay unreachable.
- Connect links require explicit consent before storing credentials or changing the destination of API traffic. Confirmed pairing and relay activation run in the main renderer, which owns the E2EE client. One-time secrets leave their queue only for that renderer and are never logged. Extension-install links likewise require confirmation and an HTTPS repository before fetching.
- Remote pages receive saved-host metadata without any host's tokens or authentication headers. Saved-host update commands accept a host id and obtain credentials and destination from storage, so a caller cannot redirect a token. Host URL path prefixes survive authentication requests.
- Returning a remote-served page to Local reloads the Local UI because local CORS and token ownership do not permit that page to switch in place. That navigation is not awaited by the page it replaces.
- External URL validation in main remains aligned with the shared UI scheme exclusions. Arbitrary filesystem reads additionally resolve beneath home or temporary directories and reject known credential paths, even for a compromised local renderer.
- Opaque-origin extension and preview frames are untrusted. Frame self-navigation can exfiltrate data in a URL despite the frame's CSP, so main refuses it before the request and logs only the host. Preview navigation remains within its grant; only the app's empty direct child qualifies for initial preview or PDF loading. Saved-host app origins include both `url` and `apiUrl` because extension frames can use the latter.

### Browser panel

- User, agent, and isolated-space pages use separate sessions from the app. A view without an approved partition would share app cookies. Session membership, checked in main, proves a guessed web contents id belongs to a panel view before capture or debugger access. Partition matching is exact, including complete validation of space partition names.
- Open-web panel sessions deny device and location permissions at both check and request stages, including device pickers. Electron's default grant would expose devices without user consent. Denial is intentional until a consent flow exists.
- Session cookies receive an expiry before quit because Electron otherwise discards logins that rely on them. Host-only cookies remain host-only, and an individual rewrite failure leaves that cookie unchanged.
- Sign-in popups retain their opener so they can post results back. Converting them to panel tabs or loading them in place loses that relationship. POST navigation stays in place when creating a tab would turn it into a GET. Popups belong to their panel window, do not count as remaining app windows, and cannot recursively open further windows.
- Panel driver scripts and annotation bindings run in isolated worlds, including cross-origin frames. Only the top overlay's own world holds the microphone binding, so page scripts cannot call it. Annotation cancellation can precede session creation; cleanup from the previous session can still be running when the next starts.
- Dialog handling stays available while Page.enable is pending because a dialog can block that command's response. Actions return when they open a dialog, and agent tabs answer dialogs immediately with the action's chosen response to avoid blocking the whole app window. Recorded dialog history is bounded because a page can loop on alerts.
- Pointer input uses the debugger session that owns the target frame and coordinates relative to that session. Sending cross-origin input to the top page makes hidden-panel hit testing depend on app layout. HTML-draggable elements use scripted drag events because native HTML drag starts a system session the guest cannot intercept.
- Focus emulation keeps agent pages' controls and clipboard usable without taking the user's keyboard focus. It is reapplied before focusing actions because navigation replaces page state. Colour-scheme emulation is per page; changing `nativeTheme.themeSource` would change the app too. A white base canvas prevents transparent pages from showing the app behind them or capturing black.
- Only shell-staged upload files enter a page. Each file has its own folder and a single-segment filename so duplicate names survive and paths cannot escape staging. Files remain for a day because a form can read them later; age-based cleanup preserves files another app instance still uses.
- Favicons are fetched with the page's own session and returned as bounded data URLs. This preserves login cookies and avoids third-party requests from the app origin. Space views receive no shell-fetched favicon because that request could reach the user's resources on the space's behalf.
- A space's session exists only in memory and receives its blocking proxy before any view or tunnel port reaches the renderer. Only its own tunnel ports bypass that proxy. Proxy writes are serialized; closing a tunnel removes its port, and closing its window tears down its listeners. Space popups stay in place to prevent escape into the user's session.
- Clear Cache removes HTTP cache only. Site storage contains device settings, pins, and login cookies that cannot be recovered elsewhere. Browser-panel clearing is scoped to its validated partition and never clears app storage.

### Shutdown, updates, and SSH

- Every exit path flushes renderer caches, session cookies, and Chromium storage before `app.exit()`, which skips unload handlers. Signals use the same backend teardown as confirmed quit so managed children are not orphaned.
- The in-process server gets its bounded stop before the detached OpenCode killer is considered. It owns terminals and other services too; external OpenCode remains externally owned. Update installation bounds all cleanup, including SSH, while preserving the backend's own grace period.
- One pending update installation owns exit until handoff or failure. Duplicate restart clicks join it. Quit/install flags are set only after backend shutdown succeeds, so closing a window cannot bypass unfinished installation. The IPC result remains pending until quit or an installer error; failure after shutdown relaunches the current version because the embedded server cannot restart in place.
- The installer error grace period starts after cleanup. Linux package installation detaches the updater error listener because an unrelated check failure during an administrator prompt must not relaunch beneath the running install. Ordinary relaunch defers until its IPC reply can flush; the dev launcher owns dev relaunches and keeps HMR alive.
- Checks preserve downloaded state for the same version and preserve pending state on feed failure. Only authoritative no-update clears it. The pending record is assigned before fetching notes because download completion can arrive during that await. Cached download completion is authoritative even without an event; an older download never marks a newer record ready.
- Channel switches wait for the entire prior check, including GitHub fallback, before changing the shared feed. A mirror failure backs off for subsequent checks and downloads, and each running check keeps its own source identity. A missing Stable mirror feed is failure; an unpublished platform feed with no pending package remains no-update.
- Canary defaults to its own feed unless the user chooses another channel. Stable after Canary permits the explicit downgrade, including package-manager downgrade flags; release builds do not downgrade. Changing channel discards the other channel's pending record.
- SSH setup searches home-installed tools and nvm explicitly because login shells omit interactive PATH setup. Installs use a user-owned prefix to avoid root-owned global directories. Existing OpenChamber installs are selected by version because an older PATH entry can shadow a fresh user-prefix install; nvm npm needs its sibling Node on PATH.
- SSH commands that do not consume stdin close it because Windows ssh.exe can hang with an open pipe. Askpass delegates prompts it cannot show to the user's configured helper. Raw SSH history stays in main and is classified before IPC; password-bearing probes are never logged because the remote shell can echo them.
- The remote CLI registry is authoritative for running servers. Registry failure is not an empty result. Reuse requires the intended password policy, version, and bind address; public system information alone proves no authentication. A responding server with another password remains untouched. Only CLI-owned daemons may be replaced, and an adopted daemon follows the instance's keep-running policy.
- Network-published SSH servers require a password. Bind changes are checked in both directions so disabling publication cannot leave an old all-interface daemon running. A pinned port must be freed before replacement; unregistered pinned-port servers still receive the reuse probe. Daemon stop uses CLI lifecycle ownership because the HTTP shutdown endpoint requires UI authentication.
- Default SSH startup opens its tunnel before probing the host entry, with a deadline and teardown on failure. A timed-out attempt is disconnected so it cannot later appear connected after Local fallback.
- A reachable local SSH tunnel is sufficient evidence of liveness when no tracked forwarding process exists. ControlMaster probing is necessary only when that tunnel is unreachable.
- Diagnostics persist the embedded server's console output through electron-log. Repeated browser-panel load failures are demoted within the warning window so a waiting dev server cannot bury genuine errors. Startup target diagnostics log origins only because paths and queries can contain credentials.
- Renderer recovery counts crashes in a row, drops the saved layout on its safe-start reload, and eventually stops reloading. A short per-minute reload budget can reset between repeated layout-induced crashes and loop indefinitely; settings and the active chat remain intact.
- Packaged HTML bypasses cache because it names versioned assets; otherwise a newly installed app can keep loading the previous UI. HMR startup clears HTTP cache because regenerated dependency filenames can change under the same immutable cache key. V8 bytecode caching remains independent of that HTTP cache.
- Unpackaged Dock branch badges take precedence over unread counts so worktree copies remain distinguishable. The window's development tape ignores pointer input and is reapplied on document readiness because inserted CSS lasts only until reload.

## Decisions

### Why manual proxy rules and not a PAC script

Space isolation uses manual rules with `<-loopback>` and explicit per-tunnel bypasses. Chromium retains its implicit loopback and localhost bypass under a PAC script, allowing a space page to reach local services; a scheme-free dead proxy covers HTTP, HTTPS, WS, and WSS.

### Why asynchronous discovery and not synchronous subprocess scans

Installed-app discovery shares in-flight scans and awaits bounded subprocess lookups. Synchronous candidate-by-candidate lookups freeze the main event loop, and an unbounded lookup can keep every later scan waiting until restart; discovery cache versions change when result shape or matching semantics change.

### Why a small renderer young generation

Streaming turns create short-lived objects, and macOS compression keeps the renderer's peak footprint charged after V8 returns memory. The 4 MB semi-space cap reduces that retained footprint; an explicit command-line V8 configuration still wins for measurement.

### Why a reduced tray animation cadence

Tray image changes cost CPU in both the main process and WindowServer throughout long-running work. Six eased frames at five changes per second preserve the roughly two-second cycle with fewer native image updates. Linux tray images stay panel-sized because StatusNotifier hosts can drop oversized images; monochrome geometric glyphs follow native menu-bar tinting.

### Why native menu refresh follows content signatures

Tray live state belongs to the renderer and the native controller owns presentation. A signature of menu-affecting data avoids rebuilding native menus for unchanged snapshots without serializing images or handlers; native menu lifecycle events also cover keyboard opening for quota refresh.
