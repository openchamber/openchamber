# OpenChamber SDK

Public author pages live in `packages/docs/content/docs/sdk.mdx`, `sdk/host.mdx`, `sdk/ui.mdx`, and `sdk/example.mdx`; the user page is `extensions.mdx`. Each has a copy under every locale folder.

## Purpose

`packages/sdk` owns the guest contract. `@openchamber/sdk` is the guest-facing entry: types, limits, `connectHost`, and pure helpers, with no schema library, so a bundled panel stays a few kilobytes. `@openchamber/sdk/schemas` is the host-facing entry: the zod parse of an untrusted guest's manifest (`parseManifest`, `parseManifestJson`) and messages (`guestMessageSchema`, `hostMessageSchema`), plus the few schemas the host reads a catalog row with (`guestToolCardSchema`). Guest-only drawing lives under `@openchamber/sdk/ui`. Host and guest import from here. Do not copy these types into `packages/ui`.

## Entrypoints

- `src/index.ts`: public exports. Host and guest protocol.
- `src/parse.ts`: `package.json` / bare-block parse. Fails closed.
- `src/host-version.ts`: `engines.openchamber` parse and compare. Install uses this against `OPENCHAMBER_VERSION`.
- `src/protocol.ts`: envelope parse for host and guest messages.
- `src/host.ts`: iframe client. Posts to `parent`. Ignores messages whose `source` is not `parent`. In-flight RPCs time out at `GUEST_REQUEST_TIMEOUT_MS` (20s) as `HOST_TIMEOUT`. `onDirectory` / `onSession` / `onSessionLifecycle` / `onItem` replay and stay current after later pushes, same as connection and settings. `onResolve` holds one handler for host `resolve` requests and answers each with `resolve-result` (the clamped chip, `null`, or the thrown error's message; no handler answers with an error). `setBadge` posts `badge` with the count clamped to 0..`GUEST_BADGE_MAX`.
- Install links: `openchamber://extensions/install?url=` from anywhere (https only, the desktop shell passes it on, the add dialog asks first), and `?path=` from chat content only, drawn as a button there.
- `scripts/check-guest.ts`: the `openchamber-guest-check` bin. Reads a package folder and names what the host would refuse: the manifest, pages and scripts that are not built, a service that was not bundled.
- `scripts/bundle-guest.ts`: official IIFE build, exposed as the `openchamber-guest-bundle` bin. Run `bunx openchamber-guest-bundle panel/main.ts panel/main.js` from the guest folder; paths resolve against the current directory. Needs Bun. Any bundler with an IIFE target is an equivalent substitute.
- `dist/`: the published output (`bun run --cwd packages/sdk build`, `tsc -p tsconfig.build.json`). `package.json` `exports` point here so Node loads the SDK from `node_modules` (packaged Electron, `openchamber serve`). Inside the monorepo, Vite aliases and tsconfig `paths` resolve `@openchamber/sdk` to `src/` so builds and type-checks never depend on a stale `dist`. The server under Bun and Node uses `dist`; the root `postinstall` builds it. The package ships to npm from the release workflow with `bun publish`, right before `@openchamber/web`; `scripts/bump-version.mjs` bumps it with the app, so the SDK version always equals the OpenChamber version it was released with.
- `src/file-editor.ts`: the `contributes.fileEditors` contract: limits, file-name pattern check and match, the document/snapshot/change types, and `createFileSaveTracker`. Zod-free, so a guest editor bundles it.
- `GUEST_SERVICES.md`: local service contract (`contributes.service`, `serviceRequest`, grant, loopback).
- `src/service-providers.ts`: contracts a service fulfils for a host role (`contributes.service.provides`). `source-control` is described under Source-control role below, `notifications` under Notifications role, `tracker` under Tracker role, `quota` under Quota role. `browser`: the twelve `browser.*` actions, their parameter and answer types, the limits, `BrowserProviderContext` (the calling project and chat, filled by the host from the tool call; `null` fields mean unknown), and `readBrowserProviderRequest` (a zod-free boundary parse for the service side). `src/service-provider-schemas.ts` is the host's zod parse of the answer, exported from `@openchamber/sdk/schemas`. A providing service needs no panel or background entry (`runtimeContributions` in `parse.ts`). The host side is `packages/web/server/lib/browser-control/provider.js`.
- `src/service-host.ts`: what a service calls on its own (`createServiceHost`, `SERVICE_HOST_METHODS`, `ServiceHostCalls`, limits) and the scheduled run and mention wires. Zod-free, so a service bundle stays small. `src/service-host-schemas.ts` is the host's parse (`serviceHostCallSchema`, `mentionsSearchResultSchema`, `mentionsResolveResultSchema`), exported from `@openchamber/sdk/schemas`. The host side is `packages/web/server/lib/guests/service-host-api.js`, `service-lifetime.js` and `mentions.js`; the contract is in `GUEST_SERVICES.md`.
- `src/session-events.ts`: the `contributes.sessionEvents` contract (`SessionEventsContribution`, the eight `GUEST_SESSION_EVENT_TYPES`, the `SESSION_EVENT*` limits, `GuestSessionEventRequest` / `GuestSessionEventResult`, and the zod-free `readSessionEventRequest` for the service side); `sessionEventResultSchema` in `src/service-provider-schemas.ts` is the host's parse of the answer. The host side is `packages/web/server/lib/guests/session-events.js`; the contract is described under Session events below and in `GUEST_SERVICES.md`.
- `src/waits.ts`: the `contributes.waits` contract (`WaitContribution`, the `GUEST_WAIT*` and `WAIT*` limits, the start and check wire types, and the zod-free `readWaitStartRequest` / `readWaitCheckRequest` for the service side); `src/waits-schemas.ts` holds the host's parses, exported from `@openchamber/sdk/schemas`: `waitArgsSchema(params)` for the agent's arguments, with a message per issue the agent can act on, `waitStartResultSchema` for a start answer, and for a check answer `waitCheckResultSchema` (the envelope) with `waitCheckOutcomeSchema` per entry, so one malformed entry fails only its wait. Declaring waits asks for the `wake` capability. The host side is `packages/web/server/lib/extension-waits/`; the wire is described in `GUEST_SERVICES.md` under Waits.
- `src/service-surface.ts`: the shared-surface contract (`contributes.service.surface`): loopback paths and headers, input event types, limits, and the zod-free `readSurfaceInputBatch` / `readSurfaceControlNotice` / `readSurfaceResizeRequest` for the service side. `src/service-surface-schemas.ts` (host entry) holds the viewer↔host socket messages (`surfaceViewerMessageSchema`, `surfaceHostMessageSchema`) shared by `packages/ui/src/lib/guests/surface-client.ts` and `packages/web/server/lib/guests/surface.js`, plus the service answer schemas. A surface service needs no entry of its own; with `panel.entry` that page is docked to one edge of the picture, `panel.dock` (`GUEST_SURFACE_DOCKS`) and `panel.size` px (`GUEST_SURFACE_DOCK_SIZE_*`), only valid with both. The rail panel is `packages/ui/src/components/layout/GuestSurfacePane.tsx` (host-drawn canvas, not an iframe); `ContextPanel` lays the page iframe (kept mounted) beside the pane (mounted only while shown) per `DOCK_LAYOUT`, and `lib/guests/surfaces.ts#guestSurfaceDocking` decides. Viewer identity is host-set: input carries `x-surface-viewer` and `x-surface-frame-seq` (the service's own number of the frame that viewer last drew; a 409 refuses it as stale), control notices carry `viewer`, and page `serviceRequest`s from a window with a live viewer (`packages/ui/src/lib/guests/surface-viewers.ts`) also carry `x-surface-viewer-controls`.
- `src/ui/`: guest drawing kit. Building blocks only (`mountButton`, `mountTextField`, `mountSearchField`, `mountSelect`, `mountCheckbox`, `mountSwitch`, `mountTabs`, `mountBadge`, `mountList`, `mountEmpty`, `mountSpinner`, `mountBanner`, `mountSeparator`, `mountProgress`, `mountMenu`, `mountText`); the guest composes screens. See `src/ui/DOCUMENTATION.md`. Import `@openchamber/sdk/ui`. Do not import this from `packages/ui`. Kit changes follow package semver, not `apiVersion`.

## Invariants

Notification services can receive kind `pull-request` for a GitHub merge the user requested here. It carries no session identity. The fixed event title and repository reference use the ordinary notification text fields; enterprise mode strips the reference at the host boundary. Services that validate notification kinds with an older SDK must update that parser to accept this additive kind.

- `scripts/bump-version.mjs` refreshes `bun.lock` after bumping package versions; include both in the release commit. Bun resolves `workspace:*` in published archives from lockfile versions, and a frozen install can succeed with stale versions. `scripts/bump-version.test.mjs` covers the bump, frozen install, and packed dependency versions together.

- Extension activity uses `useConfigStore.isConnected` plus live status records and directory `sessionStatusReady` authority. `useUIStore.eventStreamStatus` is an unmaintained diagnostic field, not a connection gate; its default `idle` must not hide known running or idle sessions as `unknown`.

- `contributes.statusSection` is `true` or `{ entry?, source?, title?, height?, defaultExpanded?, requiresProject? }` (`StatusSectionContribution`), the object form with `entry`, `source`, or both. `true` reuses `panel.entry` and fails as `invalid-status-section` without one; the object form's `entry` is package-local `.html`, `title` 1 to `GUEST_STATUS_SECTION_TITLE_MAX` (60), `height` `GUEST_STATUS_SECTION_HEIGHT_MIN`..`MAX` (24..480). `defaultExpanded` defaults to true and only applies when the user has no saved expansion choice. `requiresProject` defaults to false; when true, the actual Work Status directory controls both presence and body rendering. `resolveStatusSectionEntry` resolves shorthand. The object form is a frame of its own: without `panel.entry` or `background.entry` it permits `capabilities`, `service`, `integration`, and `filesystem`, and refuses `page`, `attach`, `actions`, and `commands` as `invalid-panel`, because those are opened or invoked elsewhere. The server validates the HTML/scripts, exposes `statusEntry`/`statusTitle`/`statusHeight`, and counts `statusEntry` as a runtime entry for serving and storage. The host mounts `PluginPane surface="status"` inside the Work Status panel (`components/chat/work-status/WorkStatusExtensionSection.tsx`, see that folder's `DOCUMENTATION.md`): the same sandbox, guest-scoped token, context, grants, approval, and pause gates as a panel. Guest `resize` (`host.setHeight`, `ResizeRequest { height }`, integer 0..`GUEST_FRAME_HEIGHT_MAX`) is a request answered with an empty result on every surface; only `status` sizes its frame from it, through `clampStatusSectionHeight`, and a page docked to a shared surface sizes its dock from it (`DockedGuestPage` in `ContextPanel`: thickness across the dock edge, at least `GUEST_SURFACE_DOCK_SIZE_MIN`, at most half the panel through CSS). Each frame's `setHeight` reaches only its own pane. A status frame never registers a command resolver, clears a badge, or closes rail tabs. Host-rendered controls exist only after a mounted, expanded status frame calls `setStatusControls`; folding, hiding, or retiring the frame removes them. A project change clears header controls; publish them again from `onDirectory`. Workspace subscriptions remain active.
- `contributes.statusSection.source` is `{ path, interval? }` (`StatusSectionSource`, `src/status-view.ts`): a section the host draws itself, with no frame. While the section is shown and expanded the host reads `GET path` from the extension's service through `/api/guests/:id/service/request`, the next read `interval` ms after the last one finished (`GUEST_STATUS_SOURCE_INTERVAL_MIN`..`MAX`, default 2000, resolved by `resolveStatusSectionSource`), with `query.locale` and, when the panel has a project, `query.directory`. The answer is a `GuestStatusView`: up to 16 rows, each a `line` (label, optional icon, dot, content, value, badge, tooltip, up to two actions) or a `note`; content is a `bar`, `chart`, `chips`, `text` or `segmented` choice; actions are a `button` (optional two-click `confirm`), `switch` or `select`; `controls` are header controls in the `setStatusControls` shape. Colours are theme tones (`GuestStatusTone`), never CSS. The host parses the answer with `guestStatusViewSchema` (`src/status-view-schemas.ts`, exported from `@openchamber/sdk/schemas`), which asserts at compile time that it equals the type, and refuses the whole answer when it does not parse. Activating a control posts `{ id, value? }` (`GuestStatusActionEvent`; a switch sends `on` or `off`) to the same path; a non-2xx answer may carry `{ message }` for the host's error toast. A source needs `contributes.service` (`invalid-status-section` without one) and makes the host the service's caller, so a source-only package needs no `panel.entry` or `background.entry` for its service; frame-only declarations (`capabilities`, `integration`, `filesystem`) still do. A section that declares both is drawn from `source` by hosts that know it; older hosts strip the unknown key and load `entry`, so an extension keeps `entry` for as long as it supports them.
- `openSurface(surfaceId)` posts `open-surface { surfaceId }`; an id that is not a context panel surface is `HOST_REJECTED`. The host (`lib/guests/open-surface.ts`) opens it the way its rail icon does, under the frame's directory, or under the directory the rail shows when the frame has none (a Work Status section in a chat draft without a project has none of its own). The result follows what the panel shows afterwards: a surface already on screen stays open where the icon would toggle it closed; one that did not open (`chat`, which needs a session beside it) is `UNSUPPORTED`; no directory yet is `NO_DIRECTORY`. VS Code and mobile answer `UNSUPPORTED` explicitly. A resolved call means the surface is on screen.
- `openCommit(sha)` posts `open-commit { sha }`. `sha` is 7 to 64 hex characters (`GUEST_COMMIT_SHA`); the client refuses anything else as `HOST_REJECTED` before posting and the host schema drops it. The host (`lib/guests/open-commit.ts`) reads the commit itself with `git.getGitLog(directory, { maxCount: 1, to: sha })` in the frame's current directory, checks the returned hash starts with the requested one (`NOT_FOUND` otherwise), selects it in `useCommitSelectionStore` under the Diff view's key (directory, current branch, git runtime key), and opens the context panel's Diff tab in `commit` scope. No project is `NO_DIRECTORY`. VS Code and mobile answer `UNSUPPORTED` explicitly; they load no guests today, so this is the contract for when they do. No capability is needed: it only shows the user their own history.
- Scrollbars in guest documents follow the app's overlay behavior: hidden at rest, shown on hover and for one second after the element last scrolled. `GUEST_SCROLLBAR_CSS` does the hiding and hover; `installGuestScrollbarActivity` (one capturing passive `scroll` listener per document) marks the scrolling element with `data-oc-scrolling`. The server appends both to every served guest HTML as `GUEST_SCROLLBAR_SCRIPT` (the function's own source), so already installed bundles get it without a rebuild; the UI kit installs it too for previews. An authored CSP that blocks inline scripts keeps the hover-only behavior. Forced-colors mode keeps system colors.
- The UI kit's look follows the running app; its geometry follows the bundle. `src/ui/style.ts` splits the kit CSS into sizes (display, dimensions, spacing, type scale), which ship in each bundle, and `GUEST_UI_LOOK_CSS` (colours, fonts, borders, radii, shadows, hover/pressed/selected/focus), exported from `@openchamber/sdk/ui`. The server appends the look to the same `data-openchamber-guest-styles` element after the authored document, so it follows the kit's own `<style>` in the head and wins at equal specificity: an installed extension takes a restyle without a rebuild, while a size change reaches it only when its author rebuilds. Look selectors keep the specificity of the rules they override in older bundles, and `style.test.ts` fails when a geometry property enters the look. Rules for markup an older bundle lacks are keyed on what newer markup adds (a select option carries `data-mark` with its check mark; an option without it keeps the selection fill). Authors override kit rules with a more specific selector; an equal-specificity override in the head loses to the host's look.
- `contributes.fileEditors` is 1 to `GUEST_FILE_EDITORS_MAX` (8) editors, each `{ id, title, match, entry }` (`FileEditorContribution`, `src/file-editor.ts`): unique kebab-case `id`, `title` 1 to `GUEST_FILE_EDITOR_TITLE_MAX` (60), `match` 1 to `GUEST_FILE_EDITOR_PATTERNS_MAX` (16) file-name globs (`isFileEditorPattern`: 1 to 128 characters, no `/`, `\` or NUL, not only wildcards; `matchesFileEditorPattern` compares the name case-insensitively, `*` any run, `?` one character), `entry` package-local `.html`, optional `content` `text` (default) or `binary` (`FileEditorContentKind`); anything else is `invalid-file-editors`. Like the status section, editors are frames of their own: without `panel.entry` or `background.entry` a package may still declare `capabilities`, `service`, `integration`, and `filesystem`, and `page`, `attach`, `actions`, `commands` are `invalid-panel`. The server checks each entry's HTML and built scripts at install, carries `fileEditors` on the catalog row, and counts them as runtime entries for serving and storage (`hasGuestFrame` in `server/lib/guests/catalog.js`). The host owns the file. Wire: host → guest `file-open { path, name, readOnly, encoding: 'text', content } | { ..., encoding: 'binary', bytes }` (a push, sent on `hello` and iframe load, never on other host-state pushes; `connectHost` drops a repeat of the same file), `file-snapshot { id, payload: { purpose: 'save' | 'handoff' } }` answered by guest `file-snapshot-result { id, payload: { snapshot: { content, version } | { bytes, version } } | { error } }` with no `result` back, and `file-saved { version }`; guest → host fire-and-forget `file-change { dirty, edited }`, `file-save`, and `file-unsupported` (no `id`, no answer). Bytes are a `Uint8Array<ArrayBuffer>`, copied by structured clone, so the host schema's `z.instanceof(Uint8Array)` holds in the receiving realm; `sameFileEditorDocument` compares them byte for byte for the repeat-push check. Content on both sides is capped at `GUEST_FILE_EDITOR_CONTENT_MAX` (20 000 000 characters or bytes, `fileEditorPayloadSize`); the guest refuses an oversized snapshot with an error instead of letting the host schema drop it. `onFileOpen` registration installs one capturing `keydown` listener that turns Cmd/Ctrl+S into `file-save`, because key events inside the frame never reach the host. `createFileSaveTracker` is the pure dirty bookkeeping: a written snapshot's version is marked saved, so edits made during the write stay dirty. The host side is `packages/ui/src/lib/guests/file-editor-channel.ts` (one channel per mounted editor; disconnect rejects every outstanding snapshot request), `PluginPane surface="file"`, and `components/views/files/GuestFileEditor.tsx`; the Files view contract is in that folder's `DOCUMENTATION.md`. VS Code and mobile keep the catalog empty, so files there stay with the host's own viewers.
- `contributes.blocks` is 1 to `GUEST_BLOCKS_MAX` (4) components, each `{ name, description, args, entry, height?, answers? }` (`GuestBlockContribution`): a PascalCase `name` (`GUEST_BLOCK_NAME`) agents write in a UI block, a `description` of up to `GUEST_BLOCK_DESCRIPTION_MAX` (120) characters that agents read, up to `GUEST_BLOCK_ARGS_MAX` (8) unique camelCase `args`, and an `entry` ending in `.html`; else `invalid-blocks`. Like a status section, a block is a frame of its own, so `page`, `attach`, `actions` and `commands` still need a panel or background entry. The server checks each entry at install and counts them in `hasGuestFrame`. The host mounts `PluginPane surface="block"` in the reply (`components/chat/uiBlocks/ExtensionBlockFrame.tsx`) with the grants of the extension's panel; `ready.block` is `{ name, args, answered }` (`GuestBlockCall`), `host.onBlock` replays it, `host.answerBlock(text)` answers the agent through the block's own path and the host refuses it without a user activation in the frame, and `setHeight` sizes the frame up to `GUEST_BLOCK_HEIGHT_MAX` (960). Arguments are written by a model, so text from a page or a ticket can steer them: they are untrusted, and a frame does nothing with side effects until the user clicks. A block's frame mounts once the block is finished and on screen. Over relay it reuses a kept document (`relayDocuments` in `lib/guests/frame-url.ts`), because a chat with several blocks would read the package through the tunnel for each.
- `contributes.opencodePlugin` is a folder inside the package (`isSafeAssetPath`: no `..`, no absolute path, no URL; else `invalid-opencode-plugin`) holding an OpenCode plugin: an entry file found the way OpenCode finds it (`exports` when `package.json` also has `name`, otherwise `server` or `index` at the folder's root; OpenCode does not read `main`), and the entry default-exporting `{ id, setup }`, the shape OpenCode 2 loads with a bare `import()` from a folder where nothing is installed, so the entry imports nothing and takes a tool's `input` as plain JSON Schema and answers `{ content }` (no `output` without an output schema). It adds the `opencodePlugin` capability, approved once at install like `skills` and refused by enterprise mode like `skills`; a new version that only changes the plugin's code or folder name is not re-approved (the approval is "runs code inside OpenCode", which the code does not change, as a service's code changes without re-approval), one that adds the contribution asks again. It needs no `service`: the plugin runs in OpenCode, not in a service process. The install checks the folder and the entry; a missing folder or a folder OpenCode would find no entry in is `invalid-opencode-plugin`; a plugin that fails to load is reported by OpenCode (its plugin list, which the server proxies as `GET /api/plugin`), and the extension keeps working. How the host delivers it is under *OpenCode plugin* below.
- `contributes.links` is `{ action, identifier?, urls? }` (`LinksContribution`, `.strict()`, else `invalid-links`) with at least one of the two: `identifier.keys` 1 to `GUEST_LINK_KEYS_MAX` (8) unique literal keys matching `GUEST_LINK_KEY` (upper case, `PROJ` claims `PROJ-123`), and `urls` with one public https `origin` (`isApprovableOrigin`, no IPv4 literal), an `identifier` shape from `TRACKER_IDENTIFIER_KINDS` and 1 to `TRACKER_URL_TEMPLATES_MAX` `item` templates in the tracker's grammar (`isTrackerUrlTemplate`). `action` is `open` (needs `panel.entry`; the click opens the extension with a `GuestLinkItem`) or `attach` (needs a template without `{segment}` or `{segments+}`, `isBuildableLinkTemplate`, so the chip of an identifier names its link, and with `identifier.keys` an `urls.identifier` other than `number`, which `PROJ-12` never fills). It adds the `links` capability, approved for exactly that action, those keys, that origin, shape and those templates: any change asks again (`grant-scope.js`). See *Links in messages*.
- `contributes.sessionControl` (`{ content?: true, answers?: true }`), `contributes.instructions` (`true`) and `contributes.mentions` (`{ label }`) need `contributes.service` (`invalid-session-control`, `invalid-instructions`, `invalid-mentions`). `sessionControl` adds the `sessionControl` capability, `content` adds `transcript` too, which each reader of content checks with its own contribution's `content` flag, since one grant covers both, `answers` adds `sessionAnswers`, `instructions` adds `instructions`.

### Why answering the agent is its own capability and stopping a turn is not

`sessions.answerPermission` lets a process outside the app allow what the agent asks to run, in any session, so it gets the `sessionAnswers` line in the approval dialog beside `sessionControl`; folding it into `sessionControl` would have widened every approval already given to session-starting extensions. A form answer rides on the same grant, since OpenCode's own consent prompts (web search, for one) are forms. `sessions.stop` stays under `sessionControl`: it only takes back what a send started. An answer allows a request once and never "always", so a standing rule is still only made by a click in the app. `contributes.skills` is a package folder of `<name>/SKILL.md` skills (`invalid-skills`, a missing folder fails the install) and adds `skills`; the server lists it in OpenCode's managed config while the extension is active. `service.keepRunning`, `service.schedule` and `mentions` ride on the `service` grant's scope, so a version that adds or changes one asks again.
- `contributes.integration.settings[].secret: true` masks the field on the card. The value reaches no frame: `ready.settings` leaves it out, the status route names only `secretsSet`, and the service reads it through `readSettings()`. An empty field keeps the stored value, because the card never holds it.
- `contributes.actions[].where` also takes `selection` (text selected in a message, `GuestSelectionItem`), `file` (a Files row, `GuestFileItem`) and `diff` (selected lines of a diff or an editor, `GuestDiffItem`). `roles` and `payload` stay on `message` and `session`. Each item carries the declared `action` and the directory; `run-action.ts` revalidates it like the others.
- `contributes.page` is `true` or `{ entry, title? }` and adds a user-opened full-screen page. `true` reuses `panel.entry` and needs it; the object form is a frame of its own like a status section (`hasPageFrame` in `parse.ts`), so a package may be only a page, and `page: true`, `attach`, `actions`, `commands` beside it still need a panel or background entry. `hasGuestFrame` counts `pageEntry`, and `PluginPane` keeps a page frame without `guest.entry` mounted. `resolvePageEntry` resolves shorthand; the server validates its HTML/scripts and exposes `pageEntry`/`pageTitle`. `PluginPane surface="page"` uses the same sandbox. `useUIStore.openGuestPageId` is transient and mutually exclusive with other main pages. The sidebar menu opens it; `close()` or explicit session navigation closes it. Pages are not context-rail surfaces.
- `workspace.ts` owns project/worktree/session snapshots and storage types; `workspace-schemas.ts` validates their wire contracts. A session record's `inWork` follows the sidebar's In work rule (`orderInWorkWorks`: top-level, not archived, `isSessionInWork`, all gated by `sessionWorkEnabled`), so it is false for everyone while the setting is off, and the observer republishes on the toggle. `unread` is `isSessionUnread` (`sync/session-unread.ts`), the sidebar's mark from OpenCode's `time.idle` and `time.viewed` or the user's own Mark as unread. `tool` and `context` come from `sync/session-live-work.ts`, which reads tool and step events for every directory before the store gate: `tool` is the newest unfinished call, else the one that ended last in the turn (most calls start and end inside one batch of events), and shows only while the status says the session runs, so a lost end event cannot leave a stale tool; and carries the call's path, never a shell command's text, because every `sessions` grant reads it; `context` is the newest step's window against the session model's limit from the provider list, unknown after a compaction, and seeded from the host's `/api/sessions/status` for sessions this client has not seen a step of. The existing `sessions` grant covers lists, subscriptions, opening sessions, and targeted creation. `lib/guests/workspace.ts` projects shared project, topology, session, and live-status stores; reads perform no network or git discovery. A registered observer is shared per runtime/extension/query and stops with its last listener. `PluginPane` limits each frame to 32 subscriptions and clears them on unmount, grant withdrawal, and runtime switch. Initial snapshots and updates have explicit loading/error coverage. `HostClient.onProjects/onWorktrees/onSessions` return promises of unsubscribe functions, so approval failures reach the caller.
- `shells.ts` owns the running-shell contract: the `shells` declared capability, the snapshot and result types, and `GUEST_SHELL_ID_MAX` (128), `GUEST_SHELLS_MAX` (200), and `GUEST_SHELL_OUTPUT_TAIL_MAX` (65536). Wire: guest `shells-subscribe` `{ subscriptionId, scope }` with scope `{ kind: 'session', sessionId }`, `{ kind: 'project', projectId }`, or `{ kind: 'global' }`, `shells-unsubscribe` `{ subscriptionId }`, `shell-output` `{ shellId, cursor?, tailBytes? }`, and `shell-stop` `{ shellId }`; host push `shells` `{ subscriptionId, snapshot }` where the snapshot carries `kind: 'shells'`, an echo of the requested `scope`, the running `shells`, and `ended` (`GuestEndedShell`: a running shell plus `status` from `GUEST_SHELL_END_STATUSES`, `endedAt`, optional integer `exit`). `lib/guests/shells.ts` projects `useBackgroundShellsStore` (the requested scope: a session and its subagents, a registered project's sessions matched by directory rather than by `projectID`, or every session; running oldest start first, ended oldest end first keeping the newest `GUEST_SHELLS_MAX`) from memory, so a read never hits the network or git; `observeGuestShells` shares one observer per runtime and scope. ### Why an extension's logo ranks above the bundled logos and not below them

The maintainer asked for this order: an extension can already ship a provider's plugin and usage card, so it also decides how that provider looks. OpenCode does not report which plugin registered a provider, so nothing ties a package to the IDs it names, and any active extension can redraw `anthropic`. What the user set in Settings stays above every extension. IDs the app draws with the replaced logo follow it (`claude` with `anthropic`), so the model picker and the usage card agree.

### Why an alias is another key and not a list under each logo

The map already says everything a list would: two IDs with the same file are an alias, and the host checks each file once. A shape like `{ logo, providers: [...] }` reads better in a large icon pack, and it would add a second way to name a provider and more parsing, for a file name repeated a few times. The limit is 256 so a pack fits, with aliases counted as entries. The host fetches only the logos it draws, so a full map costs about 10 KB on the catalog row.

## Host hole

Built-in extension source and registration rules live in `packages/extensions/DOCUMENTATION.md`. The server assigns `source: 'bundled'` only from its app-owned registry and automatically grants the package's declared capabilities. Built-ins use the same SDK, sandbox and enabled-state checks as user extensions; the `openchamber-builtin-` namespace is reserved. Their account cards appear under Built-in integrations, and their persisted disabled state and data survive app updates.

Relay panels use `lib/guests/relay-document.ts`: fetch package HTML and its statically referenced scripts, styles, CSS imports/URLs, images, fonts, and nested documents through `runtimeFetch`, then render self-contained `srcDoc` with the same `sandbox="allow-scripts"`. A normal iframe URL bypasses the client-side tunnel and can load the local host UI instead. Local resource paths stay under that guest's package; missing files, import cycles, or resource limits fail the load. The loader allows 500 referenced files, 40 MiB of fetched bytes and 64 MiB of embedded text. Runtime-created relative URLs are not intercepted: bundle those assets into the IIFE or use SDK operations. The relay document gets `guestFramePolicy(null)` as its first `<meta>` (a `srcDoc` has no response headers), so it cannot connect anywhere. Existing authored CSP is preserved and only narrows it further. Direct iframe URLs retain their existing path.

`useGuestIconSource` loads package SVGs through authenticated `runtimeFetch` in direct and relay modes, then exposes revocable blob URLs to CSS masks. It uses the package path rather than the original URL token, so cold-start token readiness and token expiry cannot strand an icon. Cache identity follows runtime, package path, extension version and catalog revision; late responses are discarded and old blobs revoked. Unknown icons and SVGs that are loading or failed use the shared `FALLBACK_GUEST_ICON`, the `apps` glyph.

Git installation accepts HTTPS, `ssh://` and scp-style SSH addresses. `POST /api/guests` accepts optional `gitIdentityId`; the server stores only that ID in the git origin, and resolves the profile again for clones and update fetches. Global/omitted identity uses the server process's Git/SSH configuration and agent. The Settings picker loads identities from the active runtime, discards stale loads, and never reuses a desktop's cached profiles on a remote server. SSH parsing, public-host validation and pinned connection options belong to `packages/web/server/lib/guests/clone.js`.

Catalog loading and installation retain typed request diagnostics in `lib/guests/request-failure.ts`: fixed API route, method, HTTP status, or a transport/invalid-response classification. Settings shows catalog diagnostics and passes install diagnostics to the toast description so Copy includes them. Response bodies, headers, credentials, and arbitrary transport error messages are excluded. Catalog failures preserve a previously loaded list; diagnostics clear on success or runtime switch, and late failures from a retired runtime are ignored.

The catalog follows the server while the app runs: `hooks/useGuestCatalogSync.ts` reads it again on `openchamber:guests-changed` (any install, update, approval, pause, removal, or edit to a folder install) and on a control-stream reconnect. `reloadGuestCatalog` never joins a read that started before the announcement; it queues one more after it, so the newer answer lands last. An extension needs no code of its own for this: its frames reload when the row's `revision` moves (part of `PluginPane`'s frame key; a file editor keeps its document and loads the new files on its next open), a shared-surface pane attaches a new viewer, a background action in flight ends as unavailable, and its service starts again from the new files on the next request.

`lib/guests/useGuestFrameUrl.ts` owns iframe URL lifetime. A direct frame loads by a grant in the path (`/api/guest-files/<grant>/…`, see `packages/web/server/lib/guests/DOCUMENTATION.md`), or by the guest-scoped query token from a server without grants. It retains the credential's expiry, renews on an expired navigation, and remints after enable/version/revision/runtime changes. Expiry alone never reloads a healthy document. Recovery is bounded until the guest's next `hello`; mint failure leaves the existing load-failed UI rather than mounting an unauthenticated URL. Late mint responses from a retired owner are discarded. Guest capability grants and provider OAuth are separate from this host file-loading authorization.

`GET /api/guests` plus `PluginPane` on the desktop/web rail. The iframe loads from `/api/guest-files/<grant>/<entry>` with a grant minted for that extension (`resolveGuestFrameUrl`); against a server without grants it falls back to a token minted for `guest:<id>` scope, valid only for `GET /api/guests/<id>/*`. The session-wide URL token never enters a guest frame. Settings → Extensions installs a folder, a local `.zip`, or an https git / zip URL into that OpenChamber instance's data dir (`extensions.json`). Settings → Integrations shows a host card for each installed guest that declared `integration`. OAuth and pasted tokens live in `guest-auth.json`. Host Linear uses `linear-auth.json`. VS Code and mobile set the catalog to `unsupported`. That is not an empty success. A guest must ship a classic IIFE (`panel/main.js`). No runtime compiles guest TypeScript. The iframe cannot load ESM.

**Folder install** stores the realpath in `extensions.json` with `source: "path"`. Uninstall drops the catalog row and extension-owned storage. The user's folder stays.

**Zip / git install** copies into `{dataDir}/extensions/{id}` with `source: "zip"` or `"git"`. Only git installs update: Settings → Extensions compares the installed `package.json` `version` with the origin's and offers Update when the origin is newer, so bump `version` to ship one; a `#tag` or `#branch` on the install URL pins that channel. The archive is not kept open. The host reads it (local file or https download, 20MB cap), extracts with a small allowlist unzip (store/deflate only; no zip64, encryption, or `..` paths; 500 files / 40MB uncompressed), unwraps a single root folder when `package.json` sits inside it, inspects the manifest, then renames staging to `{dataDir}/extensions/{id}`. Runtime serves and spawns from that copy. Uninstall deletes the copy. The original `.zip` on disk is untouched.

The iframe is `sandbox="allow-scripts"` with no `allow-same-origin`, so its origin is opaque. Host posts to that frame's `contentWindow` with target `*`. The string `null` is not a legal `postMessage` targetOrigin. Receive still accepts only `event.source === contentWindow`. Every guest document also runs under `guestFramePolicy` (`src/frame-policy.ts`): the server sends it with `sandbox allow-scripts` on each served file, the relay loader as a `<meta>`. It keeps the guest off the network: scripts, styles, images, fonts, media, workers and nested frames load only from the package (`'self'`) or `data:`/`blob:`, and `connect-src` is the guest's own package path, `/api/guest-files/<grant>/` (or `/api/guests/<id>/` on the query-token route), named by the request's `Host`, since a sandboxed document has no origin for `'self'`; `'none'` in relay. `'self'` for connections would reach the whole OpenChamber API. External data goes through the host (`request` to the declared, approved `apiOrigin`) or to `contributes.origins`: 1 to `GUEST_ORIGINS_MAX` (8) plain https origins (literal hostnames, so no `*` or other CSP syntax can widen them), granted as the `origins` capability. Its scope is the sorted list (`grant-scope.js`), so an update that adds an origin is unapproved until the dialog runs again. Approved origins join `connect-src`, `img-src`, `font-src`, `style-src` and `media-src`, never `script-src`/`worker-src`/`frame-src`: code from elsewhere could change after approval. The server reads them from the effective grants when it serves a file; relay frames get them from `PluginPane` (`approvedOrigins`, part of the frame key so an approval reloads the frame). External CDN assets not declared there do not load; bundle them. Guest files are served with `Access-Control-Allow-Origin: null`, because fonts and fetch from the opaque-origin frame are CORS requests. A guest navigating its own frame elsewhere is refused by the desktop shell (`packages/electron/guest-frame-navigation.mjs`, `will-frame-navigate`); the web runtime has no such hook. Guest `connectHost` posts `hello` to `parent` with `*`. The host answers `hello` and also pushes `ready` on iframe `load`, because a cached panel can fire `hello` while React is swapping the listener.

File calls go through `POST /api/guests/:id/files` with the `x-opencode-directory` header of the open project (`lib/guests/files.ts`). The header is handed over as plain entries so the runtime can carry a project path outside Latin-1: such a value is sent percent-encoded with `x-opencode-directory-encoding: uri` and decoded again by `resolveOptionalProjectDirectory`. `PluginPane` answers `NOT_GRANTED` and `NO_DIRECTORY` itself, mirroring the server, so a refused call costs no round trip; the server is still the authority.

Clipboard writes run in the host (`copyTextToClipboard`). Compose uses `useInputStore.setPendingInputText`. Attach writes the composer chip. The iframe has no clipboard, no composer, and no chip. The + menu and the attach window chrome are host. Guest JS is not in that React tree.

Actions, commands, and the badge are host chrome too. `useGuestActions` (`packages/ui/src/hooks/useGuestSurfaces.ts`) lists active guests' actions for message and session menus, empty on VS Code and mobile. A click builds the item with `buildGuestMessageItem` / `buildGuestSessionItem`; failed conversation loading is a toast, never an empty conversation. `runGuestAction` dispatches the declared mode. In default `open` mode, `openGuestWithItem` routes like a chip click: the attach window for `attach: "dialog"` through `useGuestDialogStore`, otherwise the rail through `useGuestItemStore`. Background mode is documented below.

The command palette (`components/ui/CommandPalette.tsx`) lists `where: "session"` actions while a session is open, and runs them on the current session the way its header menu does (`runGuestSessionAction`). Message, selection, file and diff actions stay in their own menus: the palette has no message, selection or lines to give them. Each row shows the extension's icon and name, and the rows are search-only, like project actions. A query matches a row's own label first and the extension's name after it.

`useGuestCommands` lists commands minus reserved names. The composer routes `/name args` through `submit/guestCommands.ts` to `runGuestCommand`, which asks a mounted pane's registered resolver or mounts a hidden `PluginPane` through `GuestHosts`. The pane registers after hello/load, posts `resolve`, and settles on `resolve-result` or the 20s deadline. A returned chip uses `useInputStore.setPendingGuestIssue`. The command palette lists the same commands with the same reserved names (`reservedComposerCommandNames`); picking one puts `/name ` at the start of the main composer with the draft as its argument (`setPendingInputText(name, 'slash-command')`) and sends nothing, so the command runs on the same path when the user sends. `badge` writes the memory-only `useGuestBadgeStore`; the rail paints the count and opening the panel clears it. A paused or unapproved guest contributes no actions, commands, tool presentations, or badge.

Add a type when the host grows that hole, not before. Any new `connectHost` method ships with a `PluginPane` / `answerGuestMessage` branch in the same change.

Rebuild every example bundle after an SDK change (`bunx openchamber-guest-bundle` per entry, see `examples/README.md`); the built files are checked in. An exported constant is a literal (`3_600_000`, not `60 * 60_000`): Bun keeps an expression even when nothing imports it, so it lands in every bundle. A Bun upgrade needs the same rebuild: the minifier names identifiers differently between releases, so a panel bundle built by the previous Bun no longer matches and `examples.test.ts` fails for every PR until the bundles are regenerated. Service bundles are not minified and keep matching.

## Anchored popovers

`popover.ts` owns bounded rectangles, JSON context, requests and close events; `popover-schemas.ts` validates the host boundary. `connectHost` exposes `openPopover`, `closePopover`, `setPopoverAnchorActive` and `onPopoverClosed`, gated by `ready.features.popovers`. `src/ui/popover-anchor.ts` owns DOM-anchor hover/focus events and active-only observers. Public limits and behavior live in `API.md#anchored-popovers`.

The UI host owns geometry and lifecycle in `lib/guests/popovers.ts` and `components/layout/GuestPopover.tsx`; `PluginPane` remains the message and authorization boundary. An overlay reuses its owner's approved package entry and existing direct/relay loader. It receives `surface: 'popover'`, bounded `ready.popover` data and the owner's directory. Its grants are the extension's existing grants. It cannot choose a different entry or open nested popovers. The host verifies child authority against the active owner before handling messages, including the interval before React removes a retired frame.

Project changes dismiss the overlay without resetting the owner's workspace subscriptions or unrelated pending replies. Frame, runtime, origin, grant and installation changes retire it. One fresh child exists per opening; there is no hidden warm frame. Owner-only close events identify the opening so delayed activity cannot close its replacement. The host focuses the source frame for keyboard dismissal, and the guest helper restores the actual anchor, which the host cannot access across the sandbox.

Child pointer/focus activity travels through the existing popover activity message, restricted to that child's own opening. Parent iframe `:hover` and pointer events are not reliable for opaque-origin content. The host verifies geometry but cannot prove a guest's hover intent; focus transfer requires existing owner focus. Host modal dialogs suppress previews. `setHeight` resizes the child within its bounds without changing the activation or interrupting pending replies. Dialog-owned previews remain unsupported to preserve their modal focus boundary.

## Guest toasts

`ToastRequest` adds optional `copy: boolean | { text: string }`, `dismiss: boolean`, and `persistent: boolean`. The client checks message/copy length before sending; the host schema validates the complete payload. `HostBridgeEffects.toast` receives the request intact. `lib/guests/toast.tsx` owns toast creation and per-toast dismissal; `components/layout/GuestToastActions.tsx` renders the buttons and clipboard success/failure state. Copy keeps the toast open. Persistent toasts always include OK, including when the guest passes `dismiss: false`.

Toast acknowledgement means displayed, not clicked. Button closures retain only text and toast identity, not the guest's lifetime or runtime. They survive action completion, iframe teardown, and runtime switches. Labels resolve through the host's reactive i18n context. ## Background actions

`contributes.actions[].mode` is `open` or `background`, defaulting to `open`. The manifest parser and UI catalog parser preserve it; server catalog projection already carries actions unchanged. Existing `onItem` routing stays with open-mode actions. `runGuestAction` revalidates the captured declaration, active grants, target role, and runtime before dispatch. Session actions also discard history loaded across a runtime switch.

`lib/guests/run-action.ts` owns temporary invocation state, a 20-second loading/execution deadline, and an eight-frame limit. Each click gets a distinct `PluginPane` from `GuestHosts`, preferring `backgroundEntry` and falling back to `entry`, with `surface: 'background'` and `headless`. It never registers as a slash-command resolver, consumes a parked item, clears a badge, opens a tab, or changes session selection. The pane pins session/directory context to the clicked target. Composer-writing methods retain their existing current-composer behavior.

The catalog carries `backgroundEntry` independently of the visible `entry`. Both HTML files and their built scripts are checked at install. The serving route's `hasRuntime` gate permits code when either exists; storage applies that same entry check plus enabled/approval gates. Background-only chips cannot reopen a rail panel, so the composer shows a no-panel notice while retaining the existing browser action.

Slash commands use the background entry whenever it is declared. A visible pane then does not register a resolver; only the temporary command host does, with `ready.surface: 'background'`. Panel-only extensions retain resolver reuse. Resolver registrations are retired when the frame URL or entry changes and refuse calls after runtime/grant/version changes. `examples/hello-kit/background` is the reference for a separate entry; omit that example's visible entry and page to make it background-only.

Both `MainLayout` and the separate-window `MiniChatLayout` mount `GuestHosts`; a message action must have an execution host in the window that owns its catalog and session state.

The SDK adds `HostActionMessage`, `GuestActionResultMessage`, `GuestActionItem`, `ActionResultPayload`, and `HostClient.onAction`. Wire `action` carries one message/session item and an invocation ID; `action-result` carries that ID and a discriminated success/error payload. Error text shares `GUEST_RESOLVE_ERROR_MAX`. `ready.item` stays null; a one-shot `takeMessage` prevents hello/load/context updates from executing an action twice. The handler must be registered synchronously and await its work before returning. Host schema validation plus the frame's source and invocation ID reject unrelated replies.

The runner cancels on runtime/catalog invalidation and marks the operation inactive synchronously, so queued messages cannot mutate host state during React teardown. Timeout, completion, frame-load failure, or host unmount clears the invocation and subscriptions. Unmount cleanup yields one microtask for Strict Mode's effect reattachment. Already accepted remote effects are not rolled back; no automatic retry. Web/desktop use the existing direct or relay frame loader; VS Code and mobile remain unsupported. `examples/hello-kit` demonstrates a background message-length toast.

## OpenCode role

The SDK owns `service.provides: ["opencode"]` and the implicit `opencode` capability in `manifest.ts`. The role needs no extra contribution. `requestedGuestCapabilities` requests both `service` and `opencode`; an existing service grant alone cannot approve the new access. `opencode` cannot be listed in `contributes.capabilities` and needs no scoped persisted schema.

Services use `@opencode/client` directly under the [OpenCode access contract](./GUEST_SERVICES.md#opencode-access). The [host provider module](../web/server/lib/guests/opencode-provider/DOCUMENTATION.md) owns transport, the list of allowed reads, upstream selection and process-lifetime authorization; the SDK adds no transport helper or response envelope.

### Why reading has its own capability

Sessions and messages hold everything said in them, so a service that can read them is a different thing to approve from one that only runs. A distinct approval names that access and prevents an earlier service approval from silently granting it. The grant covers reads only: the host refuses everything else, so `opencode` will never mean more than that, and wider access would be a new capability the user approves.

## Source-control role

`provides: ["source-control"]` plus `contributes.sourceControl` (`SourceControlContribution`, `manifest.ts`) make an extension a Git host. The SDK owns the manifest parse, the wire (`service-providers.ts`: `SOURCE_CONTROL_PROVIDER_PATH`, `SOURCE_CONTROL_PROVIDER_METHODS`, deadlines and caps, `readSourceControlProviderRequest`, the outbound types, `createSourceControlForge`) and the host's answer schemas (`sourceControlProviderSchemasV1` in `service-provider-schemas.ts`, from `@openchamber/sdk/schemas`). The host adapter that turns the contribution into a provider descriptor, the callback listener and the outbound proxy live in `packages/web/server/lib/source-control` and `lib/guests`. The service-side contract is in `GUEST_SERVICES.md`; `examples/source-control-provider` and its fake forge are the reference, run by `scripts/source-control-example.test.ts`.

- The role and the contribution come together: either alone fails as `invalid-service`, as does a `panel.id` longer than `SOURCE_CONTROL_GUEST_ID_MAX` (28), because the host id is `ext-<panel.id>` within 32 characters. Contribution field errors are `invalid-service` too, and the message starts with the failing field (`contributes.sourceControl.instances.defaultInstances[0]`), refined values included.
- Sign-in declares `token`, `login: { kind: 'service', hint }`, or both. Only a host whose manifest declares `login` receives `auth.status`. It answers a user DTO or null for that exact origin; an error remains unknown. The host reuses its non-persisted CLI account, carries its verified user on reads, refuses forge proxy access for its handles and leaves Git credentials to system Git. `ACCOUNT_CHANGED` invalidates only the acting service-login account. The wire stays 1 and existing token-only manifests remain unchanged. A manifest with `login` needs `engines.openchamber` `>=2.7.1`.
- `auth.verify`, `auth.status` and resource sessions accept the same user ID: a positive safe integer or a non-empty string up to 256 characters. Readers preserve the original value. Account identity comparisons use its string representation, so `7` and `"7"` identify the same user while `"0007"` and large numeric strings retain their identity.
- `sourceControlServiceLoginSchema` is exported from the host-only schemas entry and shared with the UI descriptor parser. Manifest parsing trims the hint before applying its bounds and rejects unknown fields; public descriptors preserve the hint and ignore unknown fields for forward compatibility.
- Every contribution object is `.strict()`. Capabilities and `presentation.features` default to `false`; review threads, uploads, stacks, the reference picker, multiple accounts, `createVia` and `branchHeads` are not declarable.
- The change-based fields (`terminology.changeRequest: "change"`, `capabilities.reviewModel`, `capabilities.revisions`, the `submit` merge method, `presentation.features.submitRequirements`, `token.scheme: "basic"` with `token.username`) are optional with no default, so a manifest without them parses to the same object as before and the host builds the same descriptor. Two refines hold: `submit` is the only merge method when present, and `basic` comes with `username: true` and the other way round.
- The status schema accepts `localRevision` and `stack`; the vote labels, submit requirements and revisions ride on the context, which stays a pass-through read.
- URL templates accept literal segments and the `SOURCE_CONTROL_URL_TOKENS` placeholders only, each a whole segment, with `{repo}` and `{number}` once and the owner token matching `repositoryPath`. No template can carry regex syntax, a `.` or `..` segment (a normalized URL never matches one), or appear in both `changeRequest` and `issue` (change request patterns match first, so every issue link would read as a change request).
- `readSourceControlProviderRequest` checks the envelope (`v`, `requestId`, `method`, `provider`, `session`, plain-object `input`), not each method's input: the host built and validated it, and the service bundle stays free of zod.
- The answer schemas check deeply only what the host acts on (account, probe, head, source, mutation target/result/reconcile, live summaries, status). DTO reads the UI parses itself pass as any JSON object or array within `SOURCE_CONTROL_PROVIDER_RESPONSE_MAX`. `mutationTarget` and `mutationResult` hold exactly the keys `mutation-storage.js` accepts; keep them in step.
- `SOURCE_CONTROL_PROVIDER_METHODS` is one literal array. Spreading sub-lists into it keeps the arrays in every panel bundle, because Bun cannot drop an array spread.

### Why the Git host is declared in the manifest and not answered by the service

Descriptors are read synchronously by bindings, the Git planner and tracked items, and listing providers must never start a third-party process. In the manifest the description is parsed at install, shown in the approval dialog, and pinned by the grant scope.

### Why OpenChamber names the provider `ext-<panel.id>` and not the extension

Guest ids are already unique and stable, and bindings, the auth section and mutation records persist the provider id. A derived id cannot collide with a built-in or another extension, and cannot change between versions.

### Why tokens stay in OpenChamber and not in the service

For token accounts, Git transport needs the raw secret inside OpenChamber, the auth store handles accounts, revisions and invalidation, and the outbound proxy owns origin pinning. Service-owned logins keep credentials in the service's CLI and give OpenChamber only identity; those handles cannot use the proxy and Git uses system credentials. An approved service runs as the user, without a sandbox. The quota role hands OpenCode credentials over; see *Quota role*.

### Why change-based fields are additive on wire 1 and not a wire 2

The envelope and the methods are unchanged; `revision` on three reads and `votes` in a review's input are new optional fields. The host sends them only to a host whose manifest declares the matching capability, and a service built before them cannot declare it, so no service ever receives a field it would ignore and answer wrongly. A new wire would make every existing extension rebuild for nothing. The cost is that older hosts refuse a manifest that uses the fields, which `engines.openchamber` makes an install-time message.

### Why OpenChamber owns mutation kinds and digests and not the service

The mutation store's kinds are a closed list and the digest decides whether a retry is a replay. A digest an extension computed could change between its versions and turn retained records into conflicts, or make two different writes look like one. The service resolves, performs and reconciles; the host decides what a failure means from what its proxy observed.

## Notifications role

`provides: ["notifications"]` plus `contributes.notifications` (`NotificationsContribution`, `manifest.ts`) make an extension a delivery channel for the user's notifications. The SDK owns the manifest parse, the wire (`service-providers.ts`: `NOTIFICATIONS_PROVIDER_PATH`, the three `NOTIFICATIONS_PROVIDER_METHODS`, deadlines and caps, `GuestNotification` and `GUEST_NOTIFICATION_KINDS`, `readNotificationsProviderRequest`, `createNotificationsOutbound`) and the host's answer schemas (`notificationsProviderSchemasV1`). The host side is `packages/web/server/lib/notifications/extension-channels.js` with its account store and routes; the service-side contract is in `GUEST_SERVICES.md`; `examples/notification-webhook` and its receiver are the reference, run by `scripts/notification-webhook-example.test.ts`.

- The role and the contribution come together: either alone fails as `invalid-service`, as does a `panel.id` longer than `NOTIFICATIONS_GUEST_ID_MAX` (28, the Git host's rule), because the host id is `ext-<panel.id>`. Field errors are `invalid-service` with the failing field first.
- The contribution is `.strict()`: `label`, `instances` (`fixed` origin or `user`-typed), and the Git host's `token` block with its two refines (`private-token` ↔ `none`, `basic` ↔ `username`). `toPublicNotifications` is what the catalog row and the approval dialog carry; it drops nothing secret because the contribution holds nothing secret.
- `readNotificationsProviderRequest` checks the envelope and the session (`instance`, `handle`, `account` of `{ id, login | null }` or null); the host built `input`. The answer envelope is the Git host's: `ok/data` or `ok/error { message, status?, code? }`, so a 401 is written off only when the proxy saw it.
- `createNotificationsOutbound` and `createSourceControlForge` share one `postOutbound` and differ in the callback route (`NOTIFICATIONS_OUTBOUND_PATH`) and the error class, so the two roles cannot drift in how they reach the listener.

### Why the channel's account is OpenChamber's and not the service's

The ticket's rule for roles: host-derived id, host-owned accounts, Disable withdraws the provider and keeps its data. A token the service held would leave with the service, could be logged by it, and would survive a withdrawn approval; one OpenChamber holds travels only through the outbound proxy, pinned to the account's origin, and is forgotten with the extension. It is the Git host's model reused, with the same handle.

### Why no switch on the Notifications page

The maintainer chose approval as the switch: an approved extension with a connected account delivers, a paused one does not, and the Notifications page's existing toggles already say which kinds exist. A per-channel switch or a kind-by-channel matrix would be a new setting with its own storage and sync; the ticket's open question about routing is answered by having none in v1.

## Tracker role

`provides: ["tracker"]` plus `contributes.tracker` (`TrackerContribution`, `manifest.ts`) make an extension a work item tracker next to Linear. The SDK owns the manifest parse (`trackerSchema` in `parse.ts`, `isTrackerUrlTemplate` in `manifest.ts`), the wire (`service-providers.ts`: `TRACKER_PROVIDER_PATH`, the nine `TRACKER_PROVIDER_METHODS` with the two writes in `TRACKER_PROVIDER_WRITE_METHODS`, deadlines and caps, the neutral item shapes, `readTrackerProviderRequest`, `createTrackerOutbound`) and the host's answer schemas (`trackerProviderSchemasV1`). The host side is `packages/web/server/lib/trackers/extension-*.js`; the service-side contract is in `GUEST_SERVICES.md`; `examples/tracker-provider` with its fake server is the reference, run by `scripts/tracker-provider-example.test.ts`.

- The role and the contribution come together: either alone fails as `invalid-service`, as does a `panel.id` longer than `TRACKER_GUEST_ID_MAX` (28), because the host id is `ext-<panel.id>`. A manifest that provides both `source-control` and `tracker` fails too: both roles would be that id in the one namespace tracked items and the read cache key by.
- The contribution is `.strict()`: `label`, `instances` (`fixed` origin or `user`-typed, the notifications role's shape), `auth` with `token` (the Git host's token block) and/or `oauth` (`authorizeUrl` and `tokenUrl` as https URLs or paths on the instance), `capabilities` with every flag defaulting to false, `stateFilters` starting with `open` and `all`, `identifier` (one of `TRACKER_IDENTIFIER_KINDS`) and `urls.item` templates. `toPublicTracker` is what the catalog row, the approval dialog and the account card carry; it drops nothing secret because the contribution holds nothing secret.
- Link templates are validated by `isTrackerUrlTemplate`, which lives in `manifest.ts` so the host can import it without zod: `{id}` once, in the path or as `?name={id}`, `{segment}` and at most one `{segments+}`. The host compiles them; an extension never supplies a regular expression, the Git host's rule.
- The neutral shapes in `service-providers.ts` are the UI's tracker contract without `provider`, which the host adds. `service-provider-schemas.ts` asserts each parsed shape against the type the service writes against, both ways, so the two cannot drift.
- A tracker extension without `contributes.integration` gets `ready.connection` and `onConnection` from the tracker's auth status (`trackerGuestConnection` in `packages/ui/src/lib/guests`), read through `useTrackerAuthStore`, so a disconnect on the card reaches its open frames at once. The frame reads it again when it mounts; another client's disconnect or a written-off account arrives at that read or at the app's next tracker refresh. The account file is OpenChamber's own and holds the credentials: a service never reads it.
- `readTrackerProviderRequest` checks the envelope and the session (`instance`, `handle`, `account` of `{ id, login | null }` or null, the notification channel's shape). The answer envelope is the Git host's, so a 401 is written off only when the proxy saw it.
- `createTrackerOutbound` shares `postOutbound` with the other two roles and differs in the callback route (`TRACKER_OUTBOUND_PATH`) and the error class.

### Why templates and identifier shapes instead of regular expressions

Tracker links differ widely: a key in the path, a key in a query parameter (Jira's `?selectedIssue=`), a bare number, a short code, a server under a path prefix. The maintainer kept the Git host's rule all the same: a regular expression from a package runs on every pasted link, on the server and in the UI, and JavaScript cannot bound its time. Templates with bounded placeholders and three identifier shapes cover those cases, and the matcher compiled from them is the one step 5 of OPE-367 (links in messages) reuses.

## Quota role

`provides: ["quota"]` plus `contributes.quota` (`QuotaContribution`, `manifest.ts`) make an extension a usage provider next to the built-in ones. The SDK owns the manifest parse (`quotaSchema` in `parse.ts`, `isOpenCodeProviderId` in `manifest.ts`), the wire (`service-providers.ts`: `QUOTA_PROVIDER_PATH`, the one `usage.read` method, `QUOTA_PROVIDER_TIMEOUT_MS` and the caps, `QuotaProviderCredential`, `QuotaProviderUsageData`, `readQuotaProviderRequest`) and the host's answer schema (`quotaProviderSchemasV1`). The host side is `packages/web/server/lib/quota/extension-quota.js`, attached to the quota registry by `extension-quotas.js`; the service-side contract is in `GUEST_SERVICES.md`; `examples/quota-provider` with its fake usage API is the reference, run by `scripts/quota-provider-example.test.ts`.

- The role and the contribution come together: either alone fails as `invalid-service`, as does a `panel.id` longer than `QUOTA_GUEST_ID_MAX` (28), because the provider id is `ext-<panel.id>`.
- The contribution is `.strict()`: `providers`, up to `QUOTA_PROVIDERS_MAX` unique OpenCode provider ids by shape, an empty list allowed. `toPublicQuota` is what the catalog row and the approval dialog carry.
- `readQuotaProviderRequest` checks the envelope and that `credentials` is a map of objects; the host built each entry from OpenCode's store. There is no session and no handle: the service reaches its provider's API itself.
- `quotaUsageDataSchema` is a built-in's result before the host derives the remaining share and the formatted strings, asserted both ways against `QuotaProviderUsageData`. Window and model names that would reach `Object.prototype` are refused, and zod leaves a `__proto__` key out of the record it builds.

### Why the service receives the credential and does not go through a proxy

The source-control, notifications and tracker roles keep the token in OpenChamber and hand the service a per-call handle, because each account uses one origin OpenChamber can pin. A usage API is the extension's own knowledge, a different one per provider, and the credential is not OpenChamber's: it is OpenCode's, held for the model calls already. The ticket decided the hand-over: the manifest names the providers, the dialog shows them, the user approves exactly that list, and the server hands only those entries, read through `opencode/auth.js`, never the whole store. A changed list asks again, as a new capability does.

## Services that act on their own

### Why the service's token is the callback bearer and not a capability of its own

The token already names one running process and leaves with it, and the service holds it from the start. A second secret would prove nothing the first does not. The address alone opens nothing, since each route asks for a bearer of its own, so every service now learns it; what a service may do is decided per call from the catalog, because a grant withdrawn from a process still running must end there.

### Why instructions sit on the server and not in a request to the service

`sync` runs before every message. A request to each service would put a process, its cold start and its failures on the send path, so the service writes the text when it changes and the send reads a file.

### Why a block is a frame and not a template or a host-drawn answer

Templates over the catalog, a render tree from a hidden frame, and views or images a service answers were each weighed. The first draws nothing an agent could not write itself. The second makes the list of allowed elements a contract forever, and still cannot draw freely. The third cannot react inside the chat. A sandboxed frame draws anything, reuses the panel's boundary, and is no more dangerous than the HTML a model already draws in a reply. `ExtensionBlockFrame` keeps its cost down: it mounts on screen and when finished, and a row that scrolls away gives its frame back.

### Why a mention reads its row when picked and not at send

A chip's text is what the agent reads, and the chip path already carries it, so reading at the pick reuses it and shows the failure while the user can still act on it. A read at send would need a new reference kind and a failure path through every sender. The text is as old as the pick.

## OpenCode plugin

`contributes.opencodePlugin` names a plugin folder the host hands to OpenCode. The host lists it in the OpenCode config file OpenChamber owns (`packages/web/server/lib/opencode/managed-config-file.js`, the same file that carries `contributes.skills`) while the extension is enabled, fully approved and not refused by enterprise mode, after OpenChamber's own plugins; a managed OpenCode watches that file and loads or drops the plugin within a couple of seconds, so Disable, a withdrawn approval and Remove take it out without a restart. The server tells the UI how that file reaches the OpenCode it works with, once per `GET /api/guests` as `opencodePlugins.delivery`:

- `file`: a managed OpenCode reading our file. The main path; the extension's screen shows nothing about the plugin.
- `restart`: the server's own environment sets `OPENCODE_CONFIG`, so the file is the user's and OpenChamber merges its plugins into `OPENCODE_CONFIG_CONTENT` instead; the plugin loads at the next OpenCode start. Only the server's shell environment makes this state: an `OPENCODE_CONFIG` set in Settings → Environment is replaced by the managed file.
- `none`: OpenChamber did not start this OpenCode (`OPENCODE_SKIP_START`, `OPENCODE_PORT` or `OPENCODE_HOST` on this machine), which reads neither.
- `remote`: an external OpenCode on another machine, which cannot load a folder from this one.

In `restart` and `none` the screen says so in the words settled on OPE-367 and offers **Add to global config** (`POST /api/guests/:id/opencode-plugin/global-config`), which writes the plugin folder as a path entry into the user's global `opencode.json(c)`, the file every OpenCode on the machine reads and watches, so an external OpenCode on this machine loads it within seconds too. From then on the entry is the user's: the screen names the file and sends them to Settings → Plugins to manage it, disabling the extension leaves it, and removing an extension installed from a ZIP or Git deletes the package folder, after which OpenCode lists the entry as a failed plugin and keeps running until the user deletes it there (checked live on OpenCode 2.2.5). Nothing copies the plugin anywhere to keep such an entry alive. In `remote` the screen says the plugin cannot be loaded there and offers nothing. A folder listed by the managed file and by the global config at once (the button pressed under `restart`, then a managed start) is loaded once by OpenCode 2.2.5 (checked live), so the host filters neither list.

Editing a folder install's plugin code while OpenCode runs: OpenCode used the new code on the next tool call without a restart or a config rewrite (OpenCode 2.2.5; the package watcher does not watch the plugin folder, so nothing is announced).

### Why not the user's global config automatically

That file is the user's. A plugin written there would outlive disabling the extension and even uninstalling OpenChamber, and would run in the TUI and every other OpenCode on the machine. The managed file is OpenChamber's, follows the extension's state, and reaches only the OpenCode OpenChamber runs; where it does not reach, the user is told and decides.

### Where it does not apply

VS Code and mobile load no extensions, so no plugin is delivered there and the manifest key is ignored with the rest of the catalog. A session inside an isolated space runs its own OpenCode in the container, with its own config layers; the host's managed file and global config never reach it, so an extension's plugin is absent from every session in a space.

## Links in messages

`contributes.links` lets an extension claim identifiers (`DEMO-12`) and links (`https://tasks.example.com/tasks/DEMO-12`) in chat messages. The server copies the declaration onto the catalog row compiled (`packages/web/server/lib/guests/links.js`, `toPublicLinks`): the literal keys, and the link templates turned into anchored patterns by the tracker's compiler (`compileTrackerUrlTemplate`), so the UI runs patterns it never compiled from package text. A template the compiler refuses drops that row's links and keeps the row.

- Only an extension that is on, fully approved and granted `links` claims anything (`guestLinkRulesOf`, `packages/ui/src/lib/guests/links.ts`). Between two extensions claiming the same key or link, catalog order decides.
- Recognition runs in assistant text parts and in the user's own Markdown messages, through the renderer's `guestLinks` prop; reasoning, tool output, Files, Plan, previews, copies and image exports never get it, so a copy keeps the text as written.
- An identifier is a whole word: nothing inside a word, a path, a URL, a version, inline or fenced code, or an author's link (`remarkGuestLinks`). It renders as a link with no address carrying `data-oc-guest-link`, an attribute only that parser can set (`rehypeMarkdownPolicy`), so copying gives the plain `DEMO-12`.
- A link is claimed only on its https origin exactly (port included, no `www.` folding, no credentials). The `GuestLinkItem.url` handed on keeps the path and only the template's own query parameter, never the fragment or other parameters, which can carry tokens. A link longer than `GUEST_ATTACH_URL_MAX` (2000) stays an ordinary link, since neither the item nor the chip carries it.
- The app's own readers win: a link that is a tracker item, a repository issue or change request, or a commit keeps its route (`isBuiltInLink`, read at click). A modified click keeps the browser's meaning.
- `open` routes by the attach mode (`openGuestWithItem`): the dialog, or the rail panel, which only opens and never toggles closed. With no project open nothing opens and nothing is parked for a later rail click: a clicked link then opens as any link does, and an identifier, which has nowhere else to go, shows a toast saying to open a project. `attach` puts a composer chip with the identifier as its title and the link its template names. An identifier in text fills the template only when it has `urls.identifier`'s shape; otherwise an `open` click hands it on with no `url`, and an `attach` claim stays text.
- A message already on screen re-parses when the rules change: the renderer passes `data-oc-guest-links`, a mark that changes with the rules, because streamdown's root re-renders on content and `data-*` props, not on a new plugin list.

### Why keys and templates instead of regular expressions

The tracker role's reason: a pattern from a package runs on every message the user reads, and JavaScript cannot bound its time. Literal keys and the tracker's templates cover the cases that came up, and the host owns every expression that runs.

### Where it does not apply

VS Code, mobile and the desktop mini chat window load no extensions, so nothing is claimed there. A message the app shows outside the chat transcript (a session preview, a notification) stays text.

## Session events

`contributes.sessionEvents` (`SessionEventsContribution`, `session-events.ts`) subscribes a package's service to what happens in the user's sessions: `events` is 1 to 8 distinct of `GUEST_SESSION_EVENT_TYPES`, and `content: true` asks for the `transcript` capability. The host posts one `GuestSessionEventRequest` per event per subscribed service to `SESSION_EVENTS_PATH`, from every project, with no window open; the service answers `GuestSessionEventResult`. The server side (`packages/web/server/lib/guests/session-events.js`) decides who is a subscriber from the catalog at delivery time and gates `turn-finished` the way the ready notification is gated. The service-side contract is in `GUEST_SERVICES.md`; `examples/session-events-log` is the reference, run by `scripts/session-events-example.test.ts`.

- `sessionEvents` needs `contributes.service` (`invalid-session-events`), its object is `.strict()`, and it joins roles, surfaces and status sources in freeing the service from needing a frame (`runtimeContributions`). A bad shape is `invalid-session-events` too; the message names the field.
- `transcript` is never declared under `contributes.capabilities`: `requestedGuestCapabilities` adds it from `sessionEvents.content`, and the approval dialog shows it as its own row with the event list under the service row (`PublicSessionEvents`, `toPublicSessionEvents`, on the catalog row as `sessionEvents`).
- `readSessionEventRequest` checks the envelope, the type, the session, the project, the `linked` list's shape and that a `content` has the event's type; the host built the rest. A content of another type than the event is `null`, not a surprise for the handler.
- The answer envelope `{ ok: true } | { ok: false, error }` is the one the browser role answers; `sessionEventResultSchema` is `.strict()`, so an answer with extra data is a failed delivery, never a delivered one.

### Why metadata rides on the `service` grant and only content gets a capability

A service already runs as the user with no sandbox and could read OpenCode's storage itself, so a grant for identifiers would promise a confinement the host cannot give. What the grant can say truthfully is what OpenChamber hands over on its own: the events (recorded in the service grant's scope, so a widened list asks again) and, as a line the user reads separately, the text (`transcript`). The ticket's rule, metadata without an extra grant and content with one, maps to exactly these two.

### Why every project is sent and not a host-side project filter

A filter the host keeps per project would be a new control on the card and a new store that must follow worktrees to their project; the extension's own settings and storage already hold its configuration, and `event.project.directory` is on every request. The host sends everything and the extension drops the rest; the maintainer chose this over per-project settings in OpenChamber.

### Why `turn-finished` waits for the session to want nothing

The ticket's example posts a comment on the linked issue when the agent finishes. A parent idle while its subagent still works, a turn that ended by asking a question, a goal loop's intermediate steps and an auto-review's steps are not that moment; the ready notification already decides it with those gates, so the event uses the same ones, and the asked/settled events the server already sees keep the open asks.

## Late generate answers

`LateGenerateResult`, `ready.features.lateGenerateResults`, the guest notice `generate-late-listen` and the host push `generate-late` live here; `HostClient.onLateGenerateResult` sends the notice on registration and again on every `ready` while a listener exists. The UI host owns keeping: `packages/ui/src/lib/guests/generate-results.ts` holds the outcomes, `PluginPane` decides when a `generate` reply has no frame to go to and registers a listening frame.

- A `generate` reply goes to the frame that asked while the pane still owns that frame and no later document in it has said `hello` (`PluginPane` counts them). Otherwise it is kept. A reply that lands while a frame is navigating, before the new document's `hello`, still goes to the frame and is lost there.
- Hidden frames (slash-command resolvers, background actions) do not advertise the feature, ignore `generate-late-listen`, and keep nothing: they are no panel the user pressed a button in, and a resolver frame would otherwise take an answer meant for the visible panel.
- A kept outcome belongs to runtime, extension id, installation `storageId`, surface and project directory, and goes to a listening frame with the same owner, once. A frame that cannot take it leaves it kept.
- Bounds: `GUEST_GENERATE_LATE_KEEP_MS` (one hour), `GUEST_GENERATE_LATE_MAX` (8) per extension with the oldest dropped first, and 2 000 000 characters across all kept outcomes.
- A ready catalog of the same runtime that no longer has the extension active, approved for `model`, or with the same `storageId` drops its outcomes at once; a loading catalog or another runtime's catalog drops nothing.
- The request runs to the server's own deadline. No layer cancels it when the frame goes.

### Why keep the answer and not cancel the request

The user pressed Generate and asked for that text; closing a panel or switching project is not a request to throw it away. Cancelling end to end (issue #5040's first proposal) needs a cancel message, an abort path through the host bridge and the route, and still loses the answer. The maintainer chose delivery; the server's prompt-derived deadline stays the only limit on the work.

### Why the host keeps it in the window's memory and not on the server

The answer already comes back to the window that sent the request, and that window is where the user pressed the button, so the window can hand it to the next frame with no new route and no copy of model output on disk. A reload or another window starts empty; the request belongs to the window that sent it, and an app restart ends the request anyway. A server store would deliver to whichever client opened the panel first, a phone or another window.

### Why the owner includes surface and project

The outcome should appear where the user pressed Generate. Panel tabs are kept per project, so a panel in another project or an attach dialog of the same extension is somewhere else. A frame that follows the user across projects reads its current directory at each delivery.

### Why a listen notice and not a push to every reconnecting frame

An extension built against an older SDK has no listener, and a push it ignores would count as delivered. The frame asks only when its code registered `onLateGenerateResult`, and the host only advertises the feature it implements, so old guests and old hosts keep working unchanged.

## Where extensions plug in

Decided for every new integration point:

- OpenCode's own GUI plugins are not copied: they run in process with no sandbox.
- A new point is drawn by the host from data the extension supplies. The composer and sidebar rows get no extension frames. The one exception is a UI block in a chat reply (`contributes.blocks`), a sandboxed frame with the panel's grants.
- Agents pass over extension text that competes with OpenChamber's own guidance, so behaviour that must hold is a manifest flag the app turns into its own words (`blocks[].answers`, read by `describeExtensionBlocks` in `server/lib/guests/agent-context.js`), not instructions the extension writes.
- Sidebar session marks, when they come: an icon in a theme tone right after the PR badge, a click opens only that extension's panel, at most two per row and one per extension, no "+N".
- Rejected: native window embedding, native menu or tray items, arbitrary server routes, new items in the session row menu, a separate Settings page per extension, manifest tools the service answers, a chat secret form for extensions, and a check that runs before every send.

## Not here yet

`issues.search` / `issues.get` on the host, a public OAuth broker, a second `host.provider`, file watching or globbing from the guest (it gets `listDir` and `stat`, not a search). `attach` is the chip. `startSession` creates a session and writes that snapshot. `sessionLink` writes that snapshot on the current session. `prompt` writes or sends on that session. `onSessionLifecycle` is the live phase. Search and the task list live in the guest. `@openchamber/sdk/ui` is the drawing kit: buttons, fields, select, list, tabs, badges, banners, menu, and `mountText`. No issue page, card, attach picker, or PR window; the guest composes those from the blocks. `mountText` lifts `![alt](https://…)` and `[label](https://…)` and hands link clicks to `onOpenUrl`. `ready.theme.tokens` carries the host surface and interactive colors. Call `applyHostReady` before mount.

Keyboard shortcuts for extension commands: the palette lists them now, but the shortcut schema is static today.

Local services ship on `apiVersion: 1` (`contributes.service`, `serviceRequest`, grant UI, platform socket bindings + override). Contract detail: `GUEST_SERVICES.md`. Declared `sockets` / `exec` are shown on the grant card and do not confine the process; there is no sandbox for services. VS Code and mobile do not load guests or services yet.
