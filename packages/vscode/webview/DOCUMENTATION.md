# VS Code Webview

## Ownership

The webview renders the shared OpenChamber UI inside a VS Code webview frame. `main.tsx` wraps `window.fetch` to answer the OpenChamber routes the extension host owns, forward OpenCode routes over the bridge, and serve SSE from a bridge stream. `api/` builds the runtime API objects the shared UI calls for Git, files, settings, permissions, editor, notifications and source control. The extension host owns every operation that needs the editor, the filesystem, Git or OpenCode, plus delivery of editor comments and notifications. It keeps OpenChamber-owned session state (archive flags and metadata, which OpenCode 2.x has no route for), the project setup file and the small-model provider list, using the same files and rules as the OpenChamber server. The webview owns the browser-side route shapes and the state the shared UI keeps for one view's lifetime. Host-side delivery and Git rules are in [the backend modules document](../src/DOCUMENTATION.md).

## Invariants

- A broken webview slot can make `acquireVsCodeApi()` return undefined (Cursor after an extension update, VSCodium, headless). The bridge substitutes a no-op API that warns once and drops messages, and posts `webview:ready` once per document so the host retires streams left by a previous document after a reload or a move between windows.
- Messages the host does not answer go through `postBridgeNotification`. The request path keeps one pending entry per call until a response arrives, so a fire-and-forget message sent on that path leaks an entry on every call.
- Connections the host owns have no bridge timeout: proxy reads, session messages, worktree removal and teardown, a worktree create that runs a project command, and a Git transfer. A shorter deadline reports a failure the host may still complete and frees the webview to start another operation beside it. Teardown commands get five minutes on the host, and a project create command can run for minutes.
- Remote URLs lose their userinfo, query and fragment before display and before fingerprinting. Fingerprints only need equality within one repository, so FNV-1a is enough.
- Remote branch deletion is the only Git network operation. It runs through system Git on the host with the user's own credentials. Before it executes, the webview reads the remotes again and requires the same repository, push endpoint and config revision; a change ends the operation as `conflicted`.
- Git identity profiles live in webview memory for the life of the view. The host stores nothing and no code applies a profile to a repository in this runtime.
- Local route shapes and status codes mirror the web server. Plugin entry writes answer 400 `UNLOADABLE_SPEC`, 409 `SWITCH_UNAVAILABLE` or `SWITCH_OVERRIDDEN`, and a taken snippet name answers 409; a validation failure answers 400 and any other host failure 500. The provider list is an authoritative empty list, not a failure. Directory permission requests and `/auth/session` report success because VS Code already trusts the host and its workspace.
- Features with no VS Code equivalent answer a deterministic unsupported shape instead of reaching OpenCode: the terminal API throws, TTS reports unavailable and its speak routes answer 501, dictation reports unavailable and its other routes answer 501 (the mic button hides itself when capture is unsupported), and the quota extensions route returns an empty list because VS Code loads no extensions.
- Magic Prompts keep their selectors in the query string and forward every value of a repeated name so the host can refuse a repeat. The routing directory plays no part in which file is read or written; a prompt read names its directory as `sessionDirectory`.
- OpenCode 2.x serves its own routes under `/api`, so a forwarded path keeps its prefix. It has one event stream at `/api/event` and takes a prompt at `/api/session/:id/prompt`. It has no health route of its own: `/health` reflects the extension's connection status and `/api/info` is forwarded like every other API call.
- A config entity path treats its last segment as a resource only for `config` and `permissions`. An entity name contains no slash after decoding, so that segment is the resource when it is one of the two.
- Session status comes from the host's activity watcher. Its retry and busy phases collapse to `busy`, cooldown settles a session, and the host sends the turn's age rather than a timestamp so the webview anchors it on its own clock and a remote host's clock cannot move the timer. The host keeps no pending-request map, so `pending` stays empty.
- The SSE listener is installed before the host opens the upstream stream. A reconnect can replay an event before the start response crosses the bridge.
- OpenCode 2.x delivers questions as forms: one titled request the user answers. A `form.created` event drives the question notification.
- Inline comments file under the draft key the composer reads for the current session, or `draft` while a new-session draft is open. The editor thread mints the draft id so it can track its own draft without a round trip; a comment from any other entry point carries none. A session panel is told which session the comment is for and waits until it shows that session, while the sidebar files wherever its composer is. A panel knows its directory before it selects its session, and filing on the first snapshot with a directory uses `draft`, a key that composer never reads; the handler waits up to 20 seconds for the surface to show the session. Session and directory are read from one store snapshot, because a session that finishes loading between two reads pairs its key with the previous session's directory.
- A comment removed in the editor is remembered in a bounded tombstone list of 50 ids. Delivery is asynchronous on both sides, so the removal can arrive before the draft: `remember` runs even when the draft is already in the store, where the store removal is the normal path. `consume` runs after the wait and before the draft is filed, and clears the record. The list is not state: ids are unique and an entry is never revisited after its delivery window.
- Editor threads mirror the draft store as a whole snapshot rather than add and remove events. A dropped notification cannot leave a thread anchored to a comment that is no longer attached, and sending the snapshot empties the list, which clears the threads through the same path.
- A draft written from the editor carries `written: true`. VS Code has already emptied its comment field, so a refusal would lose the text.
- Removing a comment searches the owning draft key only in the current runtime. `removeDraft` recomputes the key from the live runtime, so a key rebuilt from another runtime would delete from the wrong place. `resolveCommentTarget` returns null while the surface is booting or while a session panel shows another session.
- VS Code updates webview CSS variables asynchronously around a theme change, so the palette is read again on the next two animation frames.
- A workspace sets `directoryTreeShowHidden` to `true` and `filesViewShowGitignored` to `false` only when no stored choice exists.
- A percent sequence in `x-opencode-directory` is decoded only when `x-opencode-directory-encoding` is `uri`, so a raw sequence from another caller stays untouched.
- The extension host shows notifications because Chromium never displays `new Notification()` from a VS Code webview frame. Whether the user sees the chat comes from the host's viewer state, not from the webview document's focus. Empty template fields fall back to the localized default, and a permission ask passes its own defaults so it does not inherit the shared question label. The host's auto-accept policy is on or off, and `on` reads as `auto`.
- The loading overlay hides once the UI is mounted and OpenCode is connected. It does not wait for provider and agent fetches, the slowest part of a cold start, which would keep the splash up after the app is usable. The connecting status text stays empty because the animated logo shows progress. A failed UI bootstrap still removes the overlay so the error in the root stays visible.

## Decisions

### Why the webview projects remotes as a System binding and not providers

VS Code has no source-control binding store and manages Git hosting providers itself. Shared Git surfaces read a repository context and a binding before any network operation, so the webview builds a ready System-transport binding from the repository's remotes and system Git transfers with the user's own credentials. Provider operations stay unsupported and never reach the OpenCode proxy. The GitHub identity gives shared auth consumers an explicit checked state.

### Why host-owned operations have no bridge deadline and not a fixed timeout

A deadline shorter than the host's operation reports a failure while the host keeps working. A teardown can still remove the worktree and a Git transfer can still succeed after the webview gave up. The deadline also frees the webview to start a second operation beside the first. These operations settle when the host answers, and the original fetch signal still ends a proxy request.

### Why removal tombstones and not an event queue

The extension can deliver a comment before this document's store exists, and the removal can arrive while that delivery waits for a directory. A tombstone lets the delayed delivery recognise a comment the user already dropped. An event queue would have to name the delivery it cancels and would outlive its purpose.

### Why the comment handler waits for the target session and not the first directory

Inline drafts are keyed by runtime, directory and session. A panel that has just opened knows its directory before the session list loads, and filing there uses `draft`, a key its composer does not read, so the chip never appears while the editor thread reports it attached. Waiting for the session, within the extension's confirmation deadline, keeps the draft under the key the composer reads.
