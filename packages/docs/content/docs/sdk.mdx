# Build an extension

Use `@openchamber/sdk` to add your own panel to OpenChamber. An extension is a small web page that OpenChamber shows on the right-hand rail. It talks to the app through `connectHost()`: it can read the current project and session, show toasts, put text in the chat box, attach a task to a session, and, with the user's approval, start sessions and send prompts.

Extensions run in OpenChamber web and desktop. VS Code and mobile do not load them yet.

## What an extension is

A folder with three files:

- `package.json` with an `openchamber` block (the manifest)
- `panel/index.html`, the page OpenChamber shows
- `panel/main.js`, your script, built into a single classic file (an IIFE, not an ES module, because the page loads in a sandboxed iframe)

OpenChamber never compiles your code. Ship the built `.js` file. The SDK includes a bundler command; any bundler that outputs an IIFE works too.

```bash
npm install @openchamber/sdk
bunx openchamber-guest-bundle panel/main.ts panel/main.js
```

The bundler command runs on Bun. Without Bun, use esbuild or any other bundler with `--format=iife --platform=browser`.

A complete working extension, all three files, is on the [Example](/sdk/example/) page. Copy it and change the API and the list.

Point `index.html` at `main.js` with a normal `<script src="main.js"></script>`.

## Install it while you work

1. Run OpenChamber on web or desktop.
2. Open Settings → Extensions.
3. Paste the absolute path of your folder and click Add.

OpenChamber reads the manifest and shows a dialog listing what the extension asks for (see [Capabilities](#capabilities)). Approve it, and your icon appears on the rail. Click it and your page loads.

You can also add a local `.zip` or an https link to a git repository or a zip file. A git install is the one that can update: raise `version` in `package.json` and push, and OpenChamber checks soon after it opens and every few hours, tells the user once, and offers the update in Settings → Extensions. A link to `openchamber://extensions/install?url=<encoded repository URL>` on any page opens the desktop app with that repository in the add dialog, so you can offer an install button. A `#tag` or `#branch` on the URL pins which one it follows. Those are copied into OpenChamber's data folder and run from that copy, so ship the built files, not `node_modules` or TypeScript sources. Removing the extension deletes the copy. A folder install runs from your folder directly, so you can edit, rebuild, and reload.

## Manifest

```json
{
  "name": "@acme/hello",
  "version": "1.0.0",
  "openchamber": {
    "apiVersion": 1,
    "engines": { "openchamber": ">=1.24.0" },
    "id": "acme-hello",
    "name": "Hello",
    "icon": "window",
    "contributes": {
      "panel": { "entry": "panel/index.html" },
      "attach": "dialog",
      "page": true,
      "capabilities": ["prompt", "sessions"],
      "integration": {
        "name": "Acme",
        "description": "Tasks from Acme",
        "token": {
          "apiOrigin": "https://api.acme.example",
          "account": { "path": "/me", "name": "login" },
          "scheme": "bearer"
        },
        "settings": [{ "id": "list-id", "label": "List ID" }]
      }
    }
  }
}
```

`version` is required and must be semver. Settings → Extensions shows it on the card.

`apiVersion` is `1`. OpenChamber refuses any other value.

`engines.openchamber` is optional. Set the oldest OpenChamber version your extension works with, as `1.24.0` or `>=1.24.0`. Older builds refuse to install it instead of failing later.

`id`, `name` and `icon` name the extension. `id` is kebab-case and must be unique among installed extensions. `icon` is a Remixicon name (`RiWindowLine` becomes `window`) or an SVG file inside your folder, like `icon.svg`. `contributes.panel` is the extension's panel on the rail: its `entry` is the HTML file inside your folder. An extension with no rail panel leaves `panel` out. Older packages keep `id`, `name` and `icon` inside `panel`, and that keeps working.

`contributes.attach` is optional. It adds your extension to the + menu next to the chat box, so the user can pick a task and attach it to a session.

- `"dialog"` opens your page in a window
- `true` or `"panel"` opens the rail panel instead
- `{ "mode": "dialog", "entry": "panel/attach.html" }` opens a separate page of yours in the window, so the picker does not have to share code with the rail panel
- omit it and the extension stays off that menu

Your page can tell where it is from `ctx.surface`: `panel`, `dialog`, `page`, `status`, or `block`. When the user clicks an attached item, its `data` comes back in `ctx.item`. Opening from the rail, + menu, or full-screen page menu starts without an item.

`contributes.page: true` makes your panel available full-screen from the Extension pages menu above the session list. Use `{ "entry": "panel/page.html", "title": "Board" }` for separate HTML and an optional title. Ship that HTML and its built scripts. `true` reuses `panel.entry`; a page with its own `entry` needs no rail panel, so an extension can be only a full-screen page. A page uses the same sandbox and permissions, and opens only when the user selects it. Reload, pause, removal, or a server switch closes it.

For a board, use `host.storage` for persistent JSON and the project/worktree/session methods for shared app data. `startSession` can target another project or worktree without closing the board. See [Host API](/sdk/host/) for subscriptions, live states, and partial creation results.

`contributes.integration` is optional. It adds a card at Settings → Integrations where the user connects an account. See [Accounts and network](#accounts-and-network).

`contributes.service` is optional. It declares a local process OpenChamber starts next to the extension, for things a web page cannot reach, like a Docker socket. That process runs with the user's full access and no sandbox, so the approval dialog warns about it; declare one only when the page cannot do the job. See the package file `GUEST_SERVICES.md`. A service with `provides: ["browser"]` can also stand in for the agent's browser: it answers the `browser.*` actions on the server, so agents browse with no desktop app open, and the user picks it under Settings → OpenChamber Tools. Such a service needs no panel. A service can also be told what happens in the user's sessions: declare `contributes.sessionEvents` next to it, and OpenChamber posts each turn that finishes or fails and each permission or question the agent asks to the service, from every project, with no window open. See [Session events](/sdk/host/#session-events). And a service with `provides: ["notifications"]` delivers the user's notifications next to the desktop and the phone, to Slack, Matrix or a server of your own; the user connects the account in Settings → Integrations and the token stays in OpenChamber. See [Notification channels](/sdk/host/#notification-channels). A service with `provides: ["tracker"]` is a work item tracker next to Linear, with its account card under Extension accounts; see [Trackers](/sdk/host/#trackers). And a service with `provides: ["quota"]` reports usage next to the built-in providers, reading the credentials OpenCode holds for the providers it lists in the manifest; see [Usage providers](/sdk/host/#usage-providers).

## Capabilities

Drawing a panel and reading the current session need no permission. Anything that acts on the user's behalf does. List those in `contributes.capabilities`:

| Capability | What it allows |
| --- | --- |
| `prompt` | send messages into the user's session (`prompt({ send: true })`, `startSession` with `text`) |
| `sessions` | list projects, worktrees, and session states; create and open sessions across registered projects |
| `files` | read and write files inside the open project (`readFile`, `writeFile`, `listDir`, `stat` with a relative path) |
| `model` | one-off text generation with the user's Small Model (`generate`), outside any session |
| `shells` | watch the shell commands your agents run in the background, read their output, and stop them (`onRunningShells`, `readShellOutput`, `stopShell`) |

Twelve more are added for you: `network` when you declare an `integration`, `service` when you declare a `service`, `filesystem` when you declare `filesystem` patterns, `origins` when you declare `origins`, `conversation` when a session action asks for the messages (see [Actions, commands, and the badge](#actions-commands-and-the-badge)), `transcript` when `sessionEvents` or `sessionControl` asks for `content` (see [Session events](/sdk/host/#session-events)), `sessionControl` when your service acts on sessions (see [Calling OpenChamber](/sdk/host/#calling-openchamber-from-your-service)), `sessionAnswers` when it answers the agent's permission requests and forms for the user (`sessionControl: { answers: true }`), `instructions` when it adds to what agents read, `skills` when you declare `contributes.skills`, a package folder of skills that reach every agent while the extension is on, `opencodePlugin` when you declare `contributes.opencodePlugin` (see [An OpenCode plugin in your package](#an-opencode-plugin-in-your-package)), and `links` when you declare `contributes.links` (see [Links in chat messages](#links-in-chat-messages)).

The user sees the full list once, when they install the extension, and approves it or removes the extension. If a new version asks for more, the dialog appears again. A call that needs a capability the user has not approved fails with `NOT_GRANTED`.

## An OpenCode plugin in your package

An extension can ship an OpenCode plugin, so people install one thing instead of two. Declare `"opencodePlugin": "plugin"`, a folder inside the package with `index.js` or `server.js` at its root. OpenCode does not read `main`, so for an entry anywhere else give the folder's `package.json` a `name` and `exports`. The entry default-exports `{ id, setup }`, the shape OpenCode loads; it imports nothing, because OpenCode loads it with a bare `import()` from your folder, where nothing is installed. A tool's `input` is plain JSON Schema, and its `execute` answers `{ content }`.

```json
{
  "contributes": {
    "panel": { "id": "teapot-tools", "name": "Teapot Tools", "icon": "cup" },
    "opencodePlugin": "plugin"
  }
}
```

The approval dialog gets one more row, **Add a plugin to OpenCode**, which says plainly that plugin code runs inside OpenCode with the user's full access. Once allowed, OpenChamber lists your folder in the OpenCode config it manages, the same file that carries `contributes.skills`; the OpenCode it runs watches that file and loads the plugin within a couple of seconds. Disabling or removing the extension takes the plugin out the same way. Nothing is written into the user's own `opencode.json`: that file is theirs, and a plugin there would outlive your extension and run in every OpenCode on the machine.

Where that file does not reach OpenCode, the extension's screen says so and offers **Add to global config**, which writes your folder into the user's global OpenCode config as an entry they own from then on. That happens when OpenChamber did not start the OpenCode it talks to, or when the server's environment sets its own `OPENCODE_CONFIG` (the plugin then loads at the next OpenCode start). An OpenCode on another machine cannot load a folder from this one; the screen says so and offers nothing. A plugin that fails to load is reported by OpenCode on Settings → Plugins when it has an entry there; your extension keeps working either way. The install refuses a package whose plugin folder is missing or whose `package.json` names no entry file.

VS Code and the mobile apps load no extensions, so no plugin reaches them. A session inside an isolated space runs its own OpenCode, which never reads the host's config. Enterprise mode treats the plugin like a local service: it installs only from a repository the administrator listed. The SDK has a working example, `examples/opencode-plugin`.

## Links in chat messages

An extension can make its identifiers and links clickable in chat messages, so `DEMO-12` in an agent's reply opens that task in your extension instead of a browser tab. Declare what to recognise and what a click does:

```json
"links": {
  "action": "open",
  "identifier": { "keys": ["DEMO"] },
  "urls": { "origin": "https://tasks.example.com", "identifier": "key-number", "item": ["/tasks/{id}"] }
}
```

- `identifier.keys` are up to 8 literal upper-case keys. `DEMO` claims `DEMO-12` as a whole word; code, links, paths, and words like `XDEMO-1` or versions like `DEMO-1.5` stay text.
- `urls` claims links on one https origin, matched exactly. `item` are link templates in the tracker's form: `{id}` once, in the path or as `?name={id}`, and `{segment}` or `{segments+}` for parts that vary. `identifier` says what `{id}` looks like: `key-number`, `number`, or `short-code`. You never write a regular expression; OpenChamber compiles the templates.
- `action: "open"` opens your extension with `ready.item` (or `onItem`) set to `{ kind: "link", identifier, url? }`: in your dialog when `attach` is `"dialog"`, otherwise in your rail panel. Narrow it with `isGuestLinkItem`. It needs `panel.entry`. `url` is the clicked link without its fragment and without query parameters other than the template's own; for an identifier in text it is the link your first template without `{segment}` names, when you have one and the identifier has the shape `urls.identifier` declares (`DEMO-12` never fills a `number`).
- `action: "attach"` puts a chip with the identifier on the composer instead, and needs a template without `{segment}` or `{segments+}` so the chip can name its link; with `identifier.keys`, `urls.identifier` can't be `number`.

Recognition runs in agent replies and in the user's own messages, not in reasoning, tool output, or the Files view, and copying a message keeps its text as written. A link OpenChamber reads itself, a tracker item, a repository issue or pull request, or a commit, keeps its usual route, and a click with a modifier key keeps the browser's meaning. Declaring `links` adds the `links` capability: the approval dialog lists your keys and origin and says what a click does, and a version that changes any of them asks again. `examples/tasks-demo` recognises `DEMO-2` and `https://example.com/tasks/DEMO-2`.

## Generate text

With the `model` capability, `host.generate` asks the user's Small Model for a one-off answer: a summary, a title, a draft. Nothing enters a session, no history is kept, and the extension never picks a provider. OpenChamber uses the same model it uses for its own background work, chosen in Settings → Sessions → Small Model, or the small model of the provider the user is working with, or the default model from their OpenCode config.

```ts
const { text } = await host.generate({
  prompt: task.description,
  system: "Write a one-line summary. Return only the summary.",
  maxOutputTokens: 200,
});
```

When no model is available the call fails with `NO_MODEL`; a model that errored is `MODEL_FAILED`. Prompts are limited to 64,000 characters, and the call waits up to 960 seconds. The user sees this permission as "Use your Small Model" and it costs them tokens, so keep prompts short and call it on a click, not on every keystroke.

## Accounts and network

Your page runs in a sandbox and cannot reach the network on its own: scripts, styles, images, fonts and media load only from your package, and `fetch` reaches only your package's files. Ship fonts and images inside the package rather than loading them from a CDN.

To talk to an outside service, declare an `integration` and OpenChamber makes the calls for you through `host.request`, with the user's token attached. The token never reaches your page.

For anything else your page needs directly, such as fonts or images from a CDN or a public API, list up to 8 https origins:

```json
"origins": ["https://fonts.example.com"]
```

The user sees them on the approval dialog as addresses your extension can send data to and receive data from, and approves them again if an update adds one. Approved origins are open to `fetch`, images, fonts, styles and media, but never to scripts: code has to ship in your package. The page's origin is `null`, so to read a `fetch` response the server must allow CORS for that origin.

In [enterprise mode](/security/#enterprise-mode), an extension with `origins`, an `integration` or a `service` installs only from a Git repository the administrator listed. If your extension can work without them, it stays installable for those teams. To build one on such a machine, ask the administrator for `allowLocalExtensions`, which lets you install it from its folder.


- `token`: the user pastes an API token on the Settings → Integrations card. `apiOrigin` is the only origin `request` may call. `account` is optional: a GET path and a field name, so the card can show who is connected. `scheme` says how the token is sent; see the table below. Check the provider's API docs for which header it expects.
- `oauth`: the user pastes a client id, and OpenChamber runs the authorize flow. Needs `authorizeUrl`, `tokenUrl`, and `apiOrigin`.
- `host: { "provider": "linear" }`: reuse the Linear account already connected in OpenChamber. No client id needed.

What each `scheme` sends:

| `scheme` | Header OpenChamber sends | When to use it |
| --- | --- | --- |
| omitted | `Authorization: <token>` | the API documents a bare token in the header |
| `"bearer"` | `Authorization: Bearer <token>` | the API documents a bearer or personal access token |
| `"basic"` | `Authorization: Basic base64(username:token)` | the API documents HTTP Basic auth with a username (often an email) and an API token; the card asks for both, and `usernameLabel` names the first field |

`settings` adds plain text fields to the card. Their values arrive in `ctx.settings`. A field with `"secret": true` is masked on the card and never reaches a page; your service reads it with `readSettings()`.

## Files

Your page cannot touch the disk itself. OpenChamber reads and writes for it, inside limits the user approved.

- A relative path (`README.md`, `src/index.ts`, `.`) means the open project. Needs the `files` capability. No open project is `NO_DIRECTORY`.
- A path starting with `/` or `~/` means anywhere else. It must match one of the patterns you declare in `contributes.filesystem`, and the user sees those exact patterns in the approval dialog:

```json
"filesystem": ["~/.config/opencode/opencode.json", "~/notes/**"]
```

Patterns use `*` for one path segment and `**` for any depth. Anything outside them is `BAD_PATH`, even after approval. `..` is never allowed.

```ts
const config = await host.readFile("~/.config/opencode/opencode.json");
await host.writeFile("~/.config/opencode/opencode.json", nextJson);
const { entries } = await host.listDir(".");
```

Writes are atomic: OpenChamber writes a temporary file and renames it, so a reader never sees a half-written file. Files are read and written as UTF-8 text, up to 2 MB.

## A section in Work Status

`contributes.statusSection` adds your own section to the Work Status panel next to the chat. Users turn it on and off and move it in that panel's section list, like the built-in sections.

```json
"statusSection": { "entry": "status/index.html", "title": "Recent commits", "height": 160 }
```

- `true` reuses `panel.entry`.
- `entry` is a separate HTML page in your folder. With it you don't need `panel.entry`, so the extension can be just this section, with no rail icon.
- `title` replaces the panel name in the section header, up to 60 characters.
- `height` is the starting height in pixels, from 24 to 480 (120 by default). Call [`host.setHeight()`](/sdk/host/) when your content changes size.

Your page sees `ctx.surface` as `status`. OpenChamber loads it only while the Work Status panel is visible and your section is expanded, and unloads it when the user collapses the section, so keep nothing there you can't rebuild. A section-only extension can use capabilities, a service, an integration, files, and a page with its own `entry`, but not `page: true`, `attach`, `actions`, or `commands`. Web and desktop only. The `git-graph-status` example is a complete section.

## An editor for your file type

`contributes.fileEditors` opens files in your page instead of the text editor. When the user opens a matching file in Files, OpenChamber shows your editor there, with the same source toggle, fullscreen button, and save button the built-in viewers have.

```json
"fileEditors": [
  { "id": "canvas", "title": "Excalidraw", "match": ["*.excalidraw", "*.excalidraw.md"], "entry": "editor/index.html" }
]
```

- `match` compares file names only, ignoring case. `*` matches any run of characters and `?` matches one. A pattern can't contain `/` and can't be only wildcards.
- `entry` is an HTML page in your folder. You don't need `panel.entry`, so the extension can be just the editor, with no rail icon.
- `content` is `"text"` (the default) or `"binary"`, see below.
- Up to 8 editors per extension, up to 16 patterns each.

OpenChamber keeps the file. Your page never reads or writes it and needs no capability for it. OpenChamber hands you the text, asks for the edited text when it saves, and handles Cmd/Ctrl+S, autosave, the unsaved-changes prompt, line endings, and changes made on disk:

```ts
import { connectHost, createFileSaveTracker } from "@openchamber/sdk";

const host = connectHost();
let tracker = createFileSaveTracker(null);

host.onFileOpen((file) => {
  if (file.encoding !== "text") return; // a text editor always gets text
  load(file.content); // file.path, file.name, file.readOnly too
  tracker = createFileSaveTracker(versionOf(currentText()));
});

// Call this after every edit. `edited` holds autosave back until the user stops.
const changed = () => host.reportFileChange(tracker.observe(versionOf(currentText())));

host.onFileSnapshot(() => ({ content: currentText(), version: versionOf(currentText()) }));

// Edits made while OpenChamber was writing keep the file unsaved.
host.onFileSaved((version) => host.reportFileChange({ dirty: tracker.markSaved(version), edited: false }));
```

`version` is any short string that changes when the document changes, such as a hash. If a file isn't something your editor can open, call `host.reportFileUnsupported()` and OpenChamber shows its source with a notice. Files over 20 MB stay in the source view.

### Binary files

Set `"content": "binary"` to open files that aren't text, such as spreadsheets, documents, or images. Your editor gets the file's bytes and hands bytes back; everything else works the same.

```ts
host.onFileOpen((file) => {
  if (file.encoding !== "binary") return;
  open(file.bytes); // a Uint8Array, exactly as on disk
});

host.onFileSnapshot(() => ({ bytes: currentBytes(), version: versionOf(currentBytes()) }));
```

A binary editor can claim any file its patterns match, including ones OpenChamber previews itself, like images and PDFs. It has no source view, and when the user moves it to or from fullscreen with unsaved changes, OpenChamber saves them first. Reading and writing the format is up to your editor: OpenChamber writes back exactly the bytes you return.

Your page sees `ctx.surface` as `file`. OpenChamber reloads it, with the file handed over again, when the file changes on disk, the user discards changes, or the editor moves to or from fullscreen. The first enabled extension whose pattern matches wins, ahead of OpenChamber's own previews. An editor-only extension can use capabilities, a service, an integration, files, and a page with its own `entry`, but not `page: true`, `attach`, `actions`, or `commands`. Web and desktop only. The `checklist-editor` example is a complete editor.

## Actions, commands, and the badge

Beyond the rail and the + menu, an extension can appear in three more places. All of them hand the extension an `item` the same way a chip click does.

**Actions on messages and sessions.** Declare menu entries and OpenChamber shows them next to the built-in ones:

```json
"actions": [
  { "id": "create-task", "label": "Create task", "icon": "add-line", "where": "message", "roles": ["assistant"] },
  { "id": "summarize", "label": "Summarize session", "where": "session", "payload": ["messages"] }
]
```

`where` also takes `selection` (text selected in a message), `file` (a row in Files) and `diff` (selected lines of a file or a diff). Their items carry `kind` of the same name: `selection` has the text, `file` the path, `diff` the path and the line range. On a selection, `display` says how the action shows: `label` (the default), `icon` with the label as its tooltip, or `both`.

A message action opens your extension with `ctx.item` of `kind: "message"`: the session id and title, the project directory, the message id, its role, and its text. A session action opens it with `kind: "session"` and the session id, title, and directory. Add `"payload": ["messages"]` and the item also carries the whole conversation, oldest first, the same text the Markdown export produces. That needs the `conversation` capability, which the user sees as a separate line in the approval dialog. `item.action` tells you which entry was clicked.

**Slash commands that attach.** Declare a command and handle it in the page:

```json
"commands": [{ "name": "task", "description": "Attach a task by id" }]
```

```ts
host.onResolve(async ({ command, args }) => {
  const task = await findTask(args.trim());
  return task ? { providerId: "acme-tasks", id: task.id, title: task.title, url: task.url } : null;
});
```

When the user types `/task ABC-12` in the chat box, OpenChamber asks your extension to resolve it and attaches what you return as a chip, without opening anything. Return `null` for "nothing found". If your panel is closed, OpenChamber loads it in the background for the call. A name that OpenChamber or OpenCode already uses is ignored.

Session actions and slash commands also turn up in the command palette (⌘P or Ctrl+P) when the user searches for the label, the command, or your extension's name. A session action there runs on the open session. A command goes to the start of the chat box, with what the user already typed as its argument, and runs when they send it. Message, selection, file, and diff actions stay in their own menus.

**Badge on the rail icon.** `host.setBadge(3)` puts a dot on your icon and the number in its tooltip, for example open tasks; `host.setBadge(null)` clears it. Opening the panel clears it too.

## Your tools in the chat

When your OpenCode plugin or MCP server adds a tool, the chat shows its calls with a generic icon and a raw output. Declare how they should look instead, with no code:

```json
"tools": [
  {
    "match": "jira_*",
    "name": "Jira",
    "icon": "task-line",
    "title": "{input.key}",
    "subtitle": "{output.status}",
    "output": "table",
    "columns": ["key", "summary", "status"]
  }
]
```

`match` is the tool name as OpenCode reports it; a trailing `*` matches a prefix. `icon` is a Remixicon name or an `.svg` file in your package, like `panel.icon`. `title` and `subtitle` are templates over the call's `input`, `output`, and `metadata`. `output` picks how the body renders: `text`, `json` (a tree), `markdown`, `code` with a `language`, `table` with `columns` (rows come from the output array or `output.items`), or `auto` for the default. An exact `match` beats a wildcard, and the first installed extension wins a tie. No permission is needed: this only changes how data already in the chat is drawn.

With OpenCode's Code Mode on, the agent calls tools from a short script instead of one by one. A script that makes a single call shows as that tool's row, and `output` is what the script returned. Write `match` with `_` where the script has a dot: `tools.github.list_issues` in a script is `github_list_issues`. A script that makes several calls keeps its own row.

An extension that only styles tools needs no page at all: leave out `panel.entry` and it has no rail icon, just a card in Settings → Extensions. Without a page it may declare `tools` and `providerLogos` and nothing else. A Work Status section, a file editor or a full-screen page with its own `entry` is the other exception, see above.

## Your provider's logo

When your OpenCode plugin registers a model provider, the model pickers and Settings usually draw a generic mark for it. Ship the logo in your package and name the provider, with no code:

```json
"providerLogos": {
  "acme-cloud": "assets/acme-cloud.svg"
}
```

The key is the provider ID as OpenCode reports it. The value is a `.svg` or `.png` in your package, up to 1 MB, and a missing, empty or larger file fails the install. A package names up to 256 providers, and two IDs can point at the same file. The logo keeps its own colours, and `currentColor` in an SVG follows the light or dark theme. It replaces a logo the app ships for that ID. Anything the user set for that provider comes first, and the first installed extension wins a tie. No permission is needed. VS Code and the phone load no extensions, so they do not show these logos.

## First lines in the panel

```ts
import { connectHost } from "@openchamber/sdk";

const host = connectHost();

host.onReady((ctx) => {
  document.body.dataset.theme = ctx.theme.mode;
  document.body.dataset.surface = ctx.surface;
});
```

`connectHost` only works inside OpenChamber. Opened as a plain file, every call rejects with `HOST_UNAVAILABLE`.
