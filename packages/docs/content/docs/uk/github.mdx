# Git-хости: issues і pull requests

Підключіть обліковий запис на хості, де живе ваш проєкт, і OpenChamber зможе показувати його issues і pull requests, починати сесію з одного з них, а також відкривати pull requests, робити їм рев'ю й зливати їх за вас. Вбудовано п'ять хостів: GitHub, зокрема GitHub Enterprise; GitLab, зокрема self-managed GitLab; Gitea; Forgejo, зокрема Codeberg; і Gerrit. [Розширення](/uk/extensions/#розширення-як-git-хост) може додати ще один.

Те, з яким хостом говорить OpenChamber, визначає remote проєкту. Проєкт, у якого `origin` на gitlab.com, використовує ваш обліковий запис GitLab для дошки, позначки pull request на своїх гілках і панелі Git. Remote на аліасі хоста з `~/.ssh/config`, наприклад `github.com-work`, не зіставляється з жодним хостом.

Слова залежать від хоста. GitLab каже merge request, а Gerrit каже change (зміна).

## Підключення хоста

1. Відкрийте **Settings → Integrations**. Кожен хост має власну картку.
2. Розгорніть картку хоста вашого проєкту й увійдіть:
   - **GitHub**: виберіть **Підключити GitHub**, відкрийте показане посилання, уведіть короткий код і підтвердьте. Для GitHub Enterprise виберіть **Додати екземпляр** у розділі **Інші інстанси**, уведіть адресу свого сервера й вставте personal access token.
   - **GitLab**: на gitlab.com увійдіть за коротким кодом, через personal access token або через вхід `glab`. Для self-managed GitLab додайте його адресу й вставте personal access token.
   - **Gitea**: додайте адресу свого сервера й вставте personal access token.
   - **Forgejo**: для Codeberg вставте personal access token; для іншого сервера спершу додайте його адресу.
   - **Gerrit**: додайте адресу свого сервера, потім своє ім'я користувача Gerrit і HTTP-пароль.

Коли підключення виконано, ваш обліковий запис показується на картці. На одному хості можна підключити більше одного облікового запису й перемикатися між ними або відключитися будь-коли. Якщо на цій самій машині виконано вхід у `gh` CLI, OpenChamber може використати його й для GitHub. Які scopes потрібні кожному токену і які версії потрібні кожному хосту, описано в [Інтеграціях](/uk/integrations/#gitlab-gitea-forgejo-і-gerrit).

Підключений обліковий запис також може бути [Git-ідентичністю](/uk/git-identities/) проєкту: тоді коміти мають його ім'я, а push через HTTPS використовує його токен.

## Початок роботи з issue чи pull request

Коли ви створюєте [сесію worktree](/uk/worktrees/), її можна почати з issue або pull request хоста проєкту:

- виберіть **issue**, і OpenChamber назве гілку на його честь
- виберіть **pull request**, і він викачає гілку цього pull request; ви можете включити його diff, щоб агент мав усю зміну
- виберіть **зміну Gerrit**, і він викачає її останній патчсет у гілку `change-<number>`

Нова сесія відкривається з елементом, уже прикріпленим до поля повідомлення. Нічого не надсилається за вас: виберіть модель і агента, напишіть, що треба зробити, і надішліть.

Дошка [Issues і PR](/uk/issues-and-prs/) показує ті самі елементи з фільтрами, попереднім переглядом, коментарями й рев'ю, і з неї теж можна починати сесії.

## Відкриття pull request'ів і керування ними

З вкладки **PR** у [панелі Git](/uk/git/) ви можете створити pull request, оновити його, позначити чернетку готовою чи злити її. OpenChamber може написати заголовок та опис із ваших змін.

- **GitLab**: та сама вкладка відкриває merge requests. Для злиття є merge і squash.
- **Gitea** і **Forgejo**: так само, як на GitHub.
- **Gerrit**: зміну створюють push'ем на рев'ю, і кожен наступний push завантажує новий патчсет. Див. [Push на рев'ю в Gerrit](/uk/git/#push-на-ревю-в-gerrit). Злиття тут називається **Подати**, і воно чекає, доки зміна не відповідатиме своїм вимогам до подання (submit requirements). Рев'ю тут означає голоси за мітки проєкту, наприклад Code-Review і Verified.

## Прикріплення issue чи pull request до повідомлення

У полі вводу чату відкрийте меню **+** і виберіть пункт прикріплення для свого хоста, наприклад **Привʼязати issue або PR з GitHub**, **Прив’язати issue або MR з GitLab** або **Прив’язати зміну з Gerrit**. Виберіть один чи кілька елементів. Кожен піде як контекст із вашим наступним повідомленням, pull request може взяти з собою свій diff, а панель статусу роботи сесії збереже посилання на нього. Прикріплення лише додає контекст; що з ним робити, каже ваше повідомлення.

У Gerrit немає issues, тому там показуються лише зміни.
