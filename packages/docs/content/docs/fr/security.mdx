# Sécurité

OpenChamber donne accès à votre machine et à votre code ; verrouillez-le donc avant que quelqu’un d’autre que vous puisse l’atteindre. Cette page couvre le mot de passe UI, les passkeys et ce qu’il faut savoir avant d’exposer OpenChamber sur un réseau.

## Définir un mot de passe UI

Démarrez OpenChamber avec un mot de passe et l’UI navigateur le demandera :

```bash
openchamber --ui-password be-creative-here
```

Vous pouvez aussi le définir avec la variable d’environnement `OPENCHAMBER_UI_PASSWORD` au lieu de le mettre en ligne de commande. Après connexion, OpenChamber mémorise l’appareil pendant un moment pour ne pas vous le redemander à chaque fois.

Définissez toujours un mot de passe si l’instance est joignable par quelqu’un d’autre — surtout via un [tunnel](/fr/tunnels/) ou internet public.

## Passkeys

Une fois un mot de passe défini, vous pouvez ajouter des passkeys (Face ID, Touch ID, clé de sécurité) pour vous connecter plus vite. Ajoutez-les dans **Paramètres → OpenChamber → Passkeys**.

Les passkeys sont liées au mot de passe actuel. Si vous changez ou supprimez le mot de passe, les passkeys enregistrées sont effacées et vous devrez les ajouter à nouveau.

## Tokens d’appareil

Les appareils associés via [Connecter un appareil](/fr/connect-devices/) s’authentifient avec leurs propres tokens par appareil, pas avec le mot de passe UI. Les liens d’association sont à usage unique et expirent s’ils ne sont pas utilisés ; chaque appareil associé est listé dans **Paramètres → Instances distantes → Se connecter à ce serveur**, où vous pouvez révoquer n’importe lequel à tout moment. Les connexions hors du domicile passent par le [Relais privé](/fr/private-relay/), qui est chiffré de bout en bout et ne peut pas lire votre trafic.

## Avant de l’exposer

- Par défaut, OpenChamber n’écoute que sur votre propre machine (`127.0.0.1`). Écouter plus largement demande un changement volontaire, et vous devriez définir un mot de passe d’abord.
- Pour vos propres appareils, préférez l’[association](/fr/connect-devices/) avec le [Relais privé](/fr/private-relay/) — rien n’est exposé publiquement du tout.
- S’il vous faut une URL publique, préférez un [tunnel](/fr/tunnels/) ou un réseau privé (comme un VPN) plutôt que d’ouvrir un port sur internet.
- Si vous placez OpenChamber derrière votre propre serveur HTTPS, consultez [Reverse proxy](/fr/reverse-proxy/).

## Mode entreprise

Si votre équipe ne peut envoyer le contenu des conversations qu’aux fournisseurs de modèles configurés dans OpenCode, activez le mode entreprise. Il y a deux façons de le faire, et une seule suffit.

### Un fichier de politique sur la machine

C’est la méthode à utiliser sur les portables que vous gérez. Placez un fichier nommé `policy.json` dans un dossier où seul un administrateur peut écrire :

| Système | Chemin |
|---|---|
| macOS | `/Library/Application Support/OpenChamber/policy.json` |
| Windows | `C:\ProgramData\OpenChamber\policy.json` |
| Linux | `/etc/openchamber/policy.json` |

Le chemin ne dépend pas de la façon dont OpenChamber est installé. L’application de bureau, le serveur web lancé depuis npm, la CLI et l’extension VS Code lisent tous le même fichier. Vous pouvez le déployer avec votre outil de gestion des appareils (Jamf, Intune et autres). Pour un serveur dans Docker, montez le fichier au chemin Linux.

```json
{
  "enterpriseMode": true,
  "organization": "Acme",
  "relayUrl": "wss://relay.acme.com/ws",
  "allowNetworkAccess": false,
  "allowedExtensions": ["https://github.com/acme/"],
  "jev": {
    "url": "https://llm.acme.com/v1/systemone",
    "model": "acme-classifier",
    "apiKey": "..."
  }
}
```

Seul `enterpriseMode` est nécessaire. `organization` s’affiche dans les Paramètres sous la forme « Géré par Acme », pour que chacun sache qui a pris la décision. `relayUrl` et `jev` fixent votre propre relais et votre propre point de terminaison Jev, `allowNetworkAccess` permet à d’autres appareils d’atteindre OpenChamber par le réseau, et `allowedExtensions` liste les dépôts d’extensions auxquels vous faites confiance. Tous sont décrits plus bas.

- Rien de ce qu’un utilisateur règle, dans les Paramètres ou dans l’environnement, ne désactive ce que le fichier active.
- Quand le fichier active le mode entreprise, seul le fichier décide. Les variables d’environnement ci-dessous pour le relais, Jev et l’accès réseau sont ignorées, car un utilisateur peut les définir lui-même.
- Si le fichier existe mais ne peut pas être lu ou n’est pas un JSON valide, le mode entreprise reste actif et rien n’est fixé. Les Paramètres indiquent que la politique n’a pas pu être lue. Un fichier cassé ne lève jamais la protection en silence.
- Les modifications s’appliquent sans redémarrage.
- OpenChamber tourne sous le compte de l’utilisateur, donc l’utilisateur peut lire le fichier. Pensez-y avant d’y mettre une clé d’API.

### Une variable d’environnement

Sur un serveur ou dans un conteneur, où vous maîtrisez l’environnement, ceci suffit :

```bash
OPENCHAMBER_ENTERPRISE_MODE=1
```

Sur un portable, c’est un verrou plus faible : l’application de bureau la lit dans le profil du shell de connexion (par exemple `~/.zshrc`), et l’utilisateur peut le modifier. Utilisez plutôt le fichier de politique.

Avec la variable, le relais, Jev, l’accès réseau et les extensions autorisées viennent eux aussi de leurs propres variables : `OPENCHAMBER_RELAY_URL`, `OPENCHAMBER_JEV_URL`, `OPENCHAMBER_ALLOW_NETWORK_ACCESS=1`, `OPENCHAMBER_ALLOWED_EXTENSIONS` (des URL de dépôts séparées par des virgules) et `OPENCHAMBER_ALLOW_LOCAL_EXTENSIONS=1`. Dans Docker, il vous faudra celle de l’accès réseau, puisque le serveur doit écouter au-delà du conteneur.

### Imposer la CLI OpenCode

Si OpenCode est déjà installé sur vos machines et qu’OpenChamber doit utiliser cette installation, indiquez son chemin dans le fichier de politique. Cela marche avec ou sans le mode entreprise.

```json
{
  "opencodeBinary": "/usr/local/bin/opencode"
}
```

- OpenChamber lance OpenCode uniquement depuis ce chemin. Il ignore le chemin des Paramètres, `OPENCODE_BINARY` et la copie fournie avec l’application de bureau, qui reste sur le disque sans servir.
- S’il n’y a rien d’exécutable à ce chemin, OpenChamber ne se rabat pas sur une autre copie. Il s’arrête avec une erreur qui donne le chemin.
- Les Paramètres affichent le chemin en lecture seule, avec une note indiquant que l’administrateur l’a défini.
- OpenChamber n’installe ni ne met à jour un OpenCode imposé et n’annonce pas les nouvelles versions. Les mises à jour arrivent avec votre déploiement.
- La CLI doit être OpenCode 2.x, au moins la version demandée par OpenChamber. Avec une version plus ancienne, OpenChamber s’arrête sur l’écran « mettre à jour OpenCode ».
- Un dossier fonctionne aussi, s’il contient `opencode` (`opencode.exe` sous Windows). Il n’y a pas de variable d’environnement pour cela, puisqu’un utilisateur peut les définir lui-même.


### Masquer les catalogues de skills intégrés

OpenChamber est livré avec quelques catalogues de skills publics (Anthropic, OpenAI, Cursor, Matt Pocock). Si votre organisation tient le sien, ajoutez-le comme catalogue personnalisé et masquez les catalogues intégrés dans le fichier de politique. Cela fonctionne avec ou sans le mode entreprise.

```json
{
  "hideBuiltinSkillCatalogs": true
}
```

Les réglages ne proposent alors que les catalogues ajoutés par les utilisateurs, et OpenChamber ne charge aucun catalogue intégré, même sur demande directe. Il n’y a pas de variable d’environnement pour cela, car un utilisateur peut les définir lui-même.

### Autoriser des origines Git en HTTP simple

Lors de la connexion d’un hébergeur Git (GitLab, Gitea, Gerrit, Forgejo), OpenChamber exige du HTTPS, car un jeton envoyé en HTTP simple peut être lu par n’importe qui sur le réseau. Une machine d’intranet sans HTTPS peut être autorisée dans le fichier de stratégie. Cela fonctionne avec ou sans le mode entreprise. Chacun peut aussi autoriser ses propres origines dans Settings → Git : tant que le mode entreprise est désactivé, sa liste s’ajoute à celle du fichier ; une fois le mode activé, elle est ignorée.

```json
{
  "allowedInsecureGitOrigins": ["http://gitlab.corp.internal"]
}
```

- Chaque entrée est une origine exacte : schéma, hôte et, si utile, port. Sans chemin, sans `*`, sans identifiants. `http://gitlab.corp.internal` ne couvre pas `http://gitlab.corp.internal:8443`.
- Seules les origines listées passent. Les instances publiques de GitHub et GitLab, et tous les autres hôtes, exigent toujours du HTTPS.
- La liste n’ouvre rien d’autre : une extension d’hébergeur auto-hébergé n’accepte toujours que du HTTPS et du HTTP en bouclage local, et les transferts anonymes exigent toujours du HTTPS. Les téléchargements Git LFS suivent la même liste : HTTP en clair uniquement sur une origine listée.
- Retirer une origine de la liste fait refuser à OpenChamber les instances qui y sont liées, jusqu’à ce qu’elles soient reliées à nouveau.
- La liste de Settings → Git suit les mêmes règles : une origine exacte par ligne, et une ligne qui n’est pas une origine acceptée est écartée à l’enregistrement. Une fois le mode entreprise activé, elle est entièrement ignorée — élargir la confiance en clair reste la décision de l’administrateur.

La même liste décide aussi d’où les extensions et les skills peuvent être installés. « Installer depuis une URL » et les mises à jour des extensions refusent normalement les adresses privées, les noms internes (`.internal`, `.local`) et le HTTP simple, car c’est le serveur qui va chercher l’adresse lui-même. Un hôte nommé dans `allowedInsecureGitOrigins` est reconnu de confiance pour cela :

- Son hôte est accepté en HTTPS et en SSH sur n’importe quel port, et en HTTP uniquement sur l’origine exactement listée. Les clones Git et les téléchargements `.zip` suivent tous deux cette règle.
- L’adresse à laquelle il résout ne doit pas être une adresse de bouclage (`127.0.0.0/8`, `::1`) ni lien-local (`169.254.0.0/16`, qui inclut les métadonnées cloud). Les inscrire dans la liste ne change rien.
- Les redirections ne sont jamais suivies aveuglément : chaque saut est vérifié à nouveau, si bien qu’un hôte de confiance ne peut pas renvoyer une installation vers une autre machine d’intranet.
- Les sources de skills écrites sous la forme `http://host/group/repo.git` sont acceptées sur une origine listée.
- Les extensions qui demandent `service`, `network`, `origins` ou `transcript` doivent toujours venir d’un dépôt sous `allowedExtensions`.

### Pointer les métadonnées des modèles vers une adresse interne

Le sélecteur de modèles lit les tailles de contexte et les prix depuis `https://models.dev/api.json`. Sur un réseau sans route vers ce site, indiquez une copie interne de ce fichier. Cela fonctionne avec ou sans le mode entreprise.

```json
{
  "modelsDevUrl": "http://nginx.corp.internal/models/api.json"
}
```

- Le fichier utilise le format de models.dev. Seuls `id`, `name`, `limit`, `modalities`, `cost` et quelques indicateurs de capacité sont lus, donc un fichier court écrit à la main suffit.
- Une fois indiqué, OpenChamber ne lit que cette adresse, côté serveur comme côté navigateur. Il ne revient jamais sur models.dev.
- Une valeur qui n’est pas une URL `http(s)` simple, ou qui porte des identifiants, compte comme non définie.
- Les métadonnées des modèles servent à l’affichage et aux indices de routage. Les sessions fonctionnent sans elles.

### Remplacer les catalogues de skills intégrés

`hideBuiltinSkillCatalogs` ne masque que les catalogues publics. Pour offrir les vôtres à leur place, listez-les :

```json
{
  "skillsCatalogSources": [
    {
      "id": "corp",
      "label": "Skills de l’entreprise",
      "description": "Skills entretenus par l’équipe plateforme",
      "source": "https://gitlab.corp.internal/platform/skills.git",
      "defaultSubpath": "skills",
      "excludedSkills": ["draft"]
    }
  ]
}
```

- `id`, `label` et `source` sont obligatoires. Une source est une URL Git : du HTTPS, du SSH, ou du HTTP pour une origine listée dans `allowedInsecureGitOrigins`.
- Quand la liste n’est pas vide, elle remplace les catalogues intégrés, qu’ils soient masqués ou non.
- Une entrée que le fichier ne sait pas lire rend tout le fichier de stratégie invalide, et alors aucun catalogue n’est proposé.
- Il n’y a pas de variable d’environnement pour cela.

### Exemples

Pour placer le fichier de politique sur un Mac, exécutez ceci dans le Terminal en tant qu’administrateur :

```bash
sudo mkdir -p "/Library/Application Support/OpenChamber"
sudo tee "/Library/Application Support/OpenChamber/policy.json" > /dev/null <<'JSON'
{
  "enterpriseMode": true,
  "organization": "Acme"
}
JSON
```

Sous Linux, c’est pareil avec `/etc/openchamber` comme dossier.

Sous Windows, lancez PowerShell en tant qu’administrateur. La dernière ligne ne laisse le dossier accessible en écriture qu’aux administrateurs et au système :

```powershell
New-Item -ItemType Directory -Force "C:\ProgramData\OpenChamber" | Out-Null
@'
{
  "enterpriseMode": true,
  "organization": "Acme"
}
'@ | Set-Content -Encoding UTF8 "C:\ProgramData\OpenChamber\policy.json"
icacls "C:\ProgramData\OpenChamber" /inheritance:r /grant:r "Administrators:(OI)(CI)F" "SYSTEM:(OI)(CI)F" "Users:(OI)(CI)RX"
```

Un serveur dans Docker, ajouté à l’`environment` de `docker-compose.yml`. Le conteneur écoute au-delà de lui-même, il lui faut donc l’accès réseau autorisé :

```yaml
environment:
  OPENCHAMBER_UI_PASSWORD: ${OPENCHAMBER_UI_PASSWORD}
  OPENCHAMBER_ENTERPRISE_MODE: "1"
  OPENCHAMBER_ALLOW_NETWORK_ACCESS: "1"
  # Optional:
  OPENCHAMBER_RELAY_URL: wss://relay.acme.com/ws
  OPENCHAMBER_JEV_URL: https://llm.acme.com/v1/systemone
  OPENCHAMBER_JEV_MODEL: acme-classifier
  OPENCHAMBER_JEV_API_KEY: ${ACME_JEV_KEY}
  OPENCHAMBER_ALLOWED_EXTENSIONS: https://github.com/acme/
```

Pour vérifier que ça a marché, ouvrez Paramètres → Fournisseurs : un avis sur le mode entreprise avec le nom de votre organisation apparaît en haut.

### Ce qui change

- Les fournisseurs de modèles viennent uniquement de votre configuration OpenCode. Connecter un fournisseur, s’y identifier, ajouter une clé ou créer un fournisseur personnalisé est désactivé dans OpenChamber ; supprimer ou changer de compte existant fonctionne toujours. Cela ferme seulement l’accès par l’application ; le verrou lui-même, c’est la politique OpenCode décrite plus bas. Se connecter à un serveur MCP de votre configuration OpenCode fonctionne toujours, car cela atteint ce serveur et non un fournisseur de modèles.
- Les [Fournisseurs de classification (Jev)](/fr/classification-providers/) restent désactivés, y compris un point de terminaison personnalisé que quelqu’un saisit dans les Paramètres. Le filet de sécurité et Auto ne sont pas proposés, et les sessions en cours ne reçoivent pas l’indication « semble terminé ». Pour utiliser Jev via votre propre infrastructure, fixez un point de terminaison avec `jev` dans le fichier de politique, ou avec `OPENCHAMBER_JEV_URL` (plus `OPENCHAMBER_JEV_MODEL` et, s’il en faut une, `OPENCHAMBER_JEV_API_KEY`). Il devient le choix par défaut, on peut toujours le désactiver, et rien d’autre ne peut être choisi.
- La lecture à voix haute via OpenAI est désactivée. Un serveur personnalisé de synthèse vocale ou de transcription doit tourner sur la même machine. Les voix locales et les modèles de dictée locaux continuent de fonctionner.
- Les notifications push vers les téléphones et les navigateurs ne portent qu’un titre générique comme « Agent response is ready », sans texte de message ni nom de session. Les notifications de bureau restent sur votre machine et gardent le texte complet.
- Les vérifications de mises à jour continuent, pour que les correctifs de sécurité vous parviennent toujours, mais elles ne transmettent jamais de données d’utilisation, pas même l’identifiant d’installation anonyme.
- Les [tunnels externes](/fr/tunnels/) (Cloudflare, ngrok, Tailscale) sont désactivés. Cloudflare et ngrok déchiffrent le trafic à leur périphérie et voient chaque requête en clair ; Tailscale Serve et Funnel ouvrent cette machine à d’autres appareils.
- Les diagrammes `.drawio` s’ouvrent sous forme de texte XML. L’éditeur de diagrammes est une page de diagrams.net, et y ouvrir un diagramme lui transmet le fichier.
- Le catalogue d’intégrations de la barre latérale est masqué. Il installe des services externes depuis une liste fournie avec OpenChamber. Ajouter des serveurs MCP, des plugins et des skills dans les réglages fonctionne comme avant.
- Les polices d’interface et de code chargées depuis un CDN public reviennent aux polices du système. Votre choix est conservé pour le jour où le mode est désactivé.
- Le [Relais privé](/fr/private-relay/) ne fonctionne que via votre propre relais. Faites tourner un [relais auto-hébergé](https://github.com/openchamber/openchamber-relay) et pointez OpenChamber dessus avec `relayUrl` dans le fichier de politique ou avec `OPENCHAMBER_RELAY_URL=wss://relay.example.com/ws`. Le relais partagé ne peut pas lire votre trafic non plus, puisqu’il est chiffré de bout en bout, mais le vôtre garde les métadonnées de connexion et l’accès à cette machine à l’intérieur de votre réseau. Sans votre propre relais, aucun appareil ne peut être associé.
- OpenChamber n’écoute que sur la machine où il tourne. Le réglage de bureau qui permet aux autres appareils du réseau local d’ouvrir l’application est désactivé, et le serveur refuse de démarrer sur une adresse réseau, que ce soit via la CLI (`--host`, `--lan`) ou via l’environnement. Si le fichier de politique apparaît pendant que l’application tourne, les connexions depuis d’autres machines sont coupées jusqu’au prochain démarrage. Autorisez l’accès réseau avec `"allowNetworkAccess": true` dans le fichier de politique, ou avec `OPENCHAMBER_ALLOW_NETWORK_ACCESS=1` là où l’environnement active le mode entreprise. Gardez en tête que la connexion passe en HTTP simple, donc sur un réseau partagé n’importe qui peut la lire ; placez un serveur que d’autres atteignent derrière [votre propre HTTPS](/fr/reverse-proxy/).
- Les [extensions](/fr/extensions/) qui peuvent envoyer des données hors de la machine (celles qui parlent à une API externe, chargent depuis des adresses externes, font tourner un service en arrière-plan ou font envoyer à ce service ce que l’agent dit dans les sessions) ne s’installent que depuis un dépôt Git listé dans `allowedExtensions`. Une extension autorisée qui transmet des notifications ne reçoit que le titre générique, sans texte de message, nom de session ni projet, comme le téléphone. Les extensions qui ne font rien de tout cela s’installent comme d’habitude. Une extension installée depuis n’importe où ailleurs reste désactivée, et les Paramètres expliquent pourquoi. La liste contient des URL de dépôts, puisqu’une extension choisit elle-même son nom ; une entrée qui se termine par `/`, comme `https://github.com/acme/`, autorise tous les dépôts en dessous. Sur les machines des personnes qui développent des extensions, `"allowLocalExtensions": true` autorise aussi l’installation depuis un dossier local. Un ZIP reste bloqué dans tous les cas.
- Les variables d’environnement de **Paramètres → Général** et de `opencode service set env` n’atteignent pas OpenCode, car l’une d’elles pourrait contenir une clé de fournisseur. Git, le terminal et les actions de projet les reçoivent toujours.
- Dans l’extension VS Code, la connexion de fournisseurs est désactivée et les vérifications de mises à jour ne transmettent pas de données d’utilisation. Elle n’a de toute façon ni Jev, ni relais, ni tunnels, ni notifications push, ni synthèse vocale dans le cloud.

Les tâches du petit modèle (titres de session, récapitulatifs, messages de commit, la revue guidée des modifications) n’ont besoin d’aucun mode particulier. Elles tournent toujours sur le petit modèle choisi dans les Paramètres, sur un petit modèle du fournisseur avec lequel vous travaillez, ou sur le modèle par défaut de votre configuration OpenCode. Elles ne se rabattent jamais sur un autre fournisseur qui se trouve simplement connecté.

Quels fournisseurs de modèles peuvent être utilisés, c’est OpenCode qui le décide, pas OpenChamber. Verrouillez-le avec les [politiques OpenCode](https://opencode.ai/v2/docs/policies/) : interdisez tous les fournisseurs, puis autorisez ceux que vous avez approuvés.

```jsonc
{
  "experimental": {
    "policies": [
      { "action": "provider.use", "resource": "*", "effect": "deny" },
      { "action": "provider.use", "resource": "anthropic", "effect": "allow" }
    ]
  }
}
```

Un fournisseur interdit disparaît même si quelqu’un ajoute une clé pour lui. Placez les politiques dans le fichier global `~/.config/opencode/opencode.jsonc`, où un projet ne peut pas les lever, ou diffusez-les depuis un espace de travail OpenCode Console, qui a le dernier mot. Le mode entreprise couvre en plus ce qu’OpenChamber envoie lui-même.

Les recherches web et les récupérations de pages de l’agent passent aussi par OpenCode, vers le service de recherche et vers les pages elles-mêmes. Si elles ne doivent pas quitter votre réseau, interdisez-les avec le même type de politique :

```jsonc
{ "action": "permission", "resource": "websearch:*", "effect": "deny" },
{ "action": "permission", "resource": "webfetch:*", "effect": "deny" }
```
