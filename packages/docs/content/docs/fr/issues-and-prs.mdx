# Issues et PR

Le tableau **Issues and PRs** est une page entière qui liste les issues et pull requests GitHub, GitLab, Gitea, Forgejo ou Gerrit d'un projet (merge requests sur GitLab, changements sur Gerrit, qui n'a pas d'issues), ou tes issues Linear. Choisis un élément et son aperçu s'ouvre à côté de la liste. Regarder un autre projet ici ne change pas le projet sur lequel se trouve le reste de l'app.

## Ouvrir le tableau

- Clique sur l'icône de pull request dans l'en-tête de la barre latérale, à côté des tâches planifiées et de l'archive.
- Choisis **Issues and PRs** dans la palette de commandes.
- Appuie sur <kbd>⌘K</kbd> puis <kbd>B</kbd> (<kbd>Ctrl+K</kbd> puis <kbd>B</kbd> sous Windows et Linux). Les mêmes touches le referment.

Sur un téléphone, touche le bouton de pull request en bas du menu des sessions. Le tableau n'existe pas dans l'extension VS Code.

Le tableau se rouvre sur le projet, l'onglet et l'équipe où tu l'as laissé.

## Trouver des éléments

Tout tient sur une seule ligne de barre d'outils. À gauche, le sélecteur de projet, avec les icônes de projet et une recherche. À côté, tu passes de **Issues** à **Pull requests** ou **Linear**. Les issues et pull requests viennent de l'hébergeur du projet : GitHub, GitLab, Gitea, Forgejo, Gerrit, ou un hébergeur ajouté par une [extension](/fr/extensions/#une-extension-comme-hébergeur-git). L'onglet **Linear** n'apparaît qu'une fois Linear connecté. Un projet sur aucun de ces hébergeurs n'affiche que cet onglet, ou indique qu'il n'y a rien à lister. Un remote sur un alias d'hôte de `~/.ssh/config`, comme `github.com-work`, ne compte pour aucun d'eux.

Si le dossier d'un projet n'est pas lui-même un dépôt Git mais contient des dépôts, un second sélecteur à côté du sélecteur de projet choisit ce que liste le tableau. **All repositories** vient en premier et c'est le choix par défaut : le tableau liste ensemble les issues et pull requests de tous les dépôts GitHub du dossier, et chaque ligne indique son dépôt. La recherche porte sur tous, y compris un lien collé ou un numéro. Une note au-dessus de la liste indique combien de dépôts ne sont pas inclus, par exemple un dépôt sur GitLab, Gitea, Forgejo ou Gerrit, ou un dépôt qu'aucun compte connecté ne peut lire, et son menu montre lesquels et pourquoi. Choisis un seul dépôt pour ne lister que celui-là. Le tableau retient ce choix pour chaque projet, et il est distinct du dépôt sélectionné dans la vue Git.

Les commentaires, labels, reviewers et merges s'appliquent au dépôt auquel appartient l'élément. **New session** démarre toujours dans le dossier du projet. **Changes** et **Walkthrough** ouvrent la pull request dans son propre dépôt et laissent tel quel le dépôt sélectionné dans la vue Git. Démarrer le travail dans un worktree n'est pas encore proposé pour ces éléments. Un lien vers une issue ou une pull request de l'un de ces dépôts s'ouvre dans le panneau Suivi, lu via ce dépôt. Sur le téléphone, il s'ouvre sur le tableau, qui passe à **All repositories** pour le trouver. L'extension VS Code n'a pas de tableau, donc rien de cela n'y change quoi que ce soit.

Sur **Linear**, le sélecteur de projet devient un sélecteur d'équipe : choisis **All teams** ou une équipe. Pour un projet qui n'a que **Linear**, le sélecteur de projet reste à côté du sélecteur d'équipe, pour que tu puisses passer à un autre projet. Si tu as connecté plus d'un espace de travail Linear, change d'espace depuis le même menu. La connexion à Linear est décrite dans [Intégrations](/fr/integrations/).

La recherche accepte un titre, un numéro ou un lien collé. Le menu des filtres reste ouvert pendant que tu choisis, tu peux donc combiner les filtres.

Pour GitHub, GitLab, Gitea, Forgejo et Gerrit :

- Statut : **Open**, **Closed**, **All**, et **Merged** pour les pull requests
- Personnes : **Anyone**, **Assigned to me**, **Created by me**, et **Review requested** pour les pull requests

Pour Linear :

- Statut : **Open**, **All**, **Backlog**, **To Do**, **In Progress**, **In Review**, **Done**, **Canceled**, **Duplicate**
- Personnes : **Anyone**, **Assigned to me**, **Created by me**
- Priorité : **All priorities**, **Urgent**, **High**, **Medium**, **Low**, **No priority**

## Lire un élément

L'aperçu montre la description, les labels et les commentaires. Sur une issue Linear, clique sur la pastille de statut pour la passer dans un autre état de l'équipe.

La ligne **Labels** a un bouton crayon qui ouvre la liste des labels du dépôt, avec une recherche. Coche ou décoche-les. La modification est enregistrée quand tu fermes la liste, donc plusieurs clics comptent pour une seule modification. Une pull request ouverte (merge request sur GitLab) a aussi une ligne **Reviewers** qui fonctionne de la même façon, avec les personnes qui peuvent faire une review dans le dépôt. Sur GitHub, l'auteur de la pull request n'est pas proposé. Les issues Linear n'ont aucune de ces lignes.

## Commenter et faire une review

Sous l'activité d'une issue ou d'une pull request se trouve une zone de commentaire. **Comment** publie ton texte sur l'hébergeur du dépôt, tout comme <kbd>⌘</kbd>+<kbd>Enter</kbd> (<kbd>Ctrl</kbd>+<kbd>Enter</kbd> sous Windows et Linux). Le texte reste dans la zone jusqu'à sa publication, donc un envoi raté ne fait rien perdre. Passer à un autre élément vide la zone. Les issues Linear n'en ont pas.

Une pull request ouverte (merge request sur GitLab) a aussi **Approve** et **Request changes**, et le texte de la zone part avec la review. **Request changes** demande un texte qui dit quoi changer. La review porte sur les commits affichés dans l'aperçu. Si quelqu'un a poussé depuis, elle est refusée et l'aperçu se rafraîchit pour que tu puisses regarder à nouveau. Sur GitLab, **Request changes** fonctionne si tu es reviewer de la merge request, et le texte de la review est publié comme un commentaire séparé. Si seul ce commentaire échoue, la review compte quand même et ton texte reste dans la zone.

Un changement Gerrit a une ligne pour chacun des labels du projet, comme Code-Review et Verified, avec les notes que tu as le droit de donner ; choisis-les et choisis **Voter**. Ton texte part avec les votes comme message. Les votes portent sur le dernier patchset, ils ne sont donc pas proposés pendant que tu en lis un plus ancien.

## Démarrer le travail

Les actions se trouvent en bas de l'aperçu.

- **New session** ouvre une nouvelle session dans le projet, avec l'élément joint à la zone de message. Tu écris toi-même le premier message.
- **Start in worktree…** sur une issue, ou **Check out in worktree…** sur une pull request, ouvre la boîte de dialogue New Worktree avec l'élément déjà choisi. Une pull request récupère sa propre branche. Voir [Sessions worktree](/fr/worktrees/).

Pour une issue Linear, **Start in** montre le projet où la session démarrera. C'est le projet associé à l'équipe de l'issue dans la carte Linear de [Intégrations](/fr/integrations/). Sans association d'équipe, c'est le projet par défaut, et sans lui, le dernier projet affiché par le tableau. Tu peux y choisir un autre projet pour cette issue.

## Pull requests

L'aperçu d'une pull request montre aussi sa branche, sa taille (lignes ajoutées et supprimées, fichiers modifiés), ses checks et sa review. Le fil **Activity** range les commentaires, les verdicts de review et les commits les plus récents dans l'ordre où ils sont arrivés. Les commits qui se suivent sont regroupés, tu vois donc à quels commits une review a répondu.

Deux boutons se trouvent à côté de la taille. **Changes** ouvre le diff de la pull request dans le panneau latéral, et **Walkthrough** ouvre sa [parcours des modifications](/fr/walkthrough/). Si l'app est sur un autre projet, elle passe d'abord au projet de la PR. Sur le téléphone, **Changes** ouvre la PR dans l'onglet **Git** du panneau de travail ; **Walkthrough** n'existe que sur le bureau et le web.

En bas, **Merge** demande confirmation avant de fusionner et utilise ta méthode de merge habituelle. Un brouillon a aussi **Ready for review**.

Sur Gerrit, l'aperçu montre aussi le sujet du changement, et s'il est privé ou en cours. Quand un changement a plus d'un patchset, un sélecteur à côté de **Changes** choisit celui d'où viennent les fichiers et le diff ; il démarre sur le dernier. **Merge** devient **Soumettre**, et reste désactivé tant que les conditions de soumission du changement ne sont pas remplies, avec celles qui manquent indiquées à côté. **Close** et **Reopen** deviennent **Abandonner le changement** et **Restaurer le changement**.

Une issue ou une pull request ouverte a aussi en bas **Close issue** ou **Close pull request** (**Close merge request** sur GitLab), et une fermée a **Reopen issue** ou **Reopen pull request** (**Reopen merge request**). Aucune confirmation n'est demandée, puisqu'on peut annuler. Une pull request fusionnée ne peut être ni fermée ni rouverte. Sur GitHub, une issue est fermée comme terminée.
